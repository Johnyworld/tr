## 0. 한 줄 요약

**포스트아포칼립스 세계에서, 코드가 돌리는 냉정한 시뮬레이션 위에 AI GM이 이야기를 연출하는 1인용 TRPG.** 주인공은 언젠가 죽고, 세계는 계속된다.

- 장르: 포스트아포칼립스 생존 + 무리 간 전쟁
- 판정: 2d6 (성공 / 대가 있는 성공 / 실패)
- 영감: Project Zomboid(어려움, 죽음이 끝), Apocalypse World(2d6 판정, 장르), Crusader Kings(이벤트, 계승), Fallen London(스토리렛)
- 형태: 로컬 MCP 서버. Claude 앱 세션이 GM이 되어 채팅으로 플레이한다 (11.5). 웹 앱 모드는 12-14에 폐기

**프로젝트 목표**

1. 위 게임을 만든다
2. **RAG를 직접 구현해 본다.** 임베딩 모델과 벡터 검색은 가져다 쓰고, 청킹·메타데이터 설계·검색 시점·프롬프트 조립·평가를 직접 만든다. 끝없이 진행되는 게임이라 장기 기억이 계속 커지므로 RAG가 실제로 필요한 구조다 (11.4)
3. 게임 시스템은 그대로 두고 다른 세계관을 **시나리오 팩**으로 추가할 수 있게 한다 (12.3). 이 문서의 세계관·능력치·자원 등은 첫 시나리오 팩 `post_apoc`의 내용이다

## 1. 핵심 원칙

이 원칙은 모든 설계 판단의 기준이다.

1. **코드는 세계의 물리 법칙, AI는 GM 겸 연출가.** 판정, 상태 변경, 시뮬레이션은 전부 코드가 한다. AI는 상황을 해석하고 결과를 서술한다.
2. **AI는 숫자를 만들지 않는다.** 피해량, 가격, 병력 수, 시간, 관계 변화량은 모두 코드가 계산한다. AI가 세계를 바꾸고 싶으면 반드시 tool call로 요청하고, 코드가 검증한 뒤 적용한다.
3. **AI는 캐릭터를 죽일 수 없다.** 사망은 오직 코드의 부상 트랙과 판정 결과로만 일어난다.
4. **AI는 캐릭터가 아는 것만 안다.** AI 프롬프트에는 세계의 진짜 상태(World State)가 아니라, 현재 캐릭터의 인식 상태(Belief State)만 들어간다. **RAG 검색 결과도 마찬가지다.** 현재 캐릭터가 알 수 없는 청크는 검색 결과에 절대 포함되지 않는다.
5. **어렵지만 억울하지 않게.** 위험은 미리 암시하고, 눈치챌 판정 기회를 준다. 실패는 끝이 아니라 다른 갈래로 이어진다.
6. **플레이어 입력은 의도일 뿐이다.** "금화 1만 개를 얻는다" 같은 서술은 사실이 아니라 행동 의도로 해석하고, 결과는 코드가 판정한다.

## 2. 세계관

### 2.1 배경

- 붕괴 후 몇 년이 지난 **한국의 가상 중소도시**
- 감염체(좀비류)는 세력이 아니라 **환경 위협**: 소음과 빛에 반응하고, 조우 테이블과 월드 클락의 재료가 된다
- 핵심 정서: **희소성과 긴장감.** 식량, 물, 탄약, 의약품, 연료가 늘 부족하고, 모든 행동에 비용이 따른다
- 계절이 순환하며, 겨울마다 자원 압박이 커진다 (9.6)

### 2.2 세력

A + B 연합이 C와 전쟁 중이다. 연합(110명)은 C(200명)에 약 2:1로 열세이며, 중립인 D와 E가 어느 쪽에 기우느냐가 판도를 가른다.

| 세력 | 이름 | 규모 | 입장 | 성격 |
|---|---|---|---|---|
| A | 청솔형제단 | 70 | 연합 (중심) | *초안:* 원칙을 지키려 하지만 그 원칙 때문에 손해를 보는 무리 |
| B | 버들마을 | 40 | 연합 | *초안:* A에게 기대지만 속으로는 불안한 동맹. C가 회유하기 좋은 틈 |
| C | 붉은연합 | 200 | 적대 | **이익 앞에서 잔혹함.** *초안:* 규모는 크지만 공포로 묶여 있어 결속이 약함 |
| D | 하얀매 | 30 | 중립 | *초안:* 의료나 기술처럼 모두가 원하는 것을 가진 작은 무리 |
| E | 나루상단 | 50 | 중립 | *초안:* 실리적인 상인 집단. 이기는 쪽에 붙으려 함 |

- 이름은 `post_apoc` 콘텐츠(세력·구역·아이템·NPC·로어·스토리렛)에 쓴다. 이 문서는 짧게 A~E로 부르고, 내부 id도 `faction_a`~`faction_e` 그대로다
- 거점: 청솔형제단은 옛 공업고, 버들마을은 서쪽 옛 아파트 단지, 붉은연합은 동쪽 옛 공단, 하얀매는 옛 보건소(진료소), 나루상단은 강 하류 휴게소 장터와 정수장
- C의 약점을 "공포로 묶인 결속"으로 두면, 숫자로는 못 이기지만 내부를 흔들어서 이기는 플레이가 가능해진다
- 2~5명 규모의 **외부 생존자 무리**와 **혼자 생존자**도 존재한다. 이들도 같은 세력 스키마를 쓰는 "아주 작은 세력"이다 (`minor: true`)

> *초안* 표시는 확정 전 제안이다.

## 3. 플레이 구조

### 3.1 끝없는 진행, 죽음과 계승

- **엔딩 조건은 주인공 사망뿐.** 죽지 않으면 계속 진행된다
- 사망하면 **같은 세계에서** 새 캐릭터로 이어간다
  - 새로 만든 캐릭터, 또는 **이미 등장한 NPC** 중 하나를 선택
  - 이를 위해 주요 NPC는 처음부터 플레이어와 **같은 스키마**(능력치, 인벤토리, 관계, Belief State)를 가진다
- 새 캐릭터는 이전 캐릭터의 기억을 모른다. 플레이어는 알고 캐릭터는 모르는 상황 자체가 재미가 된다
- 이전 캐릭터의 행적 일부는 소문이나 전설로 세계에 남는다

### 3.2 연대기

좀보이드의 "당신은 N일 동안 생존했습니다"처럼, 죽은 캐릭터의 기록을 남긴다.

- 생존 일수, 소속, 최종 등급, 주요 행적, 사망 원인
- AI가 짧은 회고나 묘비명을 작성

### 3.2.1 구현 (11단계)

- **사망 기록**: 부상 트랙이 사망 단계에 이르면 코드가 연대기 기록을 만든다 (`character_died`). 이름, 소속, 최종 등급, 시작·사망 시각(생존 일수), 공적, 사망 원인(선언한 위험의 원인, 전투 중이면 "OO 전투에서 …"), 행적(중대한 것부터 5개)
- **묘비명**: AI가 쓰는 유일한 부분. `write_epitaph(text)` (한두 문장, 한 번만, 막 죽었을 때만). MCP는 GM이 호출하고, 웹 앱은 GM이 남기지 않았으면 작은 모델(`SUMMARY_MODEL`)이 기록과 마지막 장면으로 쓴다
- **다음 캐릭터 후보**: 새 캐릭터(시작 역할), 또는 이전 캐릭터가 알던 살아 있는 `playable` NPC
- **계승** (`character_switched`): 플레이어 id가 바뀌고, 복무 시작 시각·장면 인물·느낀 태도·오늘의 임무·구역·진행 중인 이야기를 새로 시작한다
  - 새 캐릭터: id `pc_<n>`, 역할의 시작값과 시작 지식(역할의 지식이지 이전 캐릭터의 기억이 아니다), 아는 인물은 역할의 `known_npcs` (서로 이름을 안다, 6.3)
  - NPC: 그 인물의 믿음·소지품·상태를 그대로 쓰고, 같은 무리 사람들을 안다
- **이전 캐릭터들의 흔적** (기억이 아니라 소문): 바로 앞 캐릭터만이 아니라 지난 하루 안에 죽은 플레이어 캐릭터 모두가 대상이다 (그 사이 여러 명이 죽었을 수 있다). 죽음은 같은 무리면 보고, 아니면 소문으로 듣는다. 같은 무리면 지난 하루 우리 무리가 낀 교전(이전 캐릭터가 죽은 전투 포함)도 보고로 듣는다 (12-3, 세이브의 `recentClashes`). 이어받는 인물이 직접 보거나 전해 들은 이전 캐릭터들의 행적은 언제 일이든 그 출처로 기억한다 (한 사람당 3개). 아는 행적이 없는 최근 사망자는 가장 큰 행적(중대함 2 이상) 하나를 소문으로 듣는다. 같은 문장의 믿음은 다시 넣지 않는다
- **기억의 경계**: 요약·일지·지난 이야기는 현재 캐릭터의 것만 (요약에 캐릭터 id, 6-1). memory 색인은 knownBy로 거른다. 웹 앱 GM의 대화 기록은 계승 경계(`characterSwitch` note)부터 새로 시작한다
- 역할의 상관이 플레이어 자신이 되거나 죽었으면 상관은 없다 (임무 배정·보고, 스토리렛의 commander 배역도 없다)
- MVP: 계승한 NPC도 역할 규칙(임무 목록, 스토리렛 태그)은 시작 역할의 것을 쓴다. 역할 선택은 2차 (3.4)
- 화면: 웹은 사망하면 입력창 대신 연대기와 후보 버튼(새 캐릭터는 이름 입력), MCP는 `get_chronicle` → `choose_next_character(character_id, name?)`. `!연대기`는 기록과 (사망했다면) 후보를 보여 준다. 연대기는 플레이어(사람)를 위한 기록이라 GM 컨텍스트에는 넣지 않는다

### 3.3 아이언맨 모드

- 자동 저장만 있고 되돌리기는 없다
- 개발 중에는 이벤트 로그 기반의 디버그용 되돌리기만 별도로 둔다

### 3.4 역할과 소속 등급

역할은 별도 로직이 아니라 **캐릭터 생성 시의 초기값 묶음**(YAML)으로 정의한다. 소속 등급은 게임 안에서 오르내리며, 역할 선택은 "이 사다리의 어느 칸에서 시작할지"를 고르는 것이다.

| 등급 | 접근 가능한 것 | 플레이 감각 |
|---|---|---|
| 혼자 | 자기 소지품 | 순수 생존 |
| 외부 무리 일원 (2~5명) | 작은 공동 자원, 동료 몇 명 | 소규모 생존 + 동료 관계 |
| 세력 하급 전투원 | 배급, 임무 | 명령을 받고 위로 올라갈 기회를 노림 |
| 분대장 | 소수 인원 지휘 | 책임과 판단 |
| 세력 간부 | 자원 관리, 지도부 회의 | 결정을 내리고 책임을 짐 |

- **MVP: A의 하급 전투원으로 고정 시작.** 올라가는 재미가 핵심
- 이후: 시작 역할을 혼자 / 외부 무리 / A~E 일원 / 간부 중 선택 가능
- 사망 후 새 캐릭터를 고를 때도 같은 선택지를 사용

```yaml
# content/roles/a_grunt.yaml
id: role_a_grunt
label: 세력 A 하급 전투원
faction: faction_a
rank: grunt
default_name: 신병
start_stats: { strength: 1, agility: 2, cool: 0, sense: 1, persuasion: -1 }
start_location: a_base
start_inventory: [kitchen_knife, water_bottle]
access: [ration, mission_board]
beliefs_preset: a_grunt
storylet_tags: [grunt, squad_life]
```

## 4. 판정 시스템: 2d6

### 4.1 기본 규칙

2d6 + 능력 + 스킬 보정 (4.2)

| 결과 | 의미 |
|---|---|
| 10 이상 | 성공 |
| 7~9 | **대가 있는 성공** (성공하지만 무언가를 잃거나, 복잡해지거나, 선택을 강요받음) |
| 6 이하 | 실패 (GM이 상황을 악화시킬 권리를 얻음) |

| 보정치 | 성공 | 대가 있는 성공 | 실패 |
|---|---|---|---|
| -1 | 8% | 33% | 58% |
| +0 | 17% | 42% | 42% |
| +1 | 28% | 44% | 28% |
| +2 | 42% | 42% | 17% |

- 종 모양 분포라 능력치와 준비가 결과에 잘 반영된다
- "대가 있는 성공"이 AI GM이 이야기를 굴리는 핵심 재료
- 판정 함수는 교체 가능하게 만든다 (나중에 분포 조정 가능)
- 보정 = 능력 + 스킬(합쳐서 최대 +4) + 난이도 + 몸 상태 패널티. AI는 스킬·능력·난이도를 enum으로만 고른다
  - 난이도 (*임시*): 쉬움 +1 / 보통 0 / 어려움 -1

### 4.2 능력과 스킬 (12-4)

> 예전의 "능력치 5개 + 기본 행동 6개"를 대체했다. 판정의 이름(능력·스킬·범위·상한·성장 수치)은 모두 시나리오 팩 데이터이고, core는 이름을 모른다

**판정**: 2d6 + 능력 + 스킬 + 난이도 + 몸 상태 보정. 결과 구간(10+ / 7~9 / 6-)은 그대로

- **능력 + 스킬은 최대 +4**까지만 더한다 (마스터에 능력 +2여도 +4). 2d6에서 보정 +5부터는 실패가 사라져 긴장이 없어지기 때문이다
- 난이도: 매우 쉬움 +2 / 쉬움 +1 / 보통 0 / 어려움 -1 / 매우 어려움 -2

**능력** (-1 ~ +2): 타고난 것. **계급·역할과 관계없다.** 같은 하급 전투원도 누구는 싸움을, 누구는 머리를 잘 쓴다. 분대장이 멍청할 수도 있다. 바뀌지 않는다

| 능력 | 뜻 |
|---|---|
| 근력 | 힘, 완력 |
| 민첩 | 손발의 빠르기, 정확함 |
| 체력 | 버티는 몸, 지구력 |
| 감각 | 보고 듣고 알아차림 |
| 냉정 | 압박 속의 침착함 |
| 매력 | 사람을 끄는 힘. 판정 밖에서도 작용한다 (아래) |
| 지능 | 배우고 기억하고 따지는 머리 |

- 새 캐릭터 (12-6 캐릭터 생성): 플레이어가 **이름·성별·능력·초상화**를 정한다. 웹은 넷 다 정하고 포인트를 남김없이 써야 시작할 수 있다 (기본값으로 채우지 않는다). 능력은 포인트 구매: 모두 0에서 시작해 4포인트를 나눠 쓴다 (+1은 1, +2는 3, -1로 낮추면 1을 돌려받고 2개까지). 4포인트는 배열 [+2, +1, +1, 0, 0, 0, -1]과 같은 무게다. "무작위"는 코드가 포인트를 배분한다
  - 직업·출신 선택은 보류. 시작 역할(하급 전투원)과 시작 훈련은 역할이 정한다
  - 사망 뒤 "새 캐릭터"로 이어 갈 때도 같은 규칙으로 만든다 (웹: 생성 화면, MCP: `choose_next_character(new)` 뒤 대화로 한 단계씩). 고르지 않고 만들어지는 캐릭터는 배열을 무작위로 섞는다
  - 규칙 수치(포인트, 값별 비용, 낮출 수 있는 수, 성별 목록)는 시나리오 `creation`, 검증은 core(`game/creation.ts`). 웹은 생성 화면, MCP는 아래의 대화식 생성
  - **MCP는 대화로 한 단계씩** (12-13, core `game/creationFlow.ts`): 생성도 이야기의 일부로 느껴지게, GM이 장면처럼 하나씩 묻는다. 새 게임은 그 앞에 월드·시나리오 고르기가 있다 (12.4). 순서: 지금 상황(새 게임만) → 이름 → 성별 → 능력(하나씩 정하기면 능력 7개를 차례로 / 운에 맡기기) → 트레잇(직접이면 약점 → 강점 → 성격 / 운에 맡기기 / 없이) → 확인(이대로 시작·한 단계 뒤로·처음부터 다시)
    - `start_session(new_world)`·`choose_next_character(new)`가 초안을 열고 첫 단계를 돌려준다. 그 뒤 `create_character(answer | back)`로 한 단계씩. 단계마다 코드가 묻는 것, 보기(클릭 도구용 값과 이름), 남은 포인트·고를 수 있는 값과 트레잇을 계산해 주고 답을 검증한다 (GM은 숫자를 만들지 않는다). 운에 맡기면 그 자리에서 굴려 확인 단계에 보여 준다
    - 월드 이야기는 `intro`(`prompts/intro.md`), 지금 상황은 시나리오(`roles/*.yaml`의 `scenario.intro`), 단계별 서술 힌트는 `creation.narration` (12.4). 사망 뒤 새 캐릭터는 둘 다 없이 "다른 사람의 삶"으로 운을 띄운다
    - 초안은 MCP 서버 메모리에만 있고, 확인을 마쳐야 세이브가 생긴다. `character`를 한 번에 넘기는 길은 자동 진행·테스트용으로 남긴다
    - 12-11의 브라우저 생성(상태 화면의 생성 화면, `create_in_browser`, `open_sheet`)은 이것으로 바꾸며 뺐다. 상태 화면은 만드는 동안 "캐릭터를 만드는 중" 안내를 보여 준다
  - 초상화는 id만 세이브에 남고, 화면이 코드로 그린 실루엣 12종(`ui/Portrait.tsx`) 중 하나를 그린다. 그림 파일이 생기면 이미지로 바꾼다
  - 캐릭터에 `gender`, `portrait`가 생겼다. NPC도 콘텐츠에 성별이 있다 (GM 상태의 인물 줄에 보인다)
- NPC는 콘텐츠에서 한 사람씩 정한다
- 매력의 수동 효과: 처음 만난 NPC의 호감 시작값 + (매력의 절반, 내림), 호감이 오르는 관계 변화에 매력 +2면 +1. 이성 관계는 3차 범위(연애)에서

**스킬** (-1 할 줄 모름 / 0 아마추어 / +1 숙련 / +2 마스터): 배우는 것. 역할이 시작 훈련을 준다 (하급 전투원은 근접전·사격). 스킬마다 쓸 수 있는 능력이 정해져 있고, GM은 그중 상황에 맞는 하나를 고른다. 스킬마다 기본값(배우지 않았을 때)이 있다

| 분류 | 스킬 | 능력 | 기본값 | 용도 |
|---|---|---|---|---|
| 전투 | 근접전 | 근력/민첩 | 0 | 칼·몽둥이·맨손 |
| | 사격 | 민첩/감각 | -1 | 총, 활 |
| 몸 | 은밀 | 민첩 | 0 | 들키지 않고 움직이기 (숨은 목격자 확률) |
| | 버티기 | 체력/냉정 | 0 | 고통·공포·추위 속에서 행동 |
| 감각 | 경계 | 감각 | 0 | 낌새, 숨은 목격자 살피기 (NPC의 경계가 목격 확률에도 들어간다) |
| | 수색 | 감각/지능 | 0 | 물자와 단서 찾기 |
| 사람 | 교섭 | 매력 | 0 | 설득, 흥정 |
| | 거짓말 | 매력/냉정 | 0 | 속이기 |
| | 위협 | 근력/냉정 | 0 | 겁주기, 압박 |
| 생존 | 생존 | 체력/감각 | 0 | 추적, 야외에서 버티기, 먹을 것·물 구하기 |
| | 응급처치 | 지능/감각 | -1 | 상처 돌보기 (치료사 없이 소모품을 더 잘 쓰기) |
| 지식 | 감염체 | 지능 | -1 | 감염체의 습성·약점·감염 징후 |
| | 역사 | 지능 | -1 | 붕괴 전후의 일, 지역과 무리들의 내력 |
| | 차량정비 | 지능/민첩 | -1 | 차량·발전기·기계 고치기 |
| | 목공 | 근력/지능 | -1 | 바리케이드, 덫, 수리 (준비물 설치에 쓴다) |
| | 전략 | 지능/냉정 | -1 | 전투·전쟁 수행. 지휘관에게 중요 (전투 장면의 배경 교전, 2차의 지휘) |

- 지식 스킬 판정은 "아는가/떠올리는가"를 정한다. 성공해도 사실은 lore·memory 검색(RAG)과 상태에서만 나온다. GM이 지식을 지어내지 않는다. 실패하면 모르거나 틀리게 기억한다 (틀린 믿음으로 남길 수 있다)
- 시나리오 팩 데이터: 능력·스킬 목록, 스킬별 능력·기본값, 범위, 상한. core는 이름을 모른다

**경험치와 성장**

- 경험치: 판정 성공 +1, 대가 있는 성공 +1, **실패 +2** (실패에서 배운다), 공적 1당 +2. 판정 경험치는 하루 최대 6 (사소한 판정을 쌓아 올리는 것을 막는다)
- 레벨업: 경험치 10, 그다음 15, 20, 25… (+5씩). 레벨업마다 **스킬 하나 +1** (최대 +2). 능력은 오르지 않는다
- 고르는 것은 플레이어다. 쌓인 레벨업은 상태와 `!상태`에 보이고, GM이 플레이어에게 물어 `learn_skill(skill)`로 올린다
- 다음 캐릭터로 이어 가면 경험치·레벨은 그 캐릭터의 것이다 (NPC로 이어 가면 그 인물의 스킬)

**몸 상태 추가: 추위와 질병** (4.5에 더한다. 허기·감염과 같은 틀: 최상 0, 나빠질수록 마이너스, 마지막 단계에서 하루마다 부상. 사망은 부상 트랙으로만)

- 몸 상태 보정은 능력 + 스킬 상한(+4)과 별개로 뒤에서 뺀다. 마스터라도 다치고 굶고 얼면 약해진다
- 몸이 좋을 때의 보너스(예: 잘 쉬고 든든하면 +1)는 **보류**한다

| 트랙 | 단계 (판정 보정) | 나빠지는 원인 | 나아지는 길 |
|---|---|---|---|
| 추위 | 따뜻함 0 → 쌀쌀함 0 → 추위 -1 → 저체온 -2 | 하루마다 계절·날씨의 추위(겨울, 눈, 한파, 비에 젖음)만큼. 우리 거점에서 무리의 연료가 있으면 막아 준다. 밖에서 밤을 나면 더 춥다 | 연료가 있는 거점에서 하루를 나면, 방한 물건(담요·방한복)을 쓰면, 불을 피우면(생존 판정) |
| 질병 | 없음 0 → 잠복(숨김) 0 → 앓음 -1 → 위중 -2 | 하루마다 확률. 굶주림 이상·추위 이상·무리의 물 부족(더러운 물)·북적이는 거점에서 높아진다. **체력**이 높으면 덜 걸린다 | 약(항생제 등), 치료사, 따뜻하고 배부르게 쉬면 하루마다 확률로 낫는다 (체력이 높을수록 잘 낫는다) |

- 질병의 잠복은 감염처럼 캐릭터도 GM도 모른다. 앓기 시작하는 날 알게 된다
- 감염(감염체에게서)과 질병(몸이 약해져서)은 따로다. 감염은 상처에서, 질병은 생활에서 온다
- 체력은 질병에 걸리고 낫는 확률에, 버티기 스킬은 추위·고통 속 판정에 쓴다
- 수치(계절·날씨별 추위, 확률, 배수)는 시나리오 팩 `body.cold`, `body.disease` (*임시*): 겨울 1, 눈·비 1, 한파 2, 방한복 -1, 연료 하루치 이상인 우리 거점에서 2단계 녹음. 질병 하루 1% + 굶주림 5% + 추위 5% + 무리의 물 부족 6%, 체력 1당 25% 덜, 배부르고 따뜻하면 하루 35%(+체력 1당 10%)로 낫고 아니면 30%로 깊어짐
- 새 아이템: 담요(쓰면 추위 2단계), 방한복(들고 있으면 추위 1 덜), 해열제(질병 1단계). 치료사는 질병도 1단계 낫게 한다
- 불 피우기(생존 판정)로 몸을 녹이는 것은 아직 없다. 지금은 거점의 연료·담요·방한복으로만 막는다

**구현** (12-4)

- 시나리오 팩: `stats`(능력), `moves`(스킬: 쓸 수 있는 능력·기본값·분류), `ranges`(능력·스킬 범위, 상한 +4), `ability_array`, `growth`, `charm`, `renamed.abilities`(옛 능력 id → 새 id)
- 판정 공식은 `engine/checks.ts`: `min(상한, 능력 + 스킬) + 난이도 + 몸 상태`. `check_rolled.modifiers`에 `skill`이 생겼다 (이전 이벤트는 0)
- `take_action.check`의 필드 이름은 그대로 `move`(스킬)·`stat`(능력)이다. 두 모드의 GM과 이전 기록이 같은 이름을 쓰게 두었다. 임무 조건·스토리렛 판정도 스킬 id(예전 행동 id를 그대로 이어 씀: fight, scavenge, sense_danger, stealth, endure, persuade)
- 경험치는 `engine/growth.ts`: 판정마다(`rollPlayerCheck`), 임무 보고·스토리렛 공적·전투 공적에서 `xp_gained` 이벤트. 레벨은 코드가 계산해 이벤트에 담고, 레벨업은 `skillPoints`로 쌓인다. `learn_skill` tool(두 모드 공통, 시간 안 씀)이 `skill_learned` 이벤트로 올린다
- 숨은 목격자의 주의력(8.2)은 그 NPC의 감각 + 경계 스킬(상한까지)
- 매력: 처음 장면에 들어온 NPC(아직 플레이어를 향한 관계가 없는)에게 `relation_changed`(첫인상), 플레이어를 향한 호감 변화에 +1 (`engine/charm.ts`)
- 새 캐릭터(새 세계, 사망 후 새 신병)는 세계의 RNG로 능력 배열을 섞는다. NPC는 콘텐츠의 능력·스킬
- 세이브: 캐릭터에 `skills`, `xp`, `level`, `skillPoints`, 상태에 `xpToday`. 이전 세이브는 옛 능력을 옮기고(교섭 → 매력), 없는 능력은 0, 스킬은 기본값으로 읽는다. `SAVE_SCHEMA_VERSION` 3
- 화면: `!상태`(능력, 분류별 스킬, 레벨·경험치), 웹 시트(능력, 할 줄 아는 스킬, 레벨), 판정 카드("감각 + 사격", 보정 내역에 스킬), 성장 카드
- 콘텐츠: 하급 전투원의 시작 훈련 근접전 +1·사격 +1 (능력은 섞는다), NPC 16명의 능력 7개와 스킬, 새 아이템(담요·방한복·해열제), 겨울옷 배급·약국 스토리렛
- 랜덤 자동 플레이 (1500턴 × 5시드, 약 60일): 오류 0. 런 사망 평균 15.2 → 17.8회 (추위로 런마다 0~2회, 질병은 잠복 1~3회). 레벨업은 캐릭터당 1회 남짓 (랜덤 플레이는 공적이 적다)
- 숨은 단계 누출 수정: 소모품·치료사가 "쓸 필요가 있는가"를 캐릭터가 아는 단계로 판단한다. 잠복기에 약을 쓰려 하면 아무 일 없을 때와 똑같이 "쓸 필요가 없다"

### 4.4 부상 (*초안*)

상태 트랙의 이름·단계·보정은 시나리오 팩이 정한다. 사망은 `harm_track`의 마지막(fatal) 단계로만 일어난다

- 부상 트랙: 무사 → 경상 → 중상 → 치명상 → 사망
- 부상 패널티 (*임시*): 경상 -1 / 중상 -2 / 치명상 -3
- 피해는 반드시 **판정 하나**에 묶이고, 위험은 **판정 전에** 선언한다 (`take_action`의 `check.harm_on_failure`)
  - 대가 있는 성공: 1단계 악화
  - 실패: 선언한 위험에 따라 가벼운 피해 1단계, 심각한 피해 2단계 (*임시*)
  - 성공했거나 위험을 선언하지 않았으면 다치지 않는다
- 부상은 며칠간 행동 패널티로 남는다. 한 번의 실수가 연쇄로 이어지게
- **회복** (12단계, 수치는 시나리오 `recovery`, *임시*)
  - 치료: 장면에 있는 치료사(NPC `healer`)에게 받거나(`take_action.treatment`, 하루 한 번, 부상·감염 1단계), 소모품을 쓴다(`take_action.use_item`, 4.5). 낫는 정도는 코드가 정한다
  - 저절로: 새 부상 없이 이틀이 지나면 한 단계. 중상까지만 저절로 낫고, 치명상은 치료가 필요하다
  - 플레이 테스트 1회차 문제 4("치료받았는데 그대로")와, 회복이 없어 랜덤 자동 플레이에서 70일에 20~30번 죽던 문제를 고쳤다
- 감염은 별도 트랙 (4.5)

### 4.5 몸 상태: 허기와 감염 (12-1). 추위와 질병은 4.2 (12-4)

상태 트랙이 셋이 됐다: 부상, 허기, 감염. 이름·단계·보정은 시나리오 팩, 규칙은 core(`engine/body.ts`). **사망은 여전히 부상 트랙으로만 일어난다** (원칙 3). 허기·감염은 마지막 단계에서 하루마다 부상을 준다

- **허기** (든든함 → 허기짐 → 굶주림 -1 → 기진함 -2): 하루가 지날 때 소속 무리의 배급 수준만큼 바뀐다 (`war.ration.levels[].hunger`, `hunger_max`)
  - 정량: 2단계 나아진다 / 줄어든 배급: 허기짐까지만 / 반쪽 배급: 굶주림까지만 / 배급 끊김: 끝까지. 기진함이면 하루마다 굶주림으로 부상 1단계
  - 전쟁·계절이 무리의 식량을 바꾸고, 그게 배급을 거쳐 캐릭터의 몸에 닿는다 (9.3 "배급")
  - 통조림(`use_item`)으로 2단계 나아진다
- **감염** (없음 → 잠복 → 발열 -1 → 악화 -2): 
  - GM이 위험을 선언할 때 감염체에게서 오는 위험이면 `check.infected_source: true`. 그 판정으로 다치면 코드가 확률(가벼운 위험 30%, 심각한 위험 60%)로 잠복기를 만든다
  - **잠복기는 숨은 단계**(`hidden`)다. 캐릭터도 GM도 모른다. 상태·명령어·화면에는 "없음"으로 보인다
  - 하루마다 한 단계씩 나빠진다. 발열이 되는 날 GM에게 "감염: 없음 → 발열"로 알린다. 악화면 하루마다 부상 1단계
  - 항생제(`use_item`)로 2단계, 치료사로 1단계 나아진다
- **소모품** (`consumables`): 아이템 → 트랙 → 나아지는 단계. 구급상자 부상 1, 항생제 부상 1·감염 2, 통조림 허기 2. 나아질 데가 없으면 쓰지 않는다
- 하루가 지나며 바뀐 몸 상태는 `take_action` 결과 문구로 GM에게 알린다
- 이전 세이브: 새 트랙이 없는 캐릭터는 그 트랙의 첫 단계로 읽는다
- 대규모 전투는 개인 판정과 별도 규칙(병력·사기 중심)으로 처리

### 4.6 트레잇 (12-10)

림월드·프로젝트 좀보이드처럼 캐릭터마다 몇 개의 **트레잇**(타고난 기질·버릇·체질)이 있다. 능력·스킬이 "얼마나 잘하나"라면 트레잇은 "어떤 사람인가"다. 플레이어와 NPC가 같은 트레잇을 쓴다 (원칙 6)

**세 종류**

- **긍정** (비용 1~2): 이득이 있는 기질·체질
- **부정** (보상 1~2): 손해가 있는 기질·체질. 골라서 포인트를 얻는다
- **성격** (0): 수치 효과가 거의 없고 연기에 쓰는 기질. NPC의 `temperament`(warm, guarded …)를 이것으로 옮긴다

**캐릭터 생성** (웹 생성 화면, MCP는 GM이 묻는다)

- 긍정·부정은 **트레잇 포인트**로: 고른 긍정 비용의 합 ≤ 고른 부정 보상의 합 (부정을 골라야 긍정을 고를 수 있다). 긍정·부정 각각 최대 3개
- 성격은 공짜로 최대 2개
- 서로 반대인 트레잇은 함께 고를 수 없다 (예: 추위에 강함 ↔ 추위를 탐)
- 능력 포인트(4)와는 따로 센다
- "무작위"는 규칙에 맞게 고른다. 고르지 않으면 트레잇 없이 시작한다 (MCP의 "알아서"는 무작위)

**효과** (core는 효과 종류만 안다. 어떤 트레잇이 무엇을 하는지는 시나리오 팩 `traits` 데이터)

| 효과 종류 | 뜻 | 쓰는 곳 |
|---|---|---|
| `skill` | 스킬 보정 ±1 (능력 + 스킬 상한 안에서) | 판정 |
| `xp` | 경험치 배수 | 4.2 성장 |
| `body` | 허기·추위 노출·질병 확률·감염 확률 배수, 저절로 낫는 날 ± | 4.5, 4.2 몸 상태 |
| `noticed` | 내가 한 일이 숨은 목격자에게 들킬 확률 배수 | 8.2 목격자 |
| `alertness` | 내가 남의 일을 목격할 확률 배수 (NPC) | 8.2 목격자 |
| `rumor` | 내가 소문을 옮길 확률 배수 (NPC) | 8.3 소문 |
| `first_impression` | 처음 만난 인물의 호감 ± | 4.2 매력과 같은 자리 |
| `looks` | 외모 등급 (+2 아름다움, +1 호감형, -1 험악함). 처음 만난 인물의 호감에 더한다. 상대가 `attraction`이면 아래 "외모와 끌림"대로 커지거나 질투가 된다 | 첫인상, 관계 변화 |
| `attraction` | 이성에게 끌린다: 이성을 향한 호감이 오를 때 +1, 이성이 나를 설득·속일 때 그 판정 +1 (성별은 4.2 캐릭터 생성의 `gender`) | 관계 변화, 판정 (`take_action.target`) |
| 연기 지침 | 수치 없이 GM에게 주는 한 줄 (말투·반응) | GM 상태 |

|---|---|---|---|
| 보통 | + 외모 등급 | — | — |
| 이성편력, A와 성별이 다르다 | + 외모 등급 × 2 | A를 향한 호감이 오를 때 +1 (외모가 +면) | A가 B를 설득·속일 때 +1, 아름다운 외모면 +2 |

- 매력(능력)의 첫인상 보정과 더해진다. 첫인상은 관계 범위(-5~+5) 안으로 자른다
- 외모가 -(험악한 인상)이면 이성편력이어도 끌림·질투가 없고 첫인상만 깎인다
- GM에게는 상대의 외모 트레잇과 이성편력이 함께 보이므로, 끌림·질투를 말투와 태도로 연기한다 (질투하는 동성은 비꼬거나 경쟁하려 든다)
- 플레이어가 이성편력이면 거꾸로도 적용된다: 아름다운 이성 NPC의 설득에 약해지는 것은 판정이 아니라 GM 서술로 (플레이어 행동은 플레이어가 정한다, 원칙 5)
- 이성편력은 끌림까지만 다룬다. 연애 관계·장면은 2차 범위(15.2)다. NPC가 가지면 플레이어가 그 NPC를 설득할 때 유리해지고(성별이 다르면), 플레이어가 가지면 GM이 이성 NPC 앞에서의 허세·흔들림을 서술하고 이성 NPC를 향한 호감이 빨리 오른다

**NPC 연기**

- NPC 16명의 `temperament`를 트레잇(성격 + 필요하면 긍정·부정)으로 옮긴다. 예: 강태호 = 원칙주의·신중함·강심장, 오지호 = 수다쟁이·열성적·겁쟁이
- GM 상태의 인물 줄에 트레잇 이름과 연기 지침이 나온다 (지금은 영어 단어 `warm, guarded`). 플레이어 캐릭터의 트레잇도 GM 상태에 나와 서술에 반영된다 (겁쟁이면 망설이는 묘사)
- 트레잇은 겉으로 드러나는 것과 아닌 것이 있다: 처음 만난 인물의 트레잇은 겉으로 보이는 것(`visible`)만 플레이어에게 보인다 (`?인물`, 시트). GM은 연기를 위해 다 안다 (NPC 프로필은 원래 GM이 아는 정보다)

**구현** (12-10)

- 시나리오: `traits` 목록(id, 이름, 종류, 비용, 설명, 연기 지침 `acting`, 겉으로 보이는지 `visible`, 반대 `opposites`, 고를 수 있는지, 효과). `creation.traits`에 종류별 최대 개수. post_apoc은 긍정 12·부정 10·성격 24개
- core: 효과는 `engine/traits.ts`가 읽는다. 판정(스킬 보정은 상한 안, 끌림은 `check_rolled.modifiers.trait`로 따로), 성장(경험치 배수), 몸(허기·추위·질병·감염·저절로 낫기), 목격(들킬 확률·주의력), 소문(옮길 확률. 예전 `talkative` 하드코딩을 대신한다), 첫인상(매력 + 외모·끌림·질투), 호감 변화(끌림 +1, 질투 -1)
- 생성: `checkTraits`(겹침·반대·최대·포인트), `randomTraits`. 웹 생성 화면에 종류별 칩(못 고르는 것은 꺼짐), MCP는 생성 안내에 목록과 규칙. `character.traits`가 null이면 무작위
- NPC 16명의 `temperament`를 트레잇으로 옮기고 체질·외모·이성편력을 더했다 (예: 마경수 = 잔혹함·인내심·아름다운 외모·이성편력, 탁봉수 = 넉살·계산적·이성편력·말재간)
- 보이는 곳: GM 상태(플레이어 트레잇과 NPC 트레잇의 연기 지침, 끌림·질투 줄), `?상태`, `?인물`(만나 본 인물의 보이는 트레잇만), 웹 시트(트레잇 칩), 판정 카드(트레잇 보정)
- 이전 세이브: 캐릭터 `traits`는 빈 목록으로 읽고, NPC는 콘텐츠의 트레잇을 쓴다. `SAVE_SCHEMA_VERSION` 5

**처음 정한 영향 범위**

- 시나리오: `traits` 목록(id, 이름, 종류, 비용, 효과, 반대, 연기 지침, 겉으로 보이는지). `creation`에 트레잇 규칙(최대 개수)
- 캐릭터: `traits: string[]` (이전 세이브는 빈 목록, NPC는 콘텐츠에서). `SAVE_SCHEMA_VERSION` 5
- 콘텐츠: NPC 16명 `temperament` → `traits`, 역할은 시작 트레잇 없음
- 생성 화면·MCP 생성 안내에 트레잇 고르기, 시트·`?상태`·슬롯에 트레잇
- 효과가 들어가는 곳: 판정(스킬 보정), 성장, 몸 상태(허기·추위·질병·감염·회복), 목격자, 소문, 첫인상

### 4.7 수색과 찾을 거리 (12-17)

폐허·창고를 뒤지면(`take_action`의 `activity: search`) 코드가 그 구역의 찾을 거리 표(`locations/*.yaml`의 `loot: { chance, items: [{ item, weight, qty }] }`)에서 굴린다. core `engine/scavenge.ts`.

- 판정 결과만큼 굴린다: 성공 2번, 대가 있는 성공 1번, 실패 0번. 판정 없이 뒤지면 1번을 절반 확률로
- 같은 날 같은 구역을 다시 뒤질수록 덜 나온다 (한 번마다 절반, 상태의 `zoneSearches`)
- 찾은 것은 바로 소지품에 들어온다. GM은 결과에 나온 것만 서술한다 (원칙 2)
- 무소속(12.5)은 배급이 없어 지닌 것과 수색으로 먹고 산다. 표는 *임시* 값이다: 버려진 곳(구시가·강변·병원·물류창고)이 많이 나오고, 거점은 적게 나온다




### 4.8 물건: 무기·탄약·방어구·도구·무게·수리·제작·흥정 (12-38)

물건은 이름과 설명만 있던 것에서, 판정과 몸과 경제에 닿는 것이 된다. 수치는 아이템·시나리오 데이터에 있고 규칙은 core(`engine/gear.ts`)에 있다. GM은 무엇을 쓰는지 고를 뿐, 효과는 코드가 정한다 (원칙 2)

**아이템의 성질** (`items/*.yaml`, 모두 선택)
- `weight`(kg, 없으면 0.5), `value`(흥정 값, 없으면 1), `kind`(무기·방어구·도구·탄약·재료·소모품·음식·기타)
- `weapon { moves, max_harm, noise, ammo?, bonus? }`: 공격에 쓰는 스킬, 입힐 수 있는 피해 상한(light/heavy), 소음(0 조용함 ~ 2 총소리), 쏠 때 하나씩 쓰는 탄약 아이템, 판정 보정
- `armor { slot: body|head, reduces, penalty?, blocks_infection? }`: 받는 피해를 줄이는 단계, 입으면 불리해지는 스킬, 물림·긁힘에서 감염을 막을 확률
- `tool { bonus }`: 지니고 있으면 그 스킬에 보정 (가장 큰 것 하나, 능력+스킬 상한 안)
- `durability`, `breaks_into`: 몇 번 버티는지, 망가지면 남는 것 (부러진 소총 → 고철)
- `repair { move, materials, tools? }`: 고치는 스킬과 재료

**장비** (캐릭터의 `equipped { weapon, body, head }`, GM tool `equip`): 손에 든 무기 하나, 몸과 머리에 입은 방어구. 가진 것만 들고 입는다. 닳은 정도는 캐릭터의 `wear`(아이템별)

**공격** (take_action에서 target_harm을 선언하거나, 전투 중에 근접·사격 판정)
- 손에 든 무기의 스킬이어야 한다. 무기가 없으면 맨손(`gear.unarmed`: 근접, 가벼운 피해까지)
- 무거운 피해(heavy)는 상한이 heavy인 무기로만 노린다
- 탄약을 쓰는 무기는 탄약이 있어야 하고, 쏠 때마다 하나 준다
- 소음: 쏘면 그 구역의 오늘 소음이 오른다 (`noise_made`). 이야기 조건 `zone_noise_gte`로 총소리를 듣고 오는 것들이 열린다
- 무기로 공격하다 실패하면 닳는다 (`durability`만큼 닳으면 망가진다)

**방어**: 주인공이 피해를 받으면 입은 방어구의 `reduces`만큼 단계를 줄이고, 막은 방어구는 닳는다. 감염원에게 다칠 때 `blocks_infection` 확률로 감염을 막는다. 입은 방어구의 `penalty`(예: 은밀 -1)는 판정에 붙는다

**무게** (`gear.carry`): 들 수 있는 무게 = base + 근력 × per_strength. 넘으면 `encumbered_moves`(은밀·근접 등) 판정에 -1. hard_limit 배를 넘으면 옮겨 가지 못한다 (내려놓아야 움직인다). 넘게 받는 transfer_item은 막는다

**수리와 제작** (take_action의 `craft { recipe | repair }`, 판정 필요)
- 제작 법(`crafting.recipes`): 재료, 필요한 도구, 판정 스킬, 걸리는 시간, 나오는 것. 성공이면 다 나오고, 대가 있는 성공이면 절반(최소 1), 실패하면 재료 절반을 잃는다
- 수리: 성공이면 닳은 것이 없어지고, 대가 있는 성공이면 절반만, 실패하면 재료만 쓴다
- 차량정비·목공 같은 기술 스킬의 쓸모

**값과 흥정** (GM tool `barter`)
- 장면의 인물과 물건을 바꾼다. 받는 쪽 값 × (상인이면 `merchant.markup`) × 관계(신뢰가 높으면 깎아 준다)만큼 줘야 한다
- 넉넉하면 그냥 바꾸고, 조금 모자라면(`barter.haggle_floor` 이상) 교섭·거짓말 판정, 턱없이 모자라면 거절. 값과 판정은 코드가 한다
- 상인(NPC의 `merchant { restock, markup }`)은 날마다 모자란 만큼 다시 채운다

**무기고** (12-39, 플레이 피드백: 부엌칼만 들고 작전에 나갔다)

### 5.1 평시: 행동 비용만큼 흐른다

- 행동 종류별 기본 소요 시간을 코드 테이블로 정의 (대화 10분, 수색 1~2시간, 보초 4시간 등)
- AI는 행동을 분류만 하고(`take_action`의 `activity`), 시간은 코드가 더한다
- 시간이 흐르면 NPC 일과, 시설 운영, 월드 클락이 함께 진행된다
- 게임 시간은 1일차 00:00부터 흐른 분(정수). 시작은 1일차 05:30
- 시간대: 새벽 04시 / 아침 06시 / 낮 10시 / 저녁 17시 / 밤 20시부터

| 활동 | 시간 (*임시*) | 방식 |
|---|---|---|
| 잠깐의 행동 `brief` | 5분 | 고정. GM이 시간을 쓰지 않은 턴에도 자동으로 흐른다 |
| 대화 `talk` | 10분 | 고정 |
| 식사 `eat`, 응급처치 `treat` | 30분 | 고정 |
| 수색 `search` | 1~2시간 | 15분 단위로 굴림 |
| 휴식 `rest` | 1시간 | 고정 |
| 작업 `work` | 2시간 | 고정 |
| 보초 `guard_duty` | 4시간 | 빨리감기 |
| 잠 `sleep` | 6시간 또는 지정한 시간대까지 | 빨리감기 |
| 기다림 `wait` | 1시간 또는 지정한 시간대까지 | 빨리감기 |

### 5.2 빨리감기: 끼어들기 조건이 핵심

장거리 이동이나 전쟁 같은 큰 사건은 빨리감기로 넘긴다. 빨리감기는 "건너뛰기"가 아니라 **시뮬레이션을 빠르게 돌리다가 의미 있는 일이 생기면 멈추는 것**이다.

```ts
function fastForward(state, until: StopCondition) {
  while (!until(state)) {
    state = simulateTick(state);              // 1시간 또는 1일 단위
    const interrupt = checkInterrupts(state);
    if (interrupt) return { state, interrupt }; // 장면 모드로 복귀
  }
  return { state, interrupt: null };
}
```

- 1시간 틱으로 돌리고, 한 번에 최대 하루까지 감는다
- 상태는 바꾸지 않고 결과(멈춘 시각, 끼어든 사건)만 계산한 뒤 `time_advanced` 이벤트 하나로 기록한다

멈추는 조건:

- (현재 구현) 이상 징후: 시간대별 시간당 확률(*임시*: 밤 8%, 새벽·저녁 5%, 아침·낮 3%)로 "무언가 있다"는 낌새만 정한다. 정체는 정하지 않고 GM이 플레이어의 반응을 기다린다. 장소·조우 테이블이 생기면 조우로 바꾼다
- 조우 (감염체, 다른 무리, 부상자)
- 월드 클락 임계값 도달
- 조건이 맞는 스토리렛 발동
- 플레이어 상태 위기 (식량 바닥, 부상 악화)
- 플레이어가 지정한 조건 ("도착하면", "적이 보이면")

### 5.3 역할별 빨리감기 단위

| 역할 | 단위 | 멈추는 지점 |
|---|---|---|
| 간부 | 일~주 | 전황 보고, 배신, 협상 제안 |
| 분대장 | 일 | 작전 회의, 보급 위기 |
| 하급 전투원 | 시간~일 | 교전 시작, 동료 부상, 탈영 제안 |
| 혼자·외부 무리 | 일 | 무리가 근처를 지나갈 때, 자원 고갈 |

빨리감기 결과 요약도 반드시 정보 필터(6장)를 거친다.

## 6. 정보 모델: World State와 Belief State

### 6.1 두 겹의 상태

- **World State**: 시뮬레이션이 쓰는 진짜 상태
- **Belief State**: 각 캐릭터가 알고 있다고 믿는 것. 출처, 시점, 정확도가 함께 기록된다

```ts
type Belief = {
  id: string;
  fact: string;                         // "적군 약 30명이 북쪽 고가도로에 있다"
  source: "seen" | "report" | "rumor";
  learnedAt: GameTime;
  accuracy: "exact" | "approximate" | "false" | "unknown";  // unknown: GM이 장면에서 기록해 시스템이 진위를 모름
};
```

- 시작 지식은 역할의 `beliefs_preset`(content/beliefs/)에서, NPC의 시작 지식은 프로필의 `knows`에서 온다
- 장면에서 새로 알게 된 것은 GM이 `add_belief(fact, source)`로 기록한다 (지금은 플레이어만)

### 6.2 원칙

- AI 프롬프트에는 **현재 캐릭터의 Belief State만** 들어간다
- 소문은 틀릴 수 있고, 정보는 오래돼서 이미 상황이 바뀌었을 수 있다
- 같은 사건이 역할에 따라 다른 정확도와 시차로 전달된다
  - 하급 전투원: "어제 동쪽에서 총성이 계속 들렸다"
  - 간부: "동쪽 초소가 C의 습격으로 함락됐다는 보고가 들어왔다"
- 캐릭터 교체 시 새 캐릭터의 Belief State로 완전히 전환된다

**정보 필터 (구현)**: GM 프롬프트의 상태 블록은 아래만 담는다. 비밀이 새지 않는지는 실제 콘텐츠 전체로 테스트한다

| 들어가는 것 | 들어가지 않는 것 |
|---|---|
| 플레이어의 Belief (출처 표시, 최근 30개) | Belief의 진짜 정확도 (UI에도 보내지 않는다) |
| 장면에 있는 NPC의 연기용 프로필 (외모, 말투, 화법, 욕망·두려움·성격·가치관·행동 규칙, 그 NPC가 아는 것) | NPC의 비밀(`secret`), 모르는 것(`doesnt_know` = 세계의 진실) |
| 장면에 없지만 아는 인물의 공개 정보 (외모, 평판) | 모르는 인물 |

### 6.3 인물을 아는 것: 만남과 이름 (13-1)

누가 누구를 아는지도 Belief의 일부다. 예전에는 "아는 인물" 목록 하나(`known`)뿐이라 장면에 들어오면 바로 이름까지 알았고, 엑스트라만 `learn_name` 전까지 이름이 없었다. 모든 인물에 같은 규칙을 쓴다

- **이름은 처음부터 있다.** 콘텐츠 NPC는 프로필의 이름, 엑스트라는 `spawn_extra` 때 이름 생성 함수로 정한다. 인물의 정체(id·이름)는 바뀌지 않고, 바뀌는 것은 "누가 그 이름을 아는가"뿐이다
- **두 단계로 안다** (방향이 있다: A가 B를 아는 것과 B가 A를 아는 것은 따로)
  - `met`: 얼굴을 안다. 같은 장면에 있었거나 행적을 직접 봤다. 겉모습·호칭으로 알아본다
  - `named`: 이름까지 안다
- **알게 되는 길**
  - 같은 무리 동료는 처음부터 서로 이름을 안다 (역할의 `known_npcs`, 계승 때 같은 무리 사람들)
  - 다른 무리·모르는 사람은 장면에 들어오면 `met`까지만. 이름은 상대가 밝히거나(묻고 답함), 장면의 누가 그 이름을 부르거나, 사이가 가까워지면(호감·신뢰 2 이상, *임시*) 안다
  - GM은 `learn_name(인물)`로 알린다 (엑스트라 전용이던 것을 모든 인물로 넓힌다). 이름을 지어내지 않는다. 코드가 그 캐릭터의 `named`에 넣고 Belief를 남긴다: "엽총 든 보초의 이름은 김철수"
  - 처음 엮일 때(`spawn_extra`, 낯선 인물의 `npc_presence`)는 "엽총 든 보초 — 이름은 모른다"(겉모습 포함)를 Belief로 남긴다. 나중에 이름을 알아도 지우지 않는다 (Belief는 시각이 붙은 기록이다). 이 두 Belief가 호칭과 이름을 잇는다
  - NPC가 주인공의 이름을 아는지도 같은 방식이다. 같은 무리면 안다. 다른 무리는 주인공이 밝히거나 장면에서 불리면 안다
- **보는 사람 기준으로 부른다**
  - GM 상태의 인물 카드·목록: 이름을 알면 `김철수 (엽총 든 보초)`, 모르면 호칭·겉모습 (`엽총 든 보초 (이름 모름)`)
  - NPC 카드에 "이 인물은 당신의 이름을 안다/모른다"를 넣어 대사에 반영한다
  - 정보 명령어(`!인물`), 상태 화면의 관계 패널도 같은 기준이다
- **기억(memory)에서도 새지 않게**: 행적 청크는 목격자가 함께 보는 청크라, 행동한 사람을 "아는 방식"별로 나눈다 (11.4)
- **엮인 인물은 사라지지 않는다**: 엑스트라도 한 번 엮이면 데이터에서 지우지 않는다 (사흘 뒤 사라지기를 없앤다). GM 상태의 "이 구역에서 전에 엮인 인물" 목록만 최근에 엮인 몇 명으로 줄인다
- **계승**: 이어받는 캐릭터의 `met`·`named`를 그대로 쓴다. 이전 캐릭터가 알던 이름은 넘어가지 않는다
- **콘텐츠**: NPC 프로필에 `alias`(이름을 모르는 사람이 부르는 짧은 호칭, 예: "귀가 반쯤 없는 분대장"). 플레이어 캐릭터는 "소속 계급". 스토리렛 문장은 배역 자리(`{guard}`)로 쓰고 주인공이 부르는 말로 채운다 (다른 무리 인물의 이름을 문장에 박지 않는다)
- **구현**
  - 상태: `known[A]`(이름까지 안다), `met[A]`(만났다). 이벤트 `name_learned(characterId, targetId)`. 세계를 만들 때·계승할 때 역할의 `known_npcs`(같은 무리)와는 서로 이름을 안다
  - `npc_entered`·`extra_spawned`는 서로 `met`만 넣는다. 장면에 들이는 곳은 모두 `enterScene`(첫인상 + 처음 보는 이름 모르는 사람이면 "○○와 마주쳤다. 이름은 모른다. 겉모습: …" Belief)
  - `learn_name(target, who: player|target)`: player면 주인공이 상대 이름을 알고 "○○의 이름은 김철수" Belief, target이면 상대가 주인공 이름을 알고 그 NPC의 Belief에 남는다
  - 부르는 말: core `game/acquaintance.ts`(`knowsName`, `hasMet`, `aliasOf`, `nameAs`, `headingAs`). GM 상태의 인물 카드·목록, 판정·피해·치료 결과, 목격자, 물건 주고받기, 스토리렛 배역, `!인물`, 상태 화면이 모두 이것을 쓴다
  - GM 상태: 장면 인물 카드에 "당신은 이 인물의 이름을 모른다", "이 인물은 당신의 이름을 안다/모른다". 장면 밖은 "알고 있는 인물"(이름), "얼굴만 아는 인물"(호칭·겉모습, 평판 없음), "이 구역에서 전에 엮인 이름 모르는 인물"(엑스트라, 최근 5명, *임시*)
  - 엑스트라는 사라지지 않는다 (`extra_gone`, 사흘 규칙 삭제)
  - `SAVE_SCHEMA_VERSION` 7. `extra_named`·`extra_gone`이 없어져 이전 세이브(6 이하)는 읽지 않는다

## 7. NPC

### 7.1 정적 프로필 (콘텐츠 YAML)

- 정체성: 이름, 역할, 외모 한 줄
- **욕망과 두려움**: 행동 일관성에 가장 큰 영향
- **성격 태그·가치관**: 관계 계산, 소문 반응, 연애 궁합에 공통으로 사용
- **말투 + 예시 대사 2~3개**
- 일과, 반응 규칙("~하면 ~한다")
- 비밀과 공개 조건
- 아는 것 / 모르는 것
- (구현에서 추가) 나이, 평판(`reputation`: 그 인물을 아는 사람이 알고 있는 모습), 능력치와 시작 소지품 (플레이어와 같은 캐릭터 스키마로 만들기 위해)

### 7.2 동적 상태 (세이브)

- 플레이어(및 다른 NPC)와의 관계: **다축** (신뢰, 호감, 존중)
- Belief State, 함께 겪은 사건
- 생사, 위치, 부상, 소속, 등급
- (구현) 장면에 함께 있는 인물 목록. GM이 `npc_presence(npc_id, enter|leave)`로 알리고, 장면에 있는 인물과만 물건을 주고받는다. 만나면 서로 얼굴을 알고(`met`), 이름은 따로 안다 (6.3)
- 관계 수치는 8장. 비밀은 그 인물의 신뢰가 `secret.min_trust` 이상이면 GM에게 "털어놓을 수 있다"는 사실과 공개 상황만 알리고, 상황이 맞으면 `reveal_secret`으로 공개된다 (내용은 그때 처음 GM에게 전달)

### 7.3 예시

```yaml
# content/npcs/a_taeho.yaml
id: a_taeho
name: 강태호
faction: faction_a
rank: squad_leader
look: 왼쪽 귀가 반쯤 없는 40대. 늘 무전기를 만지작거림
want: 분대원을 한 명도 잃지 않는 것
fear: 자기 판단 실수로 또 사람이 죽는 것
values: { discipline: 3, loyalty: 2, mercy: -1 }
temperament: [cautious, blunt]
voice:
  style: 짧은 명령조. 부하에게 반말, 간부에게 존댓말
  samples:
    - "질문은 돌아와서 해."
    - "...총 내려. 아직 아니야."
routine: { day: 초소 순찰, night: 막사 }
rules:
  - 명령 불복종을 목격하면 신뢰가 크게 떨어진다
  - 부상당한 부하를 버리는 걸 절대 용납하지 않는다
knows: [동쪽 초소 경비 교대 시간, 지난달 실종된 정찰조]
doesnt_know: [정찰조가 C에 포로로 잡혀 있다는 것]
secret:
  content: 실종된 정찰조를 두고 혼자 후퇴했다
  reveal_when: 신뢰 4 이상 + 술자리
playable: true
```

### 7.3.1 구역의 인물 (12단계)

- NPC는 집 구역(`zone`)을 가진다. 플레이어가 그 구역에 있으면 GM 컨텍스트에 "이 구역에서 마주칠 수 있는 낯선 사람"으로 나온다. 모르는 인물은 이름 없이 겉모습과 id만 준다. 등장시키면(npc_presence) 얼굴을 알게 된다. 이름은 같은 무리가 아니면 `learn_name`으로 (6.3)
- 다른 구역으로 옮기면 장면의 인물은 따라오지 않는다. 동행이면 도착한 뒤 다시 등장시킨다
- 초안 인물 16명: A 8(분대 4, 의무, 보급 간부, 대표, 취사), B 2(대표, 오지호의 누나), C 2(탈영을 생각하는 정찰병, 수용소를 맡은 간부), D 2(의사 대표, 병원 수색꾼), E 2(상인 우두머리, 심부름꾼). 비밀은 스토리렛과 엮었다 (예: E 상인이 C에 초소 교대 시간을 팔았다, C 정찰병이 수용소의 A 정찰조를 안다)

### 7.4 운용 원칙

- 장면에 등장하는 NPC는 검색하지 않고 프로필을 통째로 주입한다
- NPC 하나당 200~400 토큰 정도로 짧게 유지한다
- 등급·나이·관계에 따른 **한국어 화법 규칙**(반말/존댓말)을 프롬프트에 주입하고, 관계가 변하면 말투도 바뀌게 한다
  - (구현) 기본 화법: 지휘 계통상 높은 쪽이 반말, 같은 높이면 나이가 많거나 같은 쪽이 반말. NPC의 `voice.style`이 우선한다. 관계에 따른 변화는 8장과 함께
- 초안 NPC 6명 (`content/npcs/`): 분대장 강태호, 분대원 오지호·민서연·박만수, 의무 담당 윤채원, 보급 간부 한도윤

### 7.5 엑스트라와 상대를 쓰러뜨리기 (12-12)

이름 없는 인물(지나가는 보초, 피난민, 짐꾼)도 주인공과 엮이면 엔진의 **캐릭터**가 된다. 지금은 서술로만 다뤄서, 보초를 쓰러뜨려도 그가 든 엽총을 주울 수 없었다

**엑스트라 틀** (시나리오 팩 `extras`, *임시*)

- 틀마다: 이름표(예: "붉은연합 보초 — 엽총"), 소속, 등급, 성별(무작위 가능), 능력·스킬 범위, 트레잇 후보, **소지품 표**(아이템별 확률), 겉모습 문구 후보
- 예: 붉은연합 보초(엽총), 붉은연합 보초(소총), 떠돌이 피난민, 나루상단 짐꾼, 버들마을 경비병
- 무엇을 들고 있는지는 **틀이 정한다.** GM은 틀을 고를 뿐, 물건을 지어내지 않는다 (원칙 2). 서술에 엽총을 이미 묘사했다면 엽총이 있는 틀을 고른다

**등장** (`spawn_extra`)

- 이름 없는 인물이 주인공과 엮일 때(말을 걸거나, 싸우거나, 거래하거나, 뒤지거나, 행적을 볼 때) GM이 `spawn_extra(틀, 호칭)`을 부른다. 지나가기만 하는 배경 인물은 계속 서술로만
- 코드가 틀로 캐릭터를 만든다: id `ex_N`, 호칭(GM이 붙인 "엽총 든 보초"), 능력·스킬·트레잇·소지품은 코드가 굴린다. 장면에 들어온다
- 그 뒤로는 일반 인물과 같다: 판정 대상, 목격자, 관계, 물건 주고받기, 부상·사망
- 수명: 장면을 떠나면 그 구역에 머문다. 한 번 엮이면 사라지지 않는다. GM 상태에는 그 구역에서 이름 모르는 인물 중 최근 5명(*임시*)만 나온다 (6.3)

**이름** (이름 생성 함수)

- 엑스트라는 `spawn_extra` 때 코드가 **이름 생성 함수**로 이름을 정한다. 주인공은 처음엔 모른다 (호칭만)
- 이름을 밝히거나 불리면 GM이 `learn_name(엑스트라)`를 부른다. 이름을 짓지 않고 "주인공이 알게 됐다"를 기록한다. 이름 있는 NPC와 같은 규칙 (6.3)
- 이름 재료(성, 이름 글자, 성별별)는 시나리오 팩 `names` 데이터. 같은 세계에 같은 이름이 겹치지 않게 한다. 이름 생성은 core의 순수 함수 (`(rng, 재료, 쓰인 이름) → 이름`)라 다른 곳(사망 뒤 새 신병의 이름 등)에서도 쓴다

**상대를 쓰러뜨리기** (엑스트라와 이름 있는 인물 모두)

- `take_action.check`에 `target_harm`(상대에게 주려는 피해: none/light/heavy)을 판정 전에 선언한다. 상대를 노린 공격이 성공하면 상대의 부상 트랙이 오른다 (성공: 선언한 만큼, 대가 있는 성공: 1단계, 실패: 없음 — 대신 주인공이 위험을 진다)
- 상대가 중상 이상이면 **무력화**(*임시*): 더 맞서지 못하고, 판정 없이 소지품을 뒤져 가져올 수 있다 (`transfer_item`). 치명상까지 가면 그대로 두면 죽을 수 있다
- 사망은 부상 트랙으로만 (원칙 3). 이름 있는 인물이 죽으면 세계에서 빠지고, 그 죽음은 행적(잔혹/용기 등)과 목격자로 이어진다
- 전투 장면(9-1)의 적은 지금처럼 병력 수로 다룬다. 이 규칙은 개인과 개인이 맞붙을 때

**구현** (12-12)

- 콘텐츠 `extras/`(틀 6개: 붉은연합 보초 엽총·소총, 붉은연합 약탈조원, 떠돌이 피난민, 나루상단 짐꾼, 버들마을 경비병), 시나리오 `names`(성 30, 남녀 이름 각 24), `combat.incapacitated_at: serious`. 새 아이템: 엽총, 쇠지렛대, 마른 비상식량
- core: `game/names.ts`(이름 생성, 순수 함수), `engine/extras.ts`(`spawn_extra`, `learn_name`, 가치관), 캐릭터 `extra` 필드, 이벤트 `extra_spawned` (13-1에서 `extra_named`·`extra_gone`과 사흘 규칙을 없애고 `name_learned`로 바꿨다, 6.3)
- `take_action.check.target_harm`: 성공 = 선언한 만큼(light 1, heavy 2), 대가 있는 성공 = 1, 실패 = 0. 무력화(중상 이상·사망)면 지닌 것을 알리고 `transfer_item`이 판정 없이 된다. 이름 있는 인물도 같은 규칙으로 다치고 죽는다
- GM 상태: 장면의 엑스트라 카드(호칭·겉모습·상태·지닌 것·트레잇·무력화), 이 구역에 머무는 엑스트라, 엑스트라 틀 목록. GM 지침에 엑스트라·이름·공격 규칙
- 아직 없는 것: NPC의 부상은 저절로 낫지 않는다 (치료·회복은 플레이어만). 다친 NPC를 돌보는 규칙은 나중에
- `SAVE_SCHEMA_VERSION` 6

**예: 엽총 보초**

1. 초소 뒤에서 마주친 보초와 엮인다 → GM이 `spawn_extra("c_sentry_shotgun", "엽총 든 보초")`
2. 플레이어가 덮친다 → `take_action` 근접전 판정, `target: ex_1`, `target_harm: heavy`, 실패 시 위험 `light`
3. 성공 → 보초 중상 → 무력화 → `transfer_item(ex_1 → player, 엽총)`
4. 그 장면을 다른 보초가 봤다면 숨은 목격자로 소문이 퍼진다

### 7.6 포로 (12-27)

- 캐릭터의 `captive: { by, zone }`: by 세력이 zone에 가둬 두었다. 장면·배역·목격자·소문·상관·계승 후보에서 빠지고, 갇힌 구역에서만 만날 수 있다 (`npc_presence`도 그 구역에서만)
- 붙잡혀 있다는 것은 그 자리에 있어야 안다 (원칙 4). 다른 곳에서는 아는 인물 목록에 "행방 모름"으로만 보인다
- 콘텐츠: NPC의 `start_captive`(처음부터 갇혀 있음), 배역의 `captive: true`(갇힌 사람을 배역으로, 갇힌 구역에서만), 효과 `npc_capture { who, by, zone? }`·`npc_release { who }`
- (12-55) **주인공도 붙잡힌다** (`scenario.captivity`): 진 전투에서 물러나지 않았으면 부상 단계별 확률(`on_defeat`)로, 항복(GM tool `surrender`)하면 반드시, 이야기 효과 `capture_player { by, zone? }`로. 죽음 대신 갇힌다 (코드가 굴린다, 원칙 3)
  - 갇히면: 무기·탄을 빼앗기고(`confiscate`, 풀려나면 돌려받는다), 붙잡은 무리의 거점에 갇히고, 동행은 그 자리에 남는다. 우리 무리의 배급을 못 받는다 (허기는 `hunger_floor`까지). 싸움에 끼지 않는다
  - 갇힌 동안은 태그 `captivity` 이야기만 열린다 (조건 `captors`, 배역 faction `captor`). 다른 이야기는 열리지 않는다
  - 탈출: 맞닿은 구역으로 옮겨 가는 행동에 `escape_moves` 판정 + 무거운 위험. 성공하면 빠져나오되 빼앗긴 것은 두고 온다. 실패하면 다치고 그대로 갇힌다
  - 풀려나기: 이야기 효과 `release_player { returned, home }`, 붙잡은 무리에 들면(`join_faction`) 풀려난다
- **포로를 잡는다**: GM tool `take_prisoner` (장면의 중상 이상인 사람을 묶는다, 동행 kind `prisoner`). 우리 무리의 거점에 닿으면 우리 무리의 포로가 된다
- **포로를 다룬다**: GM tool `handle_prisoner { target, action }` (우리 무리가 지금 구역에 가둔 포로, GM 상태에 목록)
  - interrogate 심문 (`interrogate_moves`, 그 사람의 믿음 중 주인공이 모르는 것을 코드가 고른다. 위협이면 잔혹 행적과 신뢰 하락)
  - recruit 회유 (`recruit_move`, 성공하면 우리 무리로), release 석방 (자비 행적, 그 무리의 태도 +1)
  - ransom 몸값·맞교환 (그 무리에 갇힌 우리 사람이 있으면 맞바꾸고, 없으면 `ransom` 자원을 받는다. 원수(-3)면 안 된다), labor 노역 (하루 `labor` 자원)
  - 포로는 붙잡은 무리의 `upkeep`을 날마다 먹는다. 처형하는 길은 없다
- **무리 사이 싸움의 포로**: 이긴 쪽이 진 쪽의 이름 있는 싸움꾼(하급·분대장) 하나를 `war_capture_chance`로 붙잡아 간다. 우리 무리 사람이면 주인공은 소식으로 안다 (어디 갇혔는지는 모른다)
- 이야기 `storylets/captivity.yaml` 26개: 갇힌 동안(붉은연합 규율반·노역·광장·완장, 청솔의 죽 한 그릇, 버들마을의 문밖 회의, 하얀매 격리실, 나루상단 장부·짐수레, 같은 방 사람, 밤 당번 간수와 걸지 않은 자물쇠, 바깥에 소식 보내기, 구출의 밤, 몸값), 우리가 가둔 포로(밤의 말, 찾아온 가족, 괴롭힘, 탈출하려는 밤, 노역 사고), 붙잡혀 간 우리 사람(창살 안의 얼굴 → 약속한 밤 → 돌아온 사람)
- (12-56) 조건 `captive_days_gte`(갇힌 지 며칠), 배역 `captive_anywhere`(어디 갇혔든 붙잡힌 사람, 이름만 부른다), 효과 `locate { who }`(붙잡힌 사람이 어디 갇혔는지 진짜 상태로 알려 준다), 효과 `wound { steps, cause }`(이야기가 주인공을 다치게 한다: 판정의 대가 있는 성공·실패에서만, 죽음 바로 앞에서 멈춘다, 콘텐츠 검증이 막는다). 이야기: 식당의 빈자리(우리 거점에서 붙잡혀 간 동료의 행방을 찾는다 → 적 거점의 창살 안의 얼굴), 벽에 그은 날짜(갇힌 지 나흘이 지나면). 세이브 형식 27
- 별칭 `captor`는 `overhear`와 조건 `dispositions`에도 쓴다. 조건 `own_people_captive`(우리 사람이 어딘가 붙잡혀 있다). 갇힌 주인공을 `send_to`로 옮기면 빠져나온 것이다
- 세이브 형식 26
- `post_apoc`: 실종된 청솔형제단 정찰조(오정빈, 남궁혁)가 붉은연합 물류창고 수용소에 갇혀 있다. 청솔·버들마을 쪽은 해 질 녘 배수구로 구출하고, 붉은연합 쪽은 몰래 열쇠로 풀어 줄 수 있다 (`storylets/world_captives.yaml`). 풀려나면 청솔형제단으로 돌아온다

### 7.7 NPC의 몸 (12-29)

- NPC도 플레이어와 같은 상태 트랙을 가진다. 감염된 인물은 하루에 한 단계씩 나빠지고, 마지막 단계면 부상을 입는다 (죽을 수 있다. 코드가 정한다). 장면에 있는 사람의 보이는 변화만 알린다
- 효과 `npc_body { who, track, delta, chance }`: 배역의 몸 상태 ±. chance면 코드가 굴린다 (긁혔는데 정말 감염됐나). 부상 트랙은 안 된다
- 배역 조건 `condition { track, at_least?, at_most? }`: 그 인물의 진짜 몸 상태로 배역을 고른다 (연출은 GM 전용, 플레이어에게 확정해 말하지 않는다)
- `post_apoc`: 하얀매 임소리의 손목 상처는 이야기가 열릴 때 절반 확률로 정말 감염이다. 감염이면 "새벽의 열", 아니면 "아물어 가는 손목"이 열린다. 항생제를 쥐여 주면 감염을 막는다
- 아직 질병·허기 같은 다른 트랙의 NPC 시뮬레이션은 없다 (감염만)

### 7.8 동행 (12-30)

- 상태의 `companions`: 주인공과 함께 다니는 인물·동물. 구역을 옮겨도 따라와 장면에 남는다. 죽거나 떠나거나 붙잡히면 빠진다
- 이야기 효과 `companion_join`·`companion_leave`로 함께 다니게 되고(함께 다니는 것은 이야기의 결과로만), GM tool `companion_part`로 떨어지거나 헤어진다 (7.9)
- 엑스트라 틀의 `animal`(사람 이름 대신 호칭이 이름), `companion_bonus`(함께 있으면 주인공의 스킬 보정, 능력+스킬 상한 안, 같은 스킬은 가장 큰 것 하나)
- GM 상태와 `?상태`에 동행이 보인다
- `post_apoc`: 떠돌이 누렁이(경계 +1). "따라오는 누렁이"에서 먹을 것을 주면 함께 다니고, "그르렁거리는 개"는 그 개로 열린다

### 7.9 함께 다니는 이유와 떨어짐 (12-32)

사람 사이의 동행은 대개 일시적이다. 목적을 이루면 헤어지기도 하고, 더 큰 목적이나 필요 때문에 계속 함께 가기도 한다. 동행마다 **함께 다니는 이유**(`bonds`)를 두고, 언제 끝나는지는 코드가 정한다

| 이유 | 생기는 곳 | 언제 끝나나 |
|---|---|---|
| 동물 `animal` | 동물 엑스트라 (누렁이) | 끝나지 않는다. 주인을 따라다닌다 |
| 임무 짝 `buddy` | 임무의 `buddy: true` (2인 1조). 임무를 받으면 같은 무리 동료 하나가 붙는다 | 임무가 끝나면 (보고·포기·기한 초과) 자기 자리로 돌아간다 |
| 분대 `squad` | 곁에 둔 분대원 (9.11 follow) | 다른 일을 맡기거나 헤어지면 |
| 목적 `purpose` | 이야기 `companion_join { kind: purpose, until }`. until: 플래그, 도착 구역, 시간 | 목적을 이루면 **갈림길** |
| 연고 `kin` | 역할의 `start_companions` (떠돌이의 가족), 갈림길에서 남기로 한 사람 | 관계가 크게 틀어질 때만 |

- **갈림길**: 목적 동행의 until이 차면 코드가 남을지 떠날지 기울기를 정한다 (그 사람의 신뢰+호감이 3 이상이면 남고 싶어 한다). GM tool `companion_crossroads { target, choice }`
  - `let_go`: 헤어진다
  - `ask_stay`: 남고 싶어 하면 연고가 된다. 떠나고 싶어 하면 교섭 판정: 성공 연고, 대가 있는 성공 이틀 더(목적 연장), 실패 떠난다
  - 12시간 안에 정하지 않으면 기울기대로 된다
- **잠시 떨어짐** (연고·동물·목적·분대): GM tool `companion_part { target, how }`
  - `wait`: 지금 구역에 남아 기다린다. 주인공이 그 구역에 다시 오면 저절로 합류한다
  - `errand { hours }`: 볼일을 보러 간다. 시간이 지나면 주인공을 찾아 돌아온다
  - `end`: 헤어진다 (함께 다니는 이유가 끝난다)
  - 이야기 효과 `companion_part { who, hours }`: 동생이 약을 구하러 간다 같은 이야기의 떨어짐
- 떨어져 있는 동안 그 사람은 장면·배역에 나오지 않는다 (기다리는 구역에서는 만날 수 있다). GM 상태에 "떨어져 있는 동행"으로 어디서 기다리는지, 언제 돌아오는지가 보인다
- 관계가 바닥이면 이유와 상관없이 떠난다 (동물은 예외): 연고는 신뢰 -3 이하, 그 밖은 신뢰 -2 이하
- 계승하면 함께 다니는 이유도 끝난다 (죽은 사람의 가족은 다음 캐릭터의 가족이 아니다)
- 자유 시나리오: 무소속이면 연고 하나를 고를 수 있다 (`custom_start.kin`: 엑스트라 틀 목록, 이름표). 역할의 `start_companions`로 들어가, 세계를 만들 때(그리고 새 캐릭터로 이어 갈 때) 틀로 만든다. 연고는 처음부터 서로 이름을 안다
- 이야기 배역 `companion { kinds, templates }`: 지금 곁에 있는 동행 중에서 (이름 없는 인물·동물 포함)
- 이야기 효과: `companion_join { who, kind, until { flag, zone, hours } }` (사람인데 until이 없으면 48시간), `companion_part { who, hours? }` (hours가 없으면 이 구역에서 기다린다)
- `post_apoc` 콘텐츠: 연고 틀 넷(어린 가족·늙은 가족·형제자매·오랜 짝, `extras/kin.yaml`)과 누렁이. 2인 1조 임무 9개(청솔 정찰·전선 정찰·보급 습격·동쪽 초소, 붉은연합 경계 재기·텃밭 습격·탈영병·감시탑, 버들마을 연합 정찰). 이야기 `storylets/world_companions.yaml`: 진료소까지만, 반씩 나누는 조건, 먼저 챙긴 손, 하루만 다녀올게, 나를 두고 가라, 언제 끝나?, 짝의 손
- 이전 세이브의 동행은 이유가 없다: 동물 틀이면 동물, 사람이면 연고로 본다
- 치트 `~storylet`도 실제 발동과 같은 길(이름 없는 배역 만들기 포함)로 이야기를 연다

### 7.10 인물 사이의 관계와 자라는 인물 (12-35)

이야기의 큰 줄기는 손으로 쓴 주요 인물이 맡고, 그 사이를 상황에 맞게 생긴 인물이 채운다. 사람들은 서로 얽혀 있다

**인물 사이의 관계** (`ties`)
- 종류: 부모·자식·형제자매·배우자(가족), 친구, 앙숙. 한쪽에만 적어도 양쪽으로 본다 (부모 ↔ 자식)
- 정해진 관계: NPC의 `ties: [{ to, kind, secret? }]`. 무리가 달라도 된다 (적대 무리에 있는 동생)
- 동적인 관계: 세계를 만들 때 `scenario.dynamic_ties { count, kinds }`만큼 코드가 이름 있는 인물들을 잇는다 (정해진 관계가 없는 사람끼리, 나이가 맞게). 판마다 다르다. 무리가 다르면 숨은 관계가 된다
- 자라는 인물(아래)도 틀의 `ties { chance, kinds }` 확률로 이름 있는 인물과 이어진다
- 아는 것 (원칙 4): 드러난 관계는 그 인물의 카드와 아는 인물 목록에 보인다. 숨은 관계는 그 인물의 신뢰가 `min_trust` 이상이 될 때 "털어놓을 수 있다"로만 GM에게 보이고, `reveal_tie`로 털어놓으면 주인공의 믿음이 된다
- 죽음: 이름 있는 인물이 죽으면 가족·친구는 그 소식을 듣는다 (믿음). 주인공이 죽였고 그 자리에 있었다면 신뢰·호감 -3
- 이야기 배역 `tie { of: <배역>, kinds }`: 그 배역과 이어진 사람 (적의 가족을 만나는 이야기)

**자라는 인물** (이름 없는 인물 → 이름 있는 인물)
- 엑스트라 틀의 `profile` 재료: 원하는 것·두려운 것·말투·행동 규칙·비밀·평판 후보. 자랄 때 코드가 하나씩 고른다 (AI가 비밀이나 사실을 지어내지 않게)
- 자라는 때: 그 인물과의 관계(신뢰·호감·존중 절댓값의 합)가 4 이상이 되거나, 연고·목적 동행이 되거나, GM이 `promote_extra`로 이야기에 붙잡을 때 (장면에 있고 주인공과 엮인 인물만)
- 자라면 이름 있는 인물처럼: 연기 카드(원하는 것·말투·규칙·비밀), 비밀 털어놓기(`reveal_secret`), 이야기 배역 후보, 같은 무리면 다음 캐릭터 후보
- 동물은 자라지 않는다

**상황에 맞는 등장**
- 엑스트라 틀의 `appears { zones, zone_owner, segments }`: GM 상태의 엑스트라 틀 목록에는 지금 여기서 마주칠 만한 틀만 나온다 (토큰도 준다). 조건이 없는 틀은 언제나. 연고 틀은 `zones: []`로 숨긴다 (이야기·시작으로만 생긴다)

**콘텐츠 (12-35)**
- `post_apoc`: 오지호 ↔ 붙잡힌 형 오정빈(숨은 관계, 신뢰 3), 붉은연합 권무열 ↔ 청솔 3분대 권예진 남매(적대 무리, 숨은 관계). 권무열의 수용소 이야기는 청솔 포로에게서 동생 소식을 들으려는 것으로 고쳤다. `dynamic_ties: 5`
- `islands`: 선단 노꾼 곽은비 ↔ 등대 망꾼 설다빈(선단이 턴 섬에서 함께 자란 친구, 숨은 관계), 진강호 ↔ 갑판장 한상철(앙숙). `dynamic_ties: 2`
- 엑스트라 틀마다 자랄 재료(붉은연합 사람·떠돌이·버들마을 사람·짐꾼·연고)와 등장 조건, 관계 확률
- 이야기: 저쪽에 있는 사람(적대 무리 가족에게 쪽지), 닮은 얼굴(적의 땅에서 동료와 닮은 사람). 이야기 효과 `reveal_tie { who, other }`, 배역 `tie.cross`(무리가 다른 상대만)
- 소식 장사꾼 이야기(반복)에 `cooldown_days` 3: 반복 이야기가 시나리오 이야기를 밀어내지 않게

### 7.11 무리 없는 인물과 떠도는 인물 (12-37)

- NPC의 `faction`을 비우면(null) 무리에 속하지 않은 이름 있는 인물이다 (떠돌이·외톨이·유랑상인). 계급은 `loner`, 세계에서는 무리가 빈 채로 산다. 무소속 주인공이 죽으면 그가 알던 무리 없는 인물로 이어 갈 수 있다
- NPC의 `roams`: 날마다 그 구역들 중 한 곳에 있다 (유랑상인). 날짜와 id로 정해지므로 상태·RNG를 쓰지 않고, 같은 날이면 늘 같은 곳이다 (`game/whereabouts.ts`). "이 구역에서 마주칠 수 있는 낯선 사람"과 아는 인물의 "가까이" 판정이 이것을 본다
- 콘텐츠 (12-37): 이름 있는 인물 57명 → 98명. 새 인물마다 기존 인물(다른 무리 포함)과 관계·비밀로 얽힌다
  - 청솔형제단 6 (`more_pine.yaml`): 분대원을 산 채로 두고 온 1분대장 허진만, 붉은연합 밀고자의 누나인 창고지기 차연희, 하얀매 대표의 어머니인 살림 간부 신옥란 등
  - 버들마을 5 (`more_willow.yaml`): 하얀매로 달아난 아들을 둔 관정 기사 남상구, 위원장 국혜란의 옛 동료 맹석규, 사자가 들어오던 밤을 옥상에서 본 소윤재 등
  - 붉은연합 6 (`more_red.yaml`): 조카 대신 남의 이름을 명단에 적은 규율반원 석중기, 딸과 부엌 아이를 배수로 밖으로 내보낸 취사반장 옥금자, 공세 날 투항을 꿈꾸는 벌조장 성태규 등

## 8. 평판과 소문

### 8.1 흐름

```
플레이어 행동
  → 행동에 태그 부여 (코드)
  → 목격자 판정 → 목격자의 Belief에 "직접 본 사실"로 기록
  → 시간이 지나며 소문으로 퍼짐
  → 들은 NPC마다 자기 가치관으로 판단해 관계 변화
```

```yaml
deed:
  id: deed_0042
  actor: player
  summary: C 소속 포로를 몰래 풀어 줌
  tags: [mercy, disobedience, enemy_sympathy]
  witnesses: [a_jiho]
  severity: 3
```

관계 변화량 = `행동 태그 × NPC 가치관 × 심각도 × 정보 신뢰도` (관계 축별로 계산, 코드)

**구현 (*임시* 수치)**

- 관계: NPC → 대상별 신뢰·호감·존중, 각 -5 ~ +5
- 태그 13종: 성실, 명령 불복종, 자비, 잔혹, 도둑질, 거짓말, 정직, 용기, 비겁, 동료를 위함, 배신, 제 몫 챙기기, 적에게 호의
- 태그마다 가치관 축(`dim`), 방향, 가치관과 무관한 기본 몫(`base`), 영향을 받는 관계 축이 있다. `sign × (가치관 + base) × 심각도`를 축별로 더하고, 정보 신뢰도(직접 봄 1, 전해 들음 0.6, 소문 0.3)를 곱해 3으로 나눠 반올림한다. 행동 하나로 한 축은 최대 ±3
- 같은 행동도 가치관에 따라 반대로 받아들인다 (자비: 강태호 호감 하락, 박만수 호감 상승)
- GM은 `take_action`의 `deed`로 분류만 한다. 행동 하나는 한 번만 기록한다
- 임무 완수는 상관이 직접 본 "성실", 임무 포기·기한 초과는 "명령 불복종"으로 자동 기록된다

### 8.2 목격자 판정

- **보이는 목격자**: 같은 장소·시간에 있는 NPC. 플레이어도 안다
- **숨은 목격자**: 코드가 확률로 판정. 플레이어 화면과 AI 프롬프트 어디에도 나오지 않는다
  - 장소 노출도 (거점 중앙 높음, 폐건물 지하 낮음)
  - 시간대 (낮 > 밤)
  - 소음 (총성, 비명)
  - 플레이어의 은밀 행동 판정

```ts
const exposure = location.exposure * timeFactor * noiseFactor;
const hiddenWitnesses = nearbyNpcs.filter(
  npc => rng() < exposure * npc.alertness - stealthBonus
);
```

- **위험 감지**로 눈치챌 기회를 준다
  - 성공: 누가 봤는지 안다
  - 대가 있는 성공: 누군가 본 것 같다 (누군지는 모름)
  - 실패: 모른다

**구현 (*임시* 수치)**

- 장소 시스템 전까지 노출도는 GM이 분류한다: 사람 많은 곳 0.6 / 한적한 곳 0.25 / 아무도 없을 곳 0.05
- 시간대: 아침·낮 1, 저녁 0.7, 새벽 0.6, 밤 0.4. 소음 ×1.8. 주의력 0.5 + 0.1×감각. 이번 턴 은밀 행동 성공 ×0.3, 대가 있는 성공 ×0.6
- 플레이어가 주변을 살피면 GM이 `look_for_witnesses(deed_id)`. 코드가 위험 감지 판정을 굴린다. 행적 하나에 한 번, 1시간 안에만
- **플레이어 화면의 관계는 그 인물과 마지막으로 같은 장면에 있었을 때 느낀 태도다.** 진짜 관계를 바로 보여 주면 숨은 목격자가 드러나기 때문이다
- 숨은 목격자가 장면에 들어오면 GM에게 "이 인물이 아는 당신의 행적"으로 전달된다. 바로 밝히지 않고 태도에 반영한다
- 이름 없는 엑스트라는 목격자로 기록되지 않는다 (즉석 NPC 생성과 함께 다룬다)

### 8.3 단둘이었을 때

- 소문은 나지 않지만 상대는 안다
- 비밀을 지킬지는 상대의 성격, 관계, 이익으로 결정된다
- 약점을 쥐었다고 판단하면 협박이나 거래의 재료가 된다

### 8.4 전파

- 출처가 멀수록 영향이 작다: 직접 목격 > 전해 들음 > 소문
- 모이는 장소와 시간대(식당, 보초 교대, 술자리)에서 퍼진다. 말 많은 NPC가 속도를 올린다
- (구현) 턴 시작에 날이 바뀌었으면 하루에 1단계씩 퍼진다 (최대 3일치). 아는 사람마다 모르는 사람에게 20% 확률로 옮기고, 말 많은(`talkative`) 사람은 두 배. 옮길 때마다 출처가 흐려진다 (직접 봄 → 전해 들음 → 소문), 소문은 더 퍼지지 않는다. 장소·모임 시간은 장소 시스템과 함께
- 2차: 전파 시 왜곡(과장), 세력 간 전파(포로, 교역, 첩자)
- 2차: 플레이어의 소문 관리(입막음, 반대 소문, 해명, 일부러 흘리기)

### 8.5 진급과 연결

하급 전투원에게 **평판이 곧 진급 조건**이다. 착하게 굴면 지휘관이, 냉정하게 굴면 동료가 등을 돌리는 딜레마가 시나리오 없이 저절로 생긴다.

### 8.6 임무와 진급 (구현)

- **배정**: 날이 바뀌면 코드가 역할의 임무 목록(`content/missions/`)에서 오늘의 후보 2개를 고른다. 상관(역할의 `commander`)이 장면에 있을 때 GM이 `assign_mission`으로 그중 하나를 배정한다. 기한은 템플릿이 정한다
- **수행**: 임무의 요구 조건은 활동 시간(`activity`, 누적 분)이나 판정 결과(`check`, 최소 결과)다. 임무를 받은 뒤 `take_action`에 `for_mission: true`로 넘긴 판정·활동만 코드가 집계한다
- 받은 임무는 그날 후보에서 빠진다 (하루에 같은 임무를 다시 받지 않는다)
- **보고**: 상관이 장면에 있을 때 `report_mission`. 결과는 코드가 판정한다 (모두 충족 = 완수, 일부 = 일부 완수, 없음 = 실패). 플레이어의 말로 결과가 바뀌지 않는다
- **불복종**: 플레이어가 임무를 거부·포기하면 `abandon_mission`, 기한이 지나면 턴 시작에 기한 초과로 끝난다. 둘 다 불복종 1회
- 공적 (*임시*): 완수 +3, 일부 완수 +1, 실패 0, 늦은 보고 -1, 포기·기한 초과 -2
- 진급 조건 (*임시*): 하급 전투원 → 분대장. 공적 9 이상, 복무 4일 이상, 불복종 1회 이하, 직속 상관의 신뢰 2 이상. 보고 시점에 조건을 채우면 진급한다
- 분대장이 된 뒤의 지휘 콘텐츠는 2차 범위(15.2)다

## 9. 세력과 전쟁

### 9.1 세력 스키마

```yaml
id: faction_c
population: 200
combatants: 80          # 전투 가능 인원 (보통 30~40%)
resources: { food: 0, water: 0, ammo: 0, medicine: 0, fuel: 0 }
territory: [node_ids]
morale: 0
cohesion: 0             # 내부 결속. 낮으면 이탈, 반란
leader: npc_id
disposition: { faction_a: -3, faction_d: 0 }
traits: [ruthless, opportunistic]
minor: false            # 외부 소규모 무리는 true
```

### 9.2 MVP의 전쟁: "보이지만 지휘하지 않는다"

- **세력 단위 전쟁은 코드가 추상 시뮬레이션**: 매일 습격, 소규모 교전, 영역 변화, 사상자, 자원 소모
- **플레이어는 개인 단위로 전쟁을 겪는다**: 정찰, 수색, 매복, 보초, 포로 이송, 협상 호위
- 적대 세력의 행동은 코드가 유효한 후보를 만들고 세력 성향 가중치로 선택 (결정적, 테스트 가능)
- 2차 이후: 대규모 전투, 외교(동맹, 휴전, 포로 교환). 분대 명령·지도부 회의·교역 방침은 12-31·12-33에서 넣었다 (9.11)

### 9.3 자원

- 5종: **식량, 물, 탄약, 의약품, 연료**
- 인원수에 따라 매일 자동 소모. 가만히 있어도 상황이 나빠진다
- 하급 전투원은 세력 창고가 아니라 **배급**을 받는다 (몰래 챙기는 것도 가능, 들키면 평판 하락)

### 9.4 구현 (9단계)

**콘텐츠** (수치는 모두 *임시*)

- `factions/*.yaml`: 이름, 공개 평판(`public`), 인구·전투원·자원 시작값, 사기·결속(-3~+3), 공격 성향(0~3), 다른 세력에 대한 태도(-3~+3, -2 이하면 적대), 세력 클락(`plans`)
- `locations/*.yaml`: 전선의 구역. `base`(거점)·`zone`, 시작 소유 세력, 인접 구역(한쪽에만 적어도 양쪽), 하루 산출. 장소 시스템이 생기면 장소의 상위 단위가 된다
  - 초안 9곳: A 거점, 동쪽 초소, 고가도로 너머 물류창고(C), C 거점, 강변 공장 지대(빈 땅), 구시가(빈 땅), B 거점, D의 진료소, E의 장터
  - 거점 산출은 텃밭·우물·채집·교역을 뭉뚱그린 값이다. 무리마다 소모보다 조금 모자라게 둬서 바깥 구역을 두고 다투게 한다
- `scenario.yaml`의 `war`: 1인당 하루 소모량, 생존 자원(식량·물), 교전당 탄약, 사상자당 의약품, 공격 확률, 배급 수준·사기·창고 사정을 부르는 말, 전황 소식 틀(조사 처리 포함)
- 자원 단위는 "사람-일" (식량 1 = 한 사람 하루치)

**하루 틱** (`core/sim/war.ts`, 결정적)

1. 생산: 소유 구역의 산출
2. 소모: 인원수만큼. 생존 자원이 모자라면 사기 -1, 인구 1% 사망, 사기가 -2 이하면 결속 -1
3. 세력 클락: 하루 한 칸. 다 차면 목표 구역을 총공격(병력 50%)하고 다시 시작한다
4. 교전: 공격 성향 × 확률로 하루 한 번. 내 구역과 맞닿은 적대 세력 구역에 습격(자원 약탈)·교전(사상자)·공격(구역 점령), 또는 빈 구역 차지. 전투력 = 내보낸 병력 × 사기 보정 × 탄약 보정(모자라면 0.6), 거점 방어 1.5배. 진 쪽 사상자는 내보낸 병력의 최대 20%, 이긴 쪽은 0~1명. 거점은 빼앗기지 않는다 (MVP)
5. 결속과 회복: 사기·결속이 모두 -2 이하면 이탈자. 굶지 않으면 사기가 시작값 쪽으로 돌아오고, 처음 비율까지 전투원을 다시 키우고, 식량이 넉넉하면 가끔 피란민이 합류한다 (끝없는 세계에서 세력이 사라지지 않게)

- 결과는 `war_day_simulated` 이벤트 하나(세력·구역·클락의 새 값과 교전 목록)로 남긴다. 시간이 흐른 뒤 날이 바뀌었으면 지난 날만큼(최대 7일) 돈다
- 세계를 열 때도 같은 처리를 한 번 맞춘다. 세력이 없던 이전 세이브는 이때 콘텐츠의 시작값으로 채운다 (`factions_initialized`)
- 밸런스 확인 (초안 수치, 시드 3개, 120일): A는 70명에서 40명 안팎으로 서서히 줄고, 동쪽 초소·강변·구시가가 오간다. C의 동쪽 공세는 열흘마다 온다

**플레이어가 겪는 방식 (정보 필터)**

- 자기 무리가 낀 교전은 보고(전해 들음)로 듣고 화면에 카드로 보인다. 다른 무리끼리의 일은 40% 확률로 소문이 된다. 믿음에 `topic: war`를 붙인다
- 사상자는 "한두 명 / 몇 명 / 여럿"으로만 전한다
- 다른 무리의 진짜 인원·자원·클락은 어디에도 나오지 않는다. 규모는 누구나 아는 시작 규모(약 N명)로만 말한다
- 자기 무리는 분위기(사기)·배급 수준(식량이 며칠 치인지)·창고 사정(대략)만 안다
- GM 컨텍스트에 "무리 사정"과 세력 관계를 넣고, 전황은 믿음으로만 알며 지어내지 않는다고 적는다
- `!세력`: 소속 무리 분위기·배급, 다른 무리의 공개 평판·관계·대략 규모, 최근 전황 5개. `!배급`: 오늘 배급, 창고 사정. 웹 캐릭터 시트에 "무리" 칸

**태도가 바뀌는 클락 (shift, 12-22)**

- 세력 사이 태도(`disposition`)는 세이브 상태에 있다 (시작값은 콘텐츠). 전쟁 시뮬레이션은 지금 태도로 적대(-2 이하)를 판단한다
- 세력 클락 `kind: shift`: 다 차면 공격 대신 정해 둔 태도로 바뀐다 (`shift: [{ from?, to, value }]`, `to: strongest` = 그때 전투원이 가장 많은 다른 무리). 한 번 일어나고 끝나며(찬 채로 남고 이야기로 되돌릴 수 없다), `news`가 소식으로 퍼진다 (그 무리나 대상 무리 사람은 전해 듣고, 아니면 소문)
- `post_apoc`: 버들마을 `b_waver`(연합에서 발 빼기, 30일: 청솔과 0, 붉은연합과 화해), 나루상단 `e_side`(이기는 쪽에 붙기, 35일), 하얀매 `d_lean`(가장 큰 무리에 약을 먼저 대기, 40일, 12-25). 이야기의 `clock` 효과가 당기고 늦춘다 (하얀매는 붉은연합의 독점 제안·도상필의 뒷거래가 당기고, 진료소 규칙을 지키면 늦춘다)

### 9.9 무리의 문화와 규율 (12-23)

무리마다 문화가 다르다: 어떤 무리는 군대처럼 규율이 빡빡하고, 어떤 무리는 이웃끼리 자율적이고, 어떤 무리는 계약만 있는 자유로운 무리다. core `game/culture.ts`.

- 규율 단계(수치)는 시나리오의 `discipline`, 무리마다 고르는 것은 `factions/*.yaml`의 `culture { discipline, summary, rules, address, punishment }`
- 규율이 정하는 것: 임무를 버리거나 기한을 넘겼을 때의 공적, 불복종으로 치는지, 진급에 허용되는 불복종 수, 불복종 행적의 무게(0이면 행적 없음, 목격자의 반응도 없다), 임무를 부르는 말

| 규율 | 버림/기한 초과 공적 | 불복종 | 진급 허용 불복종 | 행적 | 임무를 부르는 말 | `post_apoc` |
|---|---|---|---|---|---|---|
| 군율 strict | -3 / -3 | 센다 | 0 | 무겁게(3) | 명령 | 붉은연합 |
| 질서 orderly | -2 / -2 | 센다 | 1 | 2 | 명령 | 청솔형제단, 하얀매 |
| 느슨함 loose | -1 / -1 | 안 센다 | 3 | 가볍게(1) | 당번 | 버들마을 |
| 자유 free | 0 / -1 | 안 센다 | 제한 없음 | 없음 | 일감 | 나루상단 |

- GM은 상태의 복무 줄 아래에서 소속 무리의 문화(요약, 규칙, 호칭, 어기면)를 보고 NPC를 그 문화대로 연기한다. 그 무리 사람은 `?세력`에서 규칙을 본다
- 무소속이거나 문화가 없는 무리는 질서(지금까지의 규칙)
- 역할의 권한 `access` (12-26): `ration`이 있어야 무리의 배급을 받고, `mission_board`가 있어야 상관이 그날의 임무를 내놓는다. 비어 있으면 둘 다 있는 것으로 본다. 나머지(예: 하얀매 수습의 `treatment_room`)는 GM이 보는 특권이고, 이름은 시나리오의 `access_labels`

### 9.10 빚 (12-28)

- 캐릭터의 `debts`(세력 id → 양): 주인공이 그 무리 장부에 진 빚. 캐릭터의 것이라 계승하면 새로 시작한다. 0 아래로 가지 않는다
- 시작 빚은 역할의 `start_debt` (`post_apoc`: 나루상단 짐꾼이 상단에 12)
- 갚는 길: 임무의 `repays_debt`(완수하면 임무를 준 무리에 진 빚이 그만큼, 일부 완수는 절반), 이야기의 `debt { faction, delta }` 효과(빌리기 +, 물건·일로 갚기 -)
- 조건 `debt_gte`·`debt_lte`: 독촉, 빚쟁이 (`storylets/world_debt.yaml`: 장부에 다는 통조림, 장부꾼의 독촉, 빚 받으러 온 사내들)
- `?상태`와 GM 상태에 빚이 보인다. GM은 빚의 양을 지어내지 않고 일감·물건으로만 줄인다

### 9.11 지휘: 분대 명령과 지도부 회의 (12-31)

"보이지만 지휘하지 않는다"(9.2)에서 한 걸음 나간다. 분대장은 몇 사람을 움직이고, 간부는 무리의 방침을 바꾼다. 결과는 모두 코드가 계산한다 (원칙 2)

**분대 명령** (역할의 `squad`가 있을 때)
- 역할의 `squad`: 주인공 밑의 분대원 (NPC id). 같은 무리·같은 계급의 역할로 옮겨 오면(스카우트, 자유 시나리오) 그 역할의 분대를 이어받는다
- GM tool `squad_order { members, task, zone }`: 분대원에게 일을 맡긴다. 일은 시나리오 `command.squad_tasks`에서 온다 (`post_apoc`: 보초, 수색, 정찰, 호위, 쉬게 하기, 따라오게 하기)
  - `follow`: 동행(7.8)이 된다. 분대원이 곁에 있으면 `command.follow_bonus`의 판정 보정 (가장 큰 것 하나)
  - 그 밖의 일: 분대원이 그 구역으로 나가 정한 시간 동안 장면·배역에서 빠진다. 같은 사람에게는 한 번에 한 가지 일
- 따르는지는 코드가 정한다: 분대원이 주인공을 보는 존중이 -2 이하면 거절한다 (거절도 이벤트·행적이 된다). -1이면 늦게 나가 시간이 1.5배
- 결과는 시간이 다 되면 코드가 굴린다: 2d6 + 분대원의 능력 + 스킬(상한 +4) + 구역 위험(우리 땅 0, 빈 땅 -1, 적의 땅 -2) + 주인공의 지휘(전략) 스킬이 1 이상이면 +1
  - 성공: 일의 보상 전부 (무리 자원, 물건, 공적). 위험한 일을 해내면 존중 +1
  - 대가 있는 성공: 보상 절반
  - 실패: 보상 없음. 위험한 일이면 부상 한 단계 (부상 트랙 그대로라 이미 크게 다친 사람은 죽을 수 있다. 원칙 3), 주인공에 대한 신뢰 -1
  - 쉬게 하기: 호감 +1, 가벼운 부상 회복
- 주인공은 결과를 보고로 안다: 돌아온 분대원의 보고가 믿음(report)과 화면 표시로 남는다. 돌아오지 않은 사람은 "돌아오지 않았다"만 안다 (원칙 4: 어떻게 죽었는지는 모른다)
- GM 상태의 "분대" 섹션: 분대원마다 맡긴 일, 돌아올 시각, 마지막 보고

**지도부 회의** (계급이 `command.council_ranks`에 있을 때. `post_apoc`: 간부)
- 무리 방침: 시나리오 `command.policies`의 주제와 선택지 (`post_apoc`: 배급 — 줄이기·보통·늘리기, 태세 — 지키기·보통·밀어붙이기)
- GM tool `council_propose { topic, option, approach }`: 상관(지도부)이 장면에 있을 때, 주제마다 하루 한 번 안을 올린다. 판정 2d6 + 능력 + 스킬(approach: 교섭/전략) + 상관의 신뢰(+2 이상이면 +1, -2 이하면 -1)
  - 성공: 받아들여진다. 대가 있는 성공: 받아들여지지만 그 선택지에 반대하는 사람(`opposed_by`, 무리마다 섞어 적고 같은 무리 사람만 센다)의 신뢰 -1. 실패: 기각, 사흘 동안 같은 주제를 다시 올리지 못한다
- 세력 상태의 `policy`(주제 → 선택지)를 전쟁 틱이 읽는다: 소모 배수(`upkeep`), 공격 성향 배수(`aggression`), 방어 병력 배수(`defense`), 하루 사기 변화(`morale { delta, chance }`)
- 이야기 효과 `faction_policy { faction, topic, option }`로도 바뀐다 (지도부가 스스로 배급을 줄이는 날)
- 배급 방침은 개인 배급 단계에도 닿는다 (`ration_shift`: 줄이면 창고는 오래가고 각자 한 단계 덜 받는다)
- 무리 사람은 누구나 자기 무리의 방침을 안다 (GM 상태의 "복무·임무"). 다른 무리의 방침은 보이지 않는다
- 이야기 조건 `own_policy { 주제: [선택지] }`: 방침을 겪는 사람들의 이야기 (`storylets/world_command.yaml`: 반 국자, 김이 오르는 솥, 출정 배웅, 회의의 겨울 장부·칠판 위의 화살표, 분대의 먼저 손을 든 사람·맞지 않는 보고)
- 분대는 그 자리(역할의 계급)에 있는 사람만 지휘한다. 분대원이 죽은 분대장을 이어받아 플레이하면 분대가 없다. 계승·무리 옮기기에서 명령·보고·회의 기록은 비운다
- 랜덤 자동 플레이가 분대 명령·회의 안을 섞어 돈다 (시나리오 8개 × 시드 5개 오류 0건)
- 다른 무리의 분대: 붉은연합 약탈조장(`role_c_squad_leader`, 간부 마경수 밑 사조 넷). 군율의 무리라 앞줄에 설 사람, 규율반의 귀, 탈영을 떠보는 조원 같은 이야기가 붙는다
- **교역 방침** (세력 자원 관리): 방침 선택지의 `trade { partner, fallback_partner, give, get, min_disposition }`. 전쟁 틱이 하루마다 상대 무리와 창고의 자원을 바꾼다. 상대가 자기 자신이면 `fallback_partner`와 바꾼다 (12-43). 서로의 태도가 기준 아래거나 어느 쪽 창고가 모자라면 그날은 하지 않는다 (`post_apoc`: 식량→탄약·연료→식량은 나루상단(나루상단 자신은 붉은연합·버들마을과), 물→의약품은 하얀매)

### 9.12 여울섬: 닫힌 낙원 (12-36)

가람 사람들이 "파라다이스"라고 부르는 바다 건너 섬. 자급자족하고 무기와 탄약이 넘치며, 섬이라 감염체도 거의 오지 않는다. 바깥을 경계하고 아무나 들이지 않는다. 그리고 그늘이 있다

- **세력** `faction_y` (여울섬): 크고 부유하다. 먼저 치지 않고(공격 성향 0), 누구와도 맞닿아 있지 않아 전쟁 틱의 교전에 끼지 않는다. 다른 무리와는 경계(-1). 나루상단을 통해 탄약을 조금씩 흘려보낸다는 소문이 있다
- **시작할 수 없다**: 세력의 `startable: false`. 처음 시나리오 고르기와 직접 쓰기(자유 시나리오)에 없다. 스카우트·가입 이야기도 없다 (섬 안의 이야기로만 받아들여진다)
- **건너가는 길** (구역의 `crossing`): 섬은 어느 구역과도 맞닿아 있지 않다. 강변·정수장에서만 건너간다
  - 정해진 이야기: 밀항선 뱃삯, 나루상단 탄약 거래의 호위, 떠내려온 섬사람 구하기. 건너는 표(플래그)를 얻으면 위험 없이 건넌다
  - 직접 시도: 배를 구해 판정(`crossing.attempt.moves`)으로 건넌다. 위험은 무겁게(heavy) 선언해야 하고, 실패하면 다치고 물살에 밀려 되돌아온다. 대가 있는 성공이면 다쳐도 닿는다
  - 섬에서 나가는 길도 같다 (섬의 허락 또는 위험한 밤배)
- **해금 (모든 판)**: 한 번이라도 섬에 들어가면 `unlock_earned`가 남고, 세이브 폴더의 `unlocks.json`에 월드별로 기록된다. 그 뒤로는 어느 판에서든 새 게임의 시나리오 고르기에 섬사람 시나리오(역할의 `unlock`)가 열린다. 같은 판에서 죽은 뒤 다음 캐릭터로도 고를 수 있다 (`new:<역할>`)
- **그늘**: 겉으로는 낙원이다. 섬 의회의 상위 지도자들은 인육을 즐긴다. "쓸모없어 내보낸다"던 사람들은 섬을 떠나지 않았다. 비밀은 lore(`secret:y_feast_seen`)와 인물의 비밀·숨은 관계로만 드러나고, 섬사람 시나리오의 이야기 줄기가 그 진실에 닿는다
- **외딴곳** (구역의 `isolated`): 섬에서는 그곳을 `zones`로 직접 적은 공통 이야기와 엑스트라 틀만 나온다 (떠돌이·누렁이가 섬에 나타나지 않게). 섬에는 `y_villager`(여울섬 주민) 틀
- 이야기 효과 `send_to { zone }`: 주인공을 다른 구역으로 보낸다 (쫓겨남, 바다에 던져짐)
- **콘텐츠**
  - 인물 일곱: 의장 한수자(첫 겨울 인육을 처음 꺼낸 사람, 심사관과 숨은 부부), 심사관 백천수(내보낸다던 사람을 저장고로 데려간다), 창고지기 윤미옥(장부로 안다, 딸 해솔과 탈출을 준비), 윤해솔(의장이 예뻐한다), 해안 경비조장 진강호(밤배를 띄우지만 어디 닿는지 모른다), 설다빈(단짝이 내보내졌다), 추복만(국을 먹지 않는다, 치료사)
  - 섬사람 시나리오 `role_y_islander`(해금 `yeoul`): 임무 다섯, 시작 지식(일부는 섬이 들려준 거짓)
  - 도시에서 가는 길(`storylets/world_yeoul.yaml`): 바다 건너 낙원(소문), 밀항선 뱃삯, 섬 거래선(나루상단 호위), 떠내려온 사람, 입도 심사(받아들여짐·검역 막사·쫓겨남·거짓말)
  - 섬 안의 줄기(`storylets/y_islander.yaml`): 고기 국 → 보이지 않은 배 → 맞지 않는 장부 / 바위틈 → 의회 저장고(진실) → 겨울 잔치 초대, 밤배(윤미옥 모녀와 탈출), 의회가 부른다(의심받으면), 잔치의 손님(해솔)
  - lore: 여울섬의 소문(공개), 섬 안의 생활(`faction:faction_y`), 여울섬의 진실(`secret:y_feast_seen`)
- 자동 플레이: 섬사람은 사망이 다른 시나리오의 1/3쯤이다 (낙원은 낙원이다). 섬에서 공통 이야기 0

### 9.6 계절과 경제 (12-1)

- 계절 4개, 각 20일 (*임시*). 1일차는 늦가을(가을 14일째)이라 첫 겨울이 일주일 안에 온다. 시나리오 `seasons`에 계절별 소모·산출 배수
  - 겨울: 연료 소모 2배, 물 0.9배, 식량 산출 0.6배, 물 산출 0.8배 / 봄: 식량 0.9배 / 여름: 물 소모 1.15배, 식량 1.1배 / 가을: 식량 1.3배
- GM 컨텍스트("계절: 늦가을"), `!시간`, 웹 시트 시각에 계절. 스토리렛 조건 `seasons`
- **고생 자원** (`war.hardship`, 연료): 모자라면 사람이 죽지 않고 사기만 떨어진다. 처음에는 연료를 생존 자원으로 뒀다가 첫 겨울에 A가 70명에서 42명으로 줄어 바꿨다
- **일손**: 구역 산출은 무리의 인원(시작 대비 0.7 ~ 1.2배)에 따라 줄고 는다. 없으면 인원이 줄어도 생산이 그대로라 식량이 수백 일 치 쌓였다
- 거점 산출을 소모와 비슷하게 맞췄다 (A는 강변을 잃으면 물·연료가 상시 모자라 봄·여름에 사람이 죽던 문제)
- 밸런스 (시드 3개, 160일, 겨울 두 번): A는 70명에서 30~40명으로 서서히 준다(전쟁 손실). 겨울을 지나면 배급이 "줄어든 배급"으로 떨어졌다가 가을에 회복한다. 배급 일수의 30~60%가 줄어든 배급

### 9.8 날씨 (12-3)

- 하루에 한 번(날이 바뀐 뒤 첫 처리) 계절별 무게로 오늘 날씨를 고른다. 시나리오 `weather`: 날씨 종류(이름, 설명, 시야 배수)와 계절별 무게 (*임시*)
  - `post_apoc`: 맑음 1.0 / 흐림 0.9 / 비 0.6 / 안개 0.4 / 눈 1.1(발자국) / 한파 0.9. 겨울엔 눈·한파, 여름엔 비가 잦다
- 효과: **시야 배수가 숨은 목격자 확률에 곱해진다** (안개 낀 밤의 도둑질은 잘 안 들킨다). 나머지는 GM이 설명을 장면에 반영한다
- GM 컨텍스트(시각 줄), `!시간`, 웹 시트 시각에 날씨. 스토리렛 조건 `weather`

### 9.7 전선 되돌리기 (12-2)

C가 한 달 안에 분쟁 지대를 모두 차지하고 전선이 굳던 문제(17.1)에 대한 답. 플레이어가 우리 무리의 반격을 앞당기고, 그 반격 전투에 직접 나설 수 있다.

- **반격 클락**: 세력 계획(`plans`)에 `target_rule: frontier`. 다 차면 그때 맞닿은 적대 세력의 구역 중 **원래 우리 땅이던 곳 먼저**, 그다음 산출이 많은 곳을 친다 (빈 땅이면 차지, 거점은 고르지 않는다). A의 "반격 준비"(14일)
- **플레이어가 앞당기는 길**
  - 전선 임무(`missions[].advances`): 완수하면 클락 +N, 일부 완수는 절반. 전선 정찰 +2, C 보급 털기 +3
  - 정찰 이야기의 효과(`clock`): 고가도로 위 순찰조를 끝까지 지켜보면 +1, 투항자에게서 수용소 이야기를 들으면 +2
- **반격에 나서기**: 반격이 벌어지는 새벽에 목표와 맞닿은 우리 구역에 있으면 공격 쪽 전투 장면으로 차출된다 (9.5). 이기면 구역이 넘어온다
- **정보 필터**: 우리 무리의 계획은 대략으로만 들린다 ("말만 돈다 / 준비가 한창이라는 말 / 임박했다는 말", "목표는 OO이라는 말"). 임박하면 GM 컨텍스트가 "맞닿은 우리 구역에 있으면 함께 나설 수 있다"고 알린다. 다른 무리의 계획은 여전히 들리지 않는다
- 밸런스 (시드 3개, 120일): 화면 밖에서 A의 반격은 8번 중 2~4번 성공, 구역 주인이 9~12번 바뀐다 (전에는 한 달 뒤로 굳었다). 임무로 앞당기면 반격이 13번으로 늘지만 실패한 반격만큼 A의 사람도 준다. 플레이어가 전투 장면에서 판세를 바꾸는 것이 차이를 만든다
- 실제 확인 (MCP): A 거점에서 지내자 반격 소문이 "말만 돈다 → 준비가 한창 → 임박"으로 바뀌고, 11일차에 C가 동쪽 초소를 빼앗자 목표가 동쪽 초소로 바뀌었다. 15일차 새벽 "세력 A 쪽이 동쪽 초소를 친다. 당신도 차출됐다"로 공격 쪽 전투가 열렸다

### 9.5 전투 장면 (9-1): 교전 속의 한 사람

세력 틱의 교전은 보통 화면 밖에서 숫자로 끝난다. **플레이어가 그 자리에 있으면** 교전을 바로 결론 내지 않고 라운드 단위의 전투 장면으로 연다. 플레이어는 전투의 한 일원으로서 침투, 경보 차단, 측면·후방 공격, 폭약, 미리 깔아 둔 함정으로 판세를 바꾼다. 승패와 수치는 코드가 정하고, AI는 연출한다.

**구역과 이동 (장소 시스템의 최소 형태)**

- 캐릭터는 전선 구역 하나에 있다 (`playerZone`). 시작은 역할의 `start_location`, 없으면 소속 세력의 거점
- `take_action.move_to`: 인접 구역으로 이동한다 (이동 활동 30~60분). 코드가 인접과 전투 중 여부를 검사한다

**전투가 열리는 때**

- 하루 틱에서 정해진 교전 중 플레이어가 끼는 것은 바로 계산하지 않고 그날 새벽(04:00~05:30 사이)으로 **예정**한다
  - 방어: 공격받는 구역에 플레이어가 있다
  - 공격: 우리 무리가 공격하는 구역과 맞닿은 우리 구역에 플레이어가 있다 (차출)
- 예정 시각에 플레이어가 아직 그 자리에 있으면 전투 장면이 열린다. 자리를 떴으면 화면 밖에서 계산한다
- 빨리감기(잠·보초·기다림)는 예정된 교전 시각에 멈춘다 (끼어들기 `battle`). 자정을 넘기는 빨리감기는 자정에서 하루 틱을 돌린 뒤 이어 간다

**전투 상태 (코드)**

- 양쪽 병력, 전세(-5 ~ +5, 우리 편 기준), 경보(0 ~ 3), 플레이어 위치(전선 → 측면 → 적 후방), 라운드(10분, 최대 8), 남은 적 목표물, 양쪽 사상자
- 매 라운드: 플레이어 행동의 효과 → 배경 교전(남은 병력·사기·무너진 목표물로 전세 ±1, 진 쪽 사상자) → 끝났는지 검사. 플레이어의 한 수가 전세를 끝까지 밀면 배경 교전 없이 그 자리에서 끝난다 (결정타)
- 끝: 전세가 ±5에 이르거나, 라운드가 다 되거나(전세 부호로, 0이면 방어 쪽이 버팀), 플레이어가 빠지면(남은 라운드를 코드가 굴린다)
- 결과는 세력 상태에 그대로 들어간다 (사상자, 습격 약탈, 구역 점령, 사기)

**전투 중 플레이어 행동** (`take_action.battle`)

- 효과 종류·조건·크기는 시나리오 팩(`scenario.yaml`의 `battle`)에 데이터로 둔다. core는 위치·경보·전세·목표물·준비물이라는 틀만 안다 (중세 팩이라면 폭약 대신 기름 항아리)
- 효과마다: 쓸 수 있는 위치, 경보 상한, 필요한 아이템(소모 여부), 필요한 준비물(함정), **최소 몸의 위험**, 경보 0일 때의 기습 보너스, 판정 결과(성공·대가 있는 성공·실패)별 전세·경보·전진·적 사상자·목표물 파괴
- 초안: 버티며 싸우기(전선), 숨어들기(전진, 실패하면 경보), 경보 전에 해치우기(경보를 낮춤), 측면·후방 기습(경보 0이면 더 크게), 폭약(목표물 파괴, 폭약 소모), 함정 발동(미리 설치한 함정 소모), 물러나기
- 전투 효과는 반드시 판정을 함께 넣고, 몸의 위험은 효과의 최소 위험(`min_harm`) 이상으로 선언한다. 한 번의 행동이 한 라운드(10분)다. 잠·보초·기다림·이동은 할 수 없다
  - 처음에는 모든 전투 효과에 위험을 요구했는데, 실제로 돌려 보니 대가 있는 성공(7~9)마다 부상이 쌓여 세 라운드 만에 치명상이 됐다. 숨어들기·덫 발동은 대가가 경보·전세로 오는 행동이라 none, 근접 싸움은 light, 폭약은 heavy로 둔다
- 판정 없이 지나간 턴도 한 라운드가 흐른다 (배경 교전만)

**준비** (`take_action.prepare`)

- 전투 전에 우리 구역에 함정 같은 준비물을 설치한다. 필요한 아이템을 쓰고 판정이 성공·대가 있는 성공이면 그 구역에 남는다. 그 구역에서 열린 전투에서 함정 발동으로 쓴다

**결과와 보상**

- 전투가 끝나면 플레이어의 기여(효과로 바꾼 전세의 합)에 따라 공적을 받는다 (최대 3)
- 우리 무리가 낀 전투 결과는 보고로 남고, 공이 크면 "용기" 행적으로 기록되어 소문이 된다
- GM은 라운드마다 전세·경보·위치·쓸 수 있는 행동을 받아 연출한다. 승패·사상자·점령을 지어내지 않는다

**구현 메모**

- 상태: `playerZone`, `preparations`(구역별), `pendingClashes`, `battle`. 이벤트: `zone_moved`, `preparation_set`, `item_consumed`, `clash_resolved`, `battle_started`, `battle_round`, `battle_ended` (모두 기본값이 있어 이전 세이브와 호환된다)
- 규칙은 `core/sim/battle.ts`(라운드), 연결은 `core/engine/battleTools.ts`(예정·시작·라운드·끝·문구). 끝난 결과는 `applyBattleOutcome`으로 세력 상태에 넣는다 (사상자, 약탈, 점령, 사기, 탄약·의약품)
- 예정된 교전은 GM 컨텍스트·명령어·화면 어디에도 나오지 않는다. 전투가 열린 뒤에만 "전투 중" 블록이 생긴다
- 병력은 대략적인 말로만 ("열 명 남짓", "스무 명 안팎")
- 초안 콘텐츠: 위치 3(전선·측면·적 후방), 목표물 3(지휘하는 자·탄약 더미·기관총 자리), 준비물 1(철사 덫, 철사 뭉치 필요), 효과 7. 신병은 철사 뭉치를, 박만수는 사제 폭약을 갖고 시작한다
- `!지도`: 현재 구역, 맞닿은 구역과 주인, 설치해 둔 것. 웹 시트에 "있는 곳"과 전투 칸(전세 게이지·경보·위치)
- 실제 확인 (MCP, LLM 없이): 새 세계에서 동쪽 초소로 옮겨 덫을 깔고 기다리자 5일 뒤 새벽 C의 습격으로 전투가 열렸다. 덫 발동 → 숨어들기 ×2(측면 → 적 후방) → 소리 없이 해치우기(경보를 0으로) → 기습 ×2(두 번째에 발각) → 승리. 우리 쪽 사상자 1, 적 7, 공적 +2

**계급이 오르면 (2차)**

- 같은 전투 상태 위에서 분대장은 분대(동료 NPC)에게 명령하고, 간부는 라운드마다 병력 배치·전술을 바꾼다. 적도 코드의 전술 표로 대응한다

**아직 하지 않은 것 (9.4·9.5)**

- 배급이 캐릭터 몸 상태(허기)에 닿는 규칙 (상태 트랙이 필요하다), 플레이어 행동·임무가 전황에 주는 영향 (스토리렛 단계에서), 계절·겨울, 세력 간 교역·외교, 이름 있는 NPC의 전사

## 10. 시나리오 구조

### 10.1 3층 구조

1. **거시 흐름 (코드)**: 전쟁, 계절, 세력 클락. 역할과 무관하게 진행된다
2. **스토리렛 (콘텐츠 YAML)**: 조건이 맞을 때 발동하는 이야기 조각. 조건과 효과는 코드가 판정·실행
3. **구체적 장면 (AI)**: 스토리렛과 현재 상태를 바탕으로 장면, 대사, 소규모 사건을 즉석 생성

### 10.2 같은 사건, 다른 렌즈

"C의 대규모 습격 준비"라는 사건 하나가 역할마다 다르게 닿는다.

- 하급 전투원: 초소 증원 배치, 동료의 탈영 계획
- 간부: 연합에 지원 요청, D·E 설득
- 외부 무리: 피란민 행렬, 양쪽의 징발

### 10.3 스토리렛

```yaml
id: grunt_desertion_offer
tags: [grunt, squad_life]
trigger:
  world_clock: { c_offensive: ">= 3" }
  player: { rank: grunt }
  npc_present: { role: squadmate, relation.trust: ">= 2" }
setup: 보초 교대 중, 동료가 오늘 밤 같이 도망치자고 속삭인다.
choices:
  - id: join
    effects: [set_flag(deserted), faction_status(faction_a, deserter)]
  - id: refuse_silent
    effects: [add_belief(desertion_plan)]
  - id: report
    effects: [relation(squadmate, trust, -4), relation(squad_leader, trust, +2)]
ai_direction: 동료는 겁에 질려 있다. 가족이 B 쪽에 있다는 걸 흘린다.
repeatable: false
```

- **고정 스토리렛**: 특정 인물·사건에 묶인 이야기
- **템플릿 스토리렛**: "누가 / 어디서 / 무엇이 부족해서"를 세계 상태에서 채워 넣는 반복 가능한 조각. 끝없는 진행을 지탱한다
- 조건이 맞는 스토리렛이 없으면 AI가 소소한 장면을 생성한다

### 10.4 구현 (10단계)

**콘텐츠** (`storylets/*.yaml`, 초안 8개: 고정 4 + 템플릿 4)

- `when`: 계급, 시간대, 날짜, 플레이어가 있는 구역, 우리 땅인지, 플래그(있음·없음), 세력 클락(이상·이하), 우리 무리 사기, 식량 며칠 치, 부상 단계, 가진 아이템, 임무 중인지, 최근 전황 소식
- `cast`: 배역. 지정 인물(`ids`), 상관(`commander`), 소속, 계급, 아는 인물, 신뢰 하한으로 살아 있는 NPC 중 하나를 고른다. 한 사람이 두 배역을 맡지 않는다. 채울 수 없으면 열리지 않는다
- `setup`(상황), `ai_direction`(GM 전용 연출), 선택지. 문장의 `{배역}` `{zone}`(지금 구역) `{scarce}`(우리 무리에서 가장 모자란 자원)를 채우고 조사도 맞춘다
- 선택지: 효과 목록, 또는 판정(`check`)과 결과별 효과(`outcomes`)
- 효과 (코드가 적용): 플래그 세우기·지우기, 배역·상관의 관계, 알게 된 것(믿음), 공적, 아이템(배역에게서 받기 / 새로 얻기), 세력 클락 당기기·늦추기, 우리 무리 사기, 행적. 부상·사망은 효과로 만들 수 없다 (원칙 3)
- `repeatable` + `cooldown_days`이면 템플릿, 아니면 한 번만. `tags`는 역할의 `storylet_tags`와 겹쳐야 한다
- `pnpm content:check`가 배역·아이템·구역·클락·부상 단계·문장의 자리를 검사한다

**발동**

- 시간이 흐른 뒤 처리의 마지막에: 진행 중인 것이 있으면 기한(`storylet_pacing.expire_hours`, 3시간)이 지났는지 보고, 없으면 마지막 스토리렛 뒤 간격(`min_gap_hours`, 6시간)이 지났을 때 조건이 맞는 것 중 하나를 무게로 고른다. 전투 중에는 열지 않는다. 시나리오에 묶인 이야기(태그가 world가 아닌 것)는 무게를 3배로 본다 (`ROLE_STORY_BOOST`: 도시 공통 이야기가 늘어도 시나리오 이야기가 묻히지 않게)
- 빨리감기 중 열 수 있게 되면 그 시각에 멈춘다 (끼어들기 `storylet`)
- 배역은 장면에 들어온다. GM 컨텍스트에 "진행 중인 이야기"(상황, 연출, 등장, 선택지)가 생긴다. 조건(클락 등)은 넣지 않는다

**선택** (`resolve_storylet(choice_id)`)

- 플레이어의 자연어 행동이 어느 선택지에 해당하는지 분명해지면 GM이 호출한다. 판정이 붙은 선택지는 같은 턴 take_action의 그 판정 결과로 갈린다 (판정이 없으면 거부)
- 효과는 코드가 적용하고, GM에게는 결과만 돌려준다. 세력 클락 변화는 드러나지 않는다

**플래그와 비밀**

- 캐릭터별 플래그가 RAG 검색자의 플래그가 된다. 스토리렛이 세운 `scouts_captured`가 `secret:scouts_captured` lore를 연다
- 실제 확인 (MCP, LLM 없이): 새 세계에서 동쪽 초소의 밤을 기다리자 "흘려듣는 소문"(박만수), "초소 아래의 소리", "물류창고의 불빛"이 차례로 열렸다. 불빛을 지켜보는 위험 감지 판정이 성공하자 플래그가 서고, 그 전에는 나오지 않던 비밀 문서 "실종된 정찰조의 행방 > 수용소"가 `recall`에 나왔다

**12단계에서 바꾼 것** (플레이 테스트 2회차·랜덤 자동 플레이)

- 고정 이야기(한 번뿐)가 열릴 수 있으면 반복 템플릿보다 먼저 연다 (템플릿에 묻혀 안 열리던 문제)
- 캐릭터의 이야기가 시작된 뒤 `first_after_hours`(2시간) 동안은 열지 않는다 (세계를 열자마자 끼어들던 문제)
- 자는 동안에는 `urgent` 이야기만 잠을 깨운다. 나머지는 깬 뒤에 열린다
- 구역을 옮기거나 전투가 열리면 진행 중인 이야기는 끝난다. 시간이 지나 끝나면 이야기 때문에 들어온 배역은 떠난다
- `take_item` 효과(거래): 플레이어가 내놓는다. 가진 것이 없으면 그 선택지를 고를 수 없다
- (12-22) 조건 `dispositions: [{ from, to, gte?, lte? }]`: 세력 사이 지금 태도 (이탈·편들기 뒤의 이야기). `merit_gte`·`level_gte`는 12-21
- (12-18) 조건 더하기: `flags_any`(하나라도), `day_lte`(그날까지), `zone_owner`(지금 구역이 none 누구의 땅도 아님 / own 우리 / other 다른 무리), `factions`(플레이어 소속, 무소속은 none). 태그 `world`는 어느 시나리오에서나 열린다 (12.4)
- (12-18) 효과 더하기:
  - `faction_resource { faction: own|id, resource, delta }`: 세력 자원 ± (약 재고, 물, 할당량). 양은 콘텐츠가 정하고 0 아래로 내려가지 않는다. 창고 사정은 배급과 소문으로만 드러난다
- (12-20) 배역을 이름 없는 인물로: `cast`의 배역에 `extra: <엑스트라 틀>`(+ `label` 호칭)을 주면, 발동할 때 코드가 그 틀로 인물을 만들어(능력·소지품·이름) 장면에 들인다. 다른 배역처럼 효과의 `who`로 쓴다. 반복 템플릿(피난민, 약탈자, 경쟁 떠돌이)이 매번 다른 사람이 된다
- (12-22) 이름 없는 인물을 이어서: 배역 `extra`에 `keep: <이름표>`를 주면 만든 인물을 기억하고, 다음 이야기의 배역 `recall: <이름표>`가 같은 사람을 부른다 (살아 있고 떠나지 않았을 때만, 아니면 그 이야기는 열리지 않는다). 상태의 `keptExtras`, 세이브 형식 10
  - `faction_relation { from, to, delta, mutual }` (12-22): 세력 사이 태도 ± (own = 플레이어 소속, -3~+3에서 멈춤, mutual이면 양쪽). 드러나지 않고 전황·소문으로만 보인다
  - `body { track, delta }` (12-22): 주인공의 몸 상태 ± (먹을 것을 나눠 받음, 젖은 채 밤을 샘). 부상 트랙은 안 되고(원칙 3), 마지막 단계(죽음) 바로 앞에서 멈춘다
  - `join_faction { faction, rank?, title? }`: 주인공이 그 무리에 들어간다 (무소속이면 가입, 다른 무리에 있으면 옮김, 12-21). 옮길 때의 대가(옛 상관 신뢰, 배신 행적)는 같은 선택지의 앞선 효과로 콘텐츠가 정한다. 같은 계급의 시나리오가 있으면 그 시작 지식을 "전해 들은 것"으로 받는다. 무소속 주인공이 무리에 들어간다 (rank가 없으면 자유 시나리오의 가장 낮은 계급). 역할은 코드가 만든다(`joinRole`, 12.5의 규칙 그대로: 상관·동료·임무·배급). 이미 무리에 속해 있으면 아무 일도 없다. 같은 무리 사람들과 서로 이름을 안다
  - `npc_depart { who, to_faction? }`: 배역 NPC가 떠난다. `to_faction`이면 그 세력으로 넘어가 도시에 남고(투항·변절), 없으면 도시를 떠난다(탈영·피난). 떠난 인물(`away`)은 죽음과 달리 연대기에 남지 않고 장면·배역·목격자·소문·상관·계승 후보에서 빠진다. `npc_presence`로 다시 부를 수 없다
- (12-44) 콘텐츠를 쓰며 막힌 것 메우기:
  - 선택지 조건 `choices[].when { flags_all, flags_any, flags_none, has_items, has_items_any, equipped }`: 맞지 않는 선택지는 GM에게 보이지 않고 `resolve_storylet`도 거부한다 (주인공이 모르는 길을 내밀지 않는다). 내놓는 물건(`take_item`)은 적지 않아도 본다. 판정이 붙은 선택지는 어느 결과에서든 내놓을 물건을 굴리기 전에 본다
  - 이야기 조건에도 `has_items_any`(하나라도 지님), `equipped`(지금 들거나 입은 것 중 하나)
  - `keep`은 이름 있는 NPC 배역에도 쓴다: 앞 이야기의 그 사람을 다음 이야기가 `recall`로 부른다 (붙잡혔어도 열리지 않는다)
  - 효과 `npc_relation { from, to, axis, delta, mutual }`: 두 배역 사이의 마음. 드러나지 않고 그들의 말과 태도로만
  - 효과 `zone_noise: 1~3`: 지금 구역에 소리 (`zone_noise_gte` 조건과 감염체를 부른다)
  - 효과 `npc_hurt { who, steps }`: 배역 NPC가 다친다. 죽음 바로 앞에서 멈춘다 (원칙 3)
  - 효과 `npc_rank { who, rank }`, `set_commander { who | reset }`: 지도부가 바뀐다. 주인공의 상관이 그 사람으로 바뀌고(상태 `commanderOverride`, 세이브 형식 21), 무리를 옮기거나 계승하면 역할의 상관으로 돌아간다
- (12-45) 있으면 쓰는 배역 `cast.<key>.optional: true`: 채울 수 없어도 이야기는 열리고 그 배역만 빈다. 상황·연출에는 못 쓰고, 그 배역을 쓰는 선택지는 `when.cast: [key]`에 적는다 (콘텐츠 검증이 잡는다). 예: 잔치 전날 밤, 그물 창고에 숨긴 그물꾼이 살아 있으면 셋을 데리고 나가는 길이 하나 더 열린다
- 초안 25개: 고정 10(물류창고의 불빛, 박만수의 꾸러미, 오지호의 속삭임, 고가도로 너머의 움직임, 누나의 편지, 붉은 완장의 투항자, B 정문의 경비병, 금니 상인의 흥정, 병원 지하로, 분대장의 물음) + 템플릿 15

## 11. AI 연동

### 11.1 턴 루프

```
플레이어 입력 (Claude 앱 채팅, 선택지 클릭 또는 자유 입력)
  → GM(Claude 세션)이 의도를 해석해 take_action 등 MCP tool 호출
  → 코드가 판정·상태 변경 실행 → 결과와 현재 장면(Belief State만)을 tool 결과로 반환
  → GM이 채팅에 서술
  → 상태 저장(자동), 이벤트 로그 기록, 장면이 끝나면 record_turn_summary
```

### 11.2 AI에게 여는 tool

두 플레이 모드가 같은 tool 묶음을 쓴다 (11.5). 턴은 `take_action` 하나로 진행하고, 나머지는 빼먹어도 세계가 깨지지 않는 장면 정리용이다.

**구현됨**

| tool | 용도 |
|---|---|
| `take_action(intent, check, activity, deed, target, narration_summary)` | **턴 진행의 유일한 입구.** 아래 순서로 코드가 처리한다 |
| `npc_presence(npc_id, enter\|leave)` | 이름 있는 인물의 장면 등장·퇴장 |
| `transfer_item(from, to, item_id, quantity)` | 아이템 이동 (존재 검증). 보관 위치는 플레이어, 장면에 있는 NPC, `scene`. 새 아이템은 만들 수 없음. **NPC의 물건은 근거가 있어야 가져온다**: 이번 턴 그 NPC를 `target`으로 한 판정이 성공·대가 있는 성공이었거나, 그 NPC의 신뢰가 2 이상(*임시*) |
| `add_belief(fact, source)` | 플레이어 캐릭터가 새 정보를 알게 됨 (진위는 unknown으로 기록) |
| `assign_mission(template_id)` / `report_mission()` / `abandon_mission(reason)` | 임무 배정·보고·포기 (8.6) |
| `look_for_witnesses(deed_id)` | 누가 봤는지 살피기 (낌새 판정을 코드가 굴림) |
| `reveal_secret(npc_id)` | 신뢰 조건을 채운 인물이 비밀을 털어놓음 |

`take_action` 입력과 처리 순서:

- `intent`: 하려는 것
- `check`: `{ move, stat, difficulty, harm_on_failure, harm_cause }` 또는 null. **몸의 위험(`harm_on_failure`: none·light·heavy)은 판정 전에 선언한다.** 결과가 실패·대가 있는 성공이면 코드가 피해를 적용한다 (AI가 결과를 보고 수위를 고르지 않는다)
- `deed`: `{ summary, tags, severity, privacy, noisy, condition }` 또는 null. `condition`이 `on_success`면 판정이 실패했을 때 기록하지 않는다
- `activity`: `{ kind, until }` 또는 null(잠깐의 행동 5분)
- `target`: 상대 인물 id (장면에 있어야 함) 또는 null
- `for_mission`: 수행 중인 임무를 위한 행동이면 true. **true인 판정·활동만 임무 진행으로 센다** (거점 안의 사적인 행동이 정찰 조건을 채우지 않게. 목격자 살피기 판정은 세지 않는다)
- `narration_summary`: MCP 모드 전용, 직전 서술 요약 (웹 앱 모드는 GM 루프가 자동 저장)
- 처리 순서: 턴 시작 → 판정 → 선언한 위험의 피해(사망이면 여기서 끝) → 행적·목격자 → 시간 경과(빨리감기·끼어들기) → 시간이 흐른 뒤 세계 처리(임무 기한, 오늘의 임무, 소문)
- 웹 앱 모드에서 GM이 한 입력에 `take_action`을 한 번도 부르지 않으면 GM 루프가 잠깐의 행동으로 자동 처리한다 (MCP 모드와 같은 결과)

**아직 없음 (해당 단계에서 추가)**

| tool | 용도 |
|---|---|
| `start_combat(enemies)` | 전투 시작 (적 구성은 템플릿에서) |
| `adjust_relation(a, b, axis, reason)` | 관계 변화 요청. 지금은 행적으로만 관계가 바뀐다 |
| `apply_condition(target, tag, duration)` | 서사적 상태 |
| `create_npc(template, overrides)` | 템플릿 기반 즉석 NPC (스키마 검증) |

### 11.3 프롬프트·비용 원칙

- 세계 규칙, 시스템 프롬프트 같은 고정 부분은 **프롬프트 캐싱**
- 항목별 **토큰 예산**과 초과 시 자를 우선순위를 정한다
- **모델 분리**: 분류·요약은 작은 모델, 서술은 큰 모델
- 빨리감기 시뮬레이션은 LLM 없이 돌리고, 결과 요약에만 1회 호출
- 시스템 프롬프트에 명시: 플레이어 서술을 사실로 받아들이지 않는다, 숫자를 지어내지 않는다, 숨겨진 정보를 언급하지 않는다
- tool은 strict 모드로 정의하고, 입력은 코드가 zod로 다시 검증한다. 검증에 실패하면 실행하지 않고 오류를 tool 결과로 돌려준다
- 한 턴 안의 tool 루프에서는 모델 응답(thinking 블록 포함)을 수정 없이 돌려보낸다. 지난 턴은 텍스트만 남긴다
- 매 턴 user 메시지에 현재 캐릭터 상태(능력치, 부상, 소지품)를 함께 넣고, 보낸 메시지는 그대로 기록해 다음 턴에 재사용한다 (append-only, 캐시 유지)

### 11.4 RAG

MVP에 포함한다. 프로젝트 목표 중 하나다 (0장).

**원칙**

- 임베딩 모델과 벡터 검색은 "구현"이 아니라 "사용"한다. 직접 만드는 것은 청킹, 메타데이터 설계, 검색 시점, 결과를 프롬프트에 조립하는 방식, 평가
- **검색도 정보 필터를 따른다.** 현재 캐릭터가 알 수 없는 청크는 검색 결과에 절대 포함되지 않는다 (원칙 4)
- 구조화된 상태(능력치, 소지품, 관계, 임무 등)는 지금처럼 ID·조건으로 조회해 상태 블록에 넣는다. RAG는 그 밖의 서술형 지식과 장기 기억에 쓴다

**컬렉션**

| 컬렉션 | 내용 | 작성·적재 |
|---|---|---|
| `lore` | 세계 역사, 지역, 세력 배경, 소문과 전설 | `content/scenarios/<id>/lore/*.md`. 한 번에 프롬프트에 다 넣지 않을 분량으로 쓴다 |
| `memory` | 플레이 중 쌓이는 장기 기억: 턴 요약, 장면 요약, 행적(deed), NPC와의 주요 대화 | 저장 시점에 바로 임베딩. 게임이 끝없이 진행되며 계속 커지므로 RAG의 핵심 용도 |

**메타데이터 (필터링용)**

- 공통: `scenarioId`, `collection`, `sourceId`(엔티티 ID), `createdAt`(게임 시간)
- `lore`: `visibility` = `public` | `faction:<id>` | `secret:<flag>` (캐릭터의 소속·플래그·Belief로 접근 판정)
- `memory`: `knownBy` = [characterId...] (그 장면을 보거나 전해 들은 캐릭터만)
- 캐릭터 교체 시 새 캐릭터 기준으로 필터가 바뀐다. 이전 캐릭터의 기억은 검색되지 않는다

**기술 선택**

- 임베딩: 로컬 모델 bge-m3 (Ollama 또는 transformers.js). 다국어 지원, 키 불필요
  - core에 `Embedder` 인터페이스를 두고 구현체를 바꿀 수 있게 한다 (나중에 Voyage AI 등)
- 벡터 검색: SQLite + sqlite-vec
- 키워드 검색: SQLite FTS5 (한국어 고유명사·지명 대응)
- 하이브리드: 벡터 + 키워드 결과를 RRF(Reciprocal Rank Fusion)로 병합
- 저장 시 임베딩 모델 ID와 차원을 함께 기록한다. 모델이 바뀌면 재임베딩한다

**파이프라인**

- 적재(ingestion): 콘텐츠 로드 시 lore를 청킹 → 임베딩 → 저장. 파일 해시로 변경분만 다시 처리한다
- 검색(retrieval): 컨텍스트 조립 단계에서 실행
  - 쿼리 = 플레이어 입력 + 현재 장면 요약 (+ 등장 NPC 이름)
  - 메타데이터 필터 → 하이브리드 검색 → top-k와 토큰 예산으로 자르기
- 프롬프트 배치: 고정 부분(시스템 프롬프트, 세계 규칙, 시나리오 톤)을 앞에 두고 캐싱, RAG 결과는 그 뒤에 넣는다
- 디버깅: 매 턴 어떤 청크가 왜(점수, 경로) 들어갔는지 이벤트 로그와 개발용 UI 패널에서 볼 수 있게 한다

**구현 (4-1, lore)**

- 임베딩: transformers.js로 bge-m3(ONNX 양자화 q8, 약 570MB, CLS 풀링, 1024차원)를 로컬 실행. 모델은 첫 실행 때 `.cache/models/`에 내려받는다. 테스트는 모델 없이 `HashEmbedder`(글자 3-gram 해시)로 돌린다
- lore 문서: 앞머리에 `title`, `visibility`(public | faction:<id> | secret:<flag>). 작성자 메모(`<!-- -->`)는 검색 대상이 아니다. `pnpm content:check`가 앞머리를 검사한다
- 청킹: `##` 절 단위, 긴 절은 문단을 모아 약 600자. 각 청크 앞에 `[문서 제목 > 절 제목]`을 붙인다
- 색인: `.cache/rag/<시나리오>-lore.db` (콘텐츠에서 다시 만들 수 있는 파생 데이터). sqlite-vec(코사인) + FTS5(trigram 토크나이저, 한국어 부분 일치). 파일 해시가 같으면 다시 임베딩하지 않는다. 모델 id·차원이 바뀌면 비우고 다시 만든다
- 키워드 검색어: 3글자 이상 단어. 끝 글자가 조사인지 단어의 일부인지 알 수 없으므로("고가도로"의 "로") 조사를 뗀 말과 원래 말을 둘 다 찾는다
- 검색: 벡터·키워드 후보 각 20개 → **순위를 매기기 전에 정보 필터** → RRF(k=60, 가중치 1:1) → 상위 4개, 글자 예산 2400자
- 웹 앱 모드: 매 턴 검색어 = 플레이어 입력 + 최근 턴 요약 + 함께 있는 인물 이름. 결과는 user 메시지의 `<상태>` 뒤, `<플레이어 입력>` 앞에 `<참고 자료>`로 넣는다
- MCP 모드: `recall(query)`가 lore와 memory를 함께 돌려준다 (6-1)
- 검색 기록: 세이브의 `retrievals` 테이블(append-only, 게임 상태와 별개)에 검색어·키워드 검색어·후보 수·필터 제외 수·잘린 청크·결과(점수, 벡터·키워드 순위)를 남긴다. 웹 앱의 개발용 패널에서 최근 기록을 본다
- 모델 로딩·색인 동기화는 백그라운드로 한다 (MCP 서버가 연결 요청에 바로 응답하게). 준비에 실패하면 검색은 빈 결과와 이유를 돌려주고 게임은 계속된다. `RAG=off`로 끌 수 있다
- 캐릭터 플래그(`secret:<flag>`)는 시나리오 플래그 시스템이 생기기 전까지 비어 있다 (비밀 lore는 아무에게도 검색되지 않는다)

**구현 (6-1, memory)**

- 기억은 세이브에 이미 있는 것에서 만든다: 턴·장면 요약(`summaries`), 행적(`deeds`), 믿음(`beliefs`). memory 색인은 세이브로부터 언제든 다시 만들 수 있는 파생 데이터다
  - 색인 파일: 세이브 옆 `saves/worlds/<세계>.memory.db` (세계 목록에는 나오지 않는다)
  - 청크 id는 `summary:<순번>`, `deed:<id>:named|unnamed`, `belief:<캐릭터>:<id>`. 세이브가 append-only라 id가 바뀌지 않는다
- `knownBy`
  - 요약: 그때의 플레이어 캐릭터 (`summaries.character_id`, 6-1에서 추가. 이전 요약은 현재 캐릭터로 본다)
  - 행적: 한 사람 + 그 일을 보거나 전해 들은 NPC(`deedKnowledge`). 소문이 퍼지면 늘어난다. 본문은 `행동한 사람: 행적` (이름으로 물어도 찾게). 이름 없는 엑스트라는 호칭
    - 목격자가 행동한 사람의 이름을 모를 수 있어서, 행적 하나를 "이름을 아는 사람" 청크(`이나영: …`)와 "모르는 사람" 청크(호칭: `청솔형제단 하급 전투원: …`)로 나누고 각각 `knownBy`를 붙인다 (6.3). 청크 id는 `deed:<id>:named`, `deed:<id>:unnamed`
  - 믿음: 그 믿음을 가진 캐릭터 한 명 (NPC의 믿음은 그 NPC만)
- 적재 시점: 세계를 열 때, tool 실행이 성공한 뒤, 요약을 남긴 뒤 백그라운드로 맞춘다. 본문이 새로 생기거나 바뀐 것만 임베딩하고, `knownBy`만 바뀐 것(소문 전파)은 메타데이터만 고친다. 검색은 진행 중인 적재가 끝난 뒤에 한다 (방금 저장한 기억도 찾게)
- 정보 필터: `knownBy`가 있는 청크는 검색자 캐릭터 id가 그 목록에 있어야 보인다. 캐릭터 id가 없는 검색자는 기억을 하나도 못 본다. lore와 같은 함수(`canSeeChunk`)로 순위를 매기기 전에 거른다
- 후보 모으기: memory 색인에는 모든 인물의 기억이 섞여 있다. 벡터·키워드 검색은 볼 수 있는 후보가 후보 수(20)만큼 모이거나 색인 끝에 닿을 때까지 넓혀 가며 가져온다 (한 번에 최대 4096개). 상위 몇 개만 가져와 거르면 현재 캐릭터의 기억이 남의 기억에 밀려난다
- 같은 문장의 기억이 여럿 걸리면 한 번만 보여 준다
- 웹 앱 모드: lore와 memory를 같은 검색어로 함께 찾아 `<참고 자료>`의 "세계 배경"과 "지난 기억"으로 넣는다. 최근 턴 요약은 대화 기록·지난 이야기에 이미 있으므로 memory 검색에서 뺀다 (상위 4개, 1600자)
- MCP 모드: `recall`이 세계 배경과 지난 기억을 돌려준다 (memory 상위 6개, 3000자)
- `!일지 검색어`: memory를 의미 검색한다 (상위 8개). 검색어가 없으면 최근 일지. 읽기 전용이고, 검색 기록만 `retrievals`에 남는다
- 임베딩 모델 하나를 lore와 memory가 함께 쓴다

**평가**

- 검색 평가 세트: `content/scenarios/<id>/eval/retrieval.yaml`
  - 검색자(캐릭터 id·소속·플래그), 합성 기억(아는 사람 포함), 사례(질의, 검색자, 컬렉션, 기대, 금지)
  - 기대·금지는 청크 번호가 아니라 `lore/<문서> > <절>`, `memory:<id>`로 적는다 (청크 크기를 바꿔도 세트를 고치지 않게)
  - 비슷한 장소·인물이 나오는 방해 기억과, 다른 캐릭터의 비슷한 기억을 함께 둔다
  - `pnpm content:check`가 세트의 형식과 참조(문서·절·기억·검색자)를 검사한다
- 지표: recall@k, hit@1, MRR, 정보 필터 위반 수. 위반은 결과뿐 아니라 검색 기록(trace)에서도 찾고, 색인 필터와 별개로 공개 범위를 다시 판정해 확인한다
- 단위 테스트: 해시 임베더로 여러 설정(청크 크기, top-k, 가중치)에서 위반 0건, 기본 설정 recall@k 50% 이상. 검사기가 위반을 실제로 잡는지도 확인한다
- `pnpm rag:eval`: 실제 모델(bge-m3)로 평가한다. `--chunk`, `--k`, `--candidates`, `--weights 1:1`로 설정을 바꾸고, `--compare`로 여러 설정을 한 표로 비교한다. 실제 세이브와 색인은 건드리지 않는다
- 첫 결과 (bge-m3, 사례 26개): 기본 설정 recall@4 100%, hit@1 96%, MRR 0.98, 위반 0건. 벡터만 쓰면 hit@1 96%, 키워드만 쓰면 83%
  - 평가 세트로 찾은 문제: "물린 상처는 **어떻게** 되나"에서 키워드 검색이 "어떻게"로 엉뚱한 절을 1위에 올렸다 → 키워드 검색어에서 의문사·접속어를 뺀다
  - 지금 세트는 lore·memory가 작아 top-k와 청크 크기에 따른 차이가 거의 없다. 기억이 쌓인 실제 세이브로 사례를 늘려 가며 다시 본다

### 11.5 플레이 모드

**MCP 모드 하나로 만든다** (12-14). Claude 앱(Claude Code·Claude 데스크톱) 세션이 GM이고, 엔진은 로컬 MCP 서버(`mcp`, stdio) → `core`다. 비용은 claude.ai 구독 사용량이라 API 키가 필요 없다. 화면은 채팅 + `?` 정보 명령어 + 상태 화면(캐릭터 시트, 11.6)이다.

- 처음에는 웹 앱 모드(우리 서버의 `gm` 패키지가 Claude API를 호출, 브라우저 화면)를 개발·테스트용으로 함께 만들었다. 실제 플레이가 MCP 쪽에서 이뤄지면서 12-14에 **폐기**했다: `packages/gm`, `packages/server`, 웹 화면(시작 화면·생성 화면·서술 창)을 지웠다. 되살리려면 git 기록(12-13 이전)에서 가져온다. 다시 만들 때도 웹 앱은 API 키만 쓴다 (claude.ai 구독 로그인 연결은 Anthropic 정책상 금지)
- 이 문서의 다른 곳에 남은 "웹 앱" 이야기는 그때의 기록이다
- 게임 규칙, 상태 변경, 정보 필터, RAG 필터링, 명령어 처리는 전부 `core`에 둔다. 어댑터(`mcp`)에는 로직을 두지 않는다. `core`는 LLM을 모른다
- 세이브의 `mode`·잠금의 `web` 값은 이전 세이브를 읽으려고 남겨 둔다

**세이브 공유와 잠금**

- 세이브는 SQLite 파일 하나. 여러 Claude 세션이 같은 세이브 폴더를 쓴다
- 막는 것은 "동시에 같은 세계를 여는 것"뿐이다. 세계를 열 때 잠금 파일(PID, 모드, 시각)을 만들고 닫을 때 해제한다. 죽은 프로세스가 남긴 잠금은 PID를 확인한 뒤 해제할 수 있다
- 세션을 바꿔도 이야기 흐름이 끊기지 않게, 최근 턴의 서술 요약을 반드시 세이브(`memory.recentTurns`, `summaries`)에 남긴다
  - `take_action`이 `narrationSummary`(선택)를 받고, 장면이 끝나면 `record_turn_summary`를 호출하도록 GM 지침에 명시
- `start_session` / `load_world`는 현재 장면, 최근 장면 요약, 최근 N턴 요약을 함께 돌려줘 새 세션의 GM이 바로 이어 갈 수 있게 한다

**시작 화면과 세이브 슬롯** (12-5)

- 저장은 자동이다. 상태 변경은 생기는 즉시 이벤트로 세이브에 들어가고(append-only), 이벤트가 150개 쌓일 때마다와 세계를 닫을 때 스냅숏을 남긴다 (12-47). "저장" 버튼은 없다 (아이언맨)
- 슬롯 요약은 core(`world/slots.ts`)가 만들고 두 모드가 같이 쓴다: 주인공(이름·나이·소속·계급·레벨), 몸 상태(첫 단계에서 나빠진 것만, 숨은 단계는 보이는 단계로), 게임 안 시각과 장소, 복무 일수, 몇 대째, 사망 여부, 마지막 플레이(마지막 이벤트 시각), 다른 곳에서 사용 중인지
- 세이브 형식이 바뀌어도 이전 세이브를 버리지 않는다: `MIN_READABLE_SAVE_VERSION`(2)부터는 스냅숏 대신 이벤트를 처음부터 다시 읽어 새 필드를 스키마 기본값으로 채우고, 이름이 바뀐 능력(`renamed`)도 옮긴 뒤 형식 버전을 올린다. 1은 시나리오 팩 분리 전이라 읽지 않는다 (12-4에서 버전을 올리며 이전 세이브가 보관함으로 밀려난 문제를 12-6에서 고쳤다)
- 웹 앱: 서버를 켜도 세계를 열지 않는다. 시작 화면에서 새 게임(→ 캐릭터 생성) 또는 슬롯을 고른다 (`GET /api/worlds`, `POST /api/worlds`, `POST /api/worlds/:id/open`). 게임 중 "메인 화면"(`POST /api/game/close`)으로 세계를 닫고 잠금을 푼다. 새로고침하면 열린 세계로 바로 돌아간다
- 세이브는 캐릭터 생성이 끝났을 때 처음 만든다 (웹은 생성 화면의 "시작", MCP는 `character`를 받은 `start_session`). 만드는 도중 실패하면 파일을 지운다
- 세이브 삭제 (되돌릴 수 없다, 세이브·WAL·잠금·memory 색인 파일을 모두 지운다). 어디서든 열려 있는 세이브는 지우지 않는다
  - 웹: 시작 화면 슬롯 옆 휴지통 버튼 → 확인 창 → `DELETE /api/worlds/:id`
  - MCP: 게임 목록을 보고 있을 때만 (게임 중이나 목록을 보여 주기 전에는 거절). 플레이어가 "2번 지워 줘"처럼 말하면 GM이 `delete_world(slot)`로 지울 것을 받아 보여 주고, 확인받은 뒤 `confirmed: true`로 지운다. 번호는 플레이어가 본 목록 기준
- MCP: `list_worlds`가 번호 목록(맨 위 0번이 새 게임, 1번부터 저장된 게임)을 돌려주고, GM이 그대로 보여 준다. `start_session`은 `slot`(번호)·`world_id`·`new_world`로 열고, 아무것도 없으면 저장된 게임이 있을 때 목록만 돌려준다. `end_session`으로 닫는다 (잠금 해제)
- Claude Code 스킬: `/play`(목록 → 고르기 → 진행, `/play 2`처럼 번호를 바로 줄 수 있다), `/quit`(장면을 맺고 요약을 남긴 뒤 `end_session`). 저장소의 `.claude/skills/`. MCP prompt `play`도 같은 흐름

### 11.6 MCP 모드

**원칙**

- Claude는 MCP tool 결과로 받은 정보만 본다. 정보 필터(현재 캐릭터의 Belief State)는 서버가 강제한다. World State, 숨은 목격자, 남의 비밀은 tool 결과에 절대 넣지 않는다
- "AI는 숫자를 만들지 않는다"를 서버가 강제한다. 시간 경과와 상태 변경은 반드시 tool을 거쳐야만 일어난다
- Claude가 tool 호출을 빼먹어도 세계가 망가지지 않게, tool을 잘게 쪼개지 않고 **턴 단위로 묶는다**

**상태 화면** (12-8)

- MCP 서버가 `http://127.0.0.1:8790`(쓰이고 있으면 다음 포트, `TRPG_STATUS_PORT`로 변경, `TRPG_STATUS=off`로 끔)에 읽기 전용 상태 화면을 함께 띄운다. Claude 앱의 브라우저 패널에 띄워 두면 웹 앱 오른쪽 시트처럼 게임 상태를 계속 볼 수 있다
- 화면은 웹 앱과 같은 `CharacterSheet`로 된 `ui/status.html`이고, MCP 서버가 Vite 미들웨어로 띄운다 (로그는 stderr, HMR·웹소켓 끔). **시트만 보여 준다.** 이야기(서술)는 Claude 세션의 채팅에서 진행한다
- `GET /api/status/stream`(SSE)이 지금 세션이 연 게임의 플레이어 시트(core `playerView`)를 바뀔 때마다 밀어 준다 (서버가 0.25초마다 비교). SSE가 없는 이전 버전 서버면 화면이 `GET /api/status`를 1.5초마다 읽는다
- 시트의 항목 (12-41에서 따라잡음): 상태·능력·트레잇·스킬, 임무(빌린 장비), 복무(공적·빚), 무리(분위기·배급·방침), 함께 있는 인물, 동행(이유·떨어짐·갈림길), 분대(맡긴 일·보고), 장비(손·몸·머리·팔, 탄약, 닳음, 짐 무게·무거움), 소지품, 관계, 인물 사이(드러났거나 털어놓은 관계만), 행적, 아는 것. 모두 core `views/player.ts`가 정보 필터를 거쳐 만든다
- 캐릭터 생성은 채팅에서 대화로 한다 (4.2, 12-13). 만드는 동안 상태 화면은 "캐릭터를 만드는 중" 안내를 보여 주고, 다 만들면 시트가 열린다. (12-11에서 상태 화면에 생성 화면을 띄웠다가 12-13에서 뺐다)
- **토큰 아끼기** (12-24): MCP 모드에서는 tool 결과가 대화에 쌓이므로, 매 행동에 장면 정보 전체를 붙이지 않는다. 정보를 지우는 것이 아니라 필요할 때 다시 보게 한다

- 행동(`take_action`, `fast_forward`) 뒤에는 지난번 GM에게 보낸 뒤 바뀐 덩어리만 보낸다 (`GameWorld.sceneUpdate`). 캐릭터 상태 덩어리는 늘 싣고, 그대로인 덩어리는 이름만 알린다 ("전체가 필요하면 get_scene")
- 장면 전체를 다시 보내는 때: 세션 시작·`get_scene`, 구역·날짜가 바뀌었을 때, 전투가 시작되거나 끝났을 때, 주인공이 바뀌었을 때, 8턴마다. 이야기가 열리고 끝날 때는 바뀐 덩어리(이야기·함께 있는 인물·알고 있는 인물)만 (12-42)
- 이 구역의 낯선 사람: 최대 5명(갇힌 사람·떠도는 사람 먼저, 나머지는 날마다 돌아가며), 호칭과 겉모습 첫 문장만. 나머지는 "이 밖에 N명" (12-42, 인물이 98명으로 늘어 가장 큰 덩어리가 됐다)
- 알고 있는 인물: 상관·진행 중인 이야기의 배역·이 구역 사람은 겉모습·평판까지, 나머지는 이름·계급·평판 첫 문장 한 줄. 장면에 들어오면 카드 전체가 붙는다
- 알고 있다고 믿는 것: 최근 10개 + 장면에 있는 인물에 관한 것 (최대 30). 나머지는 개수만 알리고 `recall`(기억 검색)로 찾는다
- 20턴 기준 장면 정보가 약 70% 줄었다 (하급 전투원 9.2만 → 2.8만 자, 참모 12.7만 → 3.4만 자)
- 12-42에 다시 쟀다 (지침 + 첫 장면 + 20턴 동안의 변화 + 행동 결과, 5턴마다 구역을 옮기는 측정): 하급 전투원 5.0만 → 4.1만 자, 참모 6.4만 → 5.6만, 분대장 5.7만 → 4.9만, 여울섬 3.1만 그대로. 조용한 턴의 변화는 약 420자, 이야기가 열린 턴은 약 2,500자 (전에는 장면 전체 약 5,000자). 측정 스크립트는 지침(약 9,200자)이 세션마다 한 번이다

**턴 문** (Claude Code 훅): 플레이어가 메시지를 보내면(`UserPromptSubmit`) 상태 화면을 그 순간 모습에서 멈추고, Claude의 답변이 끝나면(`Stop`) 푼다. 그래서 다치거나 물을 마셔도 "행동 → 채팅에 결과 서술 → 시트 갱신" 순서가 된다
  - `scripts/status-hook.sh`가 대화 기록에서 이 세션이 마지막으로 연 세계 id(세션 시작 결과의 `[trpg-world:ID]`)를 찾아 상태 서버들(8790~8799)에 `POST /api/turn/start|end?world=ID`를 보낸다. 서버는 자기 세계 id와 같을 때만 따른다 (세션이 여럿이어도 섞이지 않는다). 훅은 아무것도 출력하지 않고 늘 성공으로 끝난다
  - 훅 설정은 저장소의 `.claude/settings.json`. 훅이 없는 앱(Claude 데스크톱 일반 채팅, 다른 MCP 클라이언트)에서는 신호가 오지 않아 지금처럼 바로 갱신된다. 끝 신호를 놓쳐도 5분이면 풀린다
- 주인공이 죽은 순간에는 GM이 채팅에 무슨 일이 있었는지 서술할 때까지 상태 화면이 죽기 직전 모습을 보여 준다. GM이 서술 뒤에 부르는 `write_epitaph`(또는 `get_chronicle`, `choose_next_character`, 2분 경과)에 사망이 반영된다. 사망 결과 문구는 "결과를 건너뛰고 죽었다는 말만 하지 않는다: 무슨 일이 있었는지, 누가·무엇이 어떻게 해서 죽음에 이르렀는지부터"를 요구한다
- 12-9에서 서술을 상태 화면으로 보내는 방식(`narrate`, 채팅은 입력만)을 시도했다가 되돌렸다: MCP 모드는 Claude 세션의 채팅에서 진행하는 것으로 둔다
- 정보 필터는 웹 앱과 같다 (core 뷰만 보낸다). 상태를 바꾸는 API는 없다
- `start_session` 결과에 주소가 들어 있어 GM이 플레이어에게 한 번 알린다
- 웹 앱의 좁은 화면용 시트 접기 규칙은 게임 화면(`.app`)에만 적용해, 브라우저 패널처럼 좁은 곳에서도 상태 화면은 시트 전체를 보여 준다

**tool**

| tool | 용도 |
|---|---|
| `start_session(worldId)` / `load_world` / `list_worlds` | 세계 열기·목록. 현재 장면과 최근 요약을 함께 반환 |
| `get_scene()` | 현재 장면, 등장 인물(프로필 + 관계), 플레이어 상태, 활성 스토리렛, 선택지 후보. 필터 적용 |
| `take_action(intent, move?, target?, details, narrationSummary?)` | **턴 진행의 유일한 입구.** 행동 분류 검증 → 판정(2d6) → 상태 변경 → 시간 경과 → 목격자·소문 처리 → 끼어들기 확인 → 결과와 다음 장면 반환. 사망 시 사망 정보 포함 |
| `resolve_storylet(choice_id)` | 스토리렛 선택 (10.4). 이동은 `take_action.move_to`, 플래그는 스토리렛 효과로만 |
| `fast_forward(until)` | 이동·대기 빨리감기. 끼어들기가 생기면 멈추고 반환 |
| `recall(query)` | RAG 검색 (lore + memory). 필터링은 서버에서 |
| `record_turn_summary(text)` | 턴·장면 요약을 memory에 저장·임베딩 (웹 앱 모드는 `gm`이 같은 core 함수를 호출) |
| `run_command(input)` | 정보 명령어 (11.7) |
| `get_chronicle()` / `choose_next_character(character_id, name?)` / `write_epitaph(text)` | 사망 후 연대기·묘비명·계승 (3.2.1) |

**GM 지침**

- 웹 앱 모드의 시스템 프롬프트(GM 원칙, 시나리오 톤, 화법 규칙)를 MCP prompt로도 노출한다. 예: `play` 프롬프트를 고르면 GM 지침 + `start_session` 안내
- 지침 원문은 `content/scenarios/<id>/prompts/`에 두고 두 모드가 같은 파일을 읽는다
- 지침에 명시할 것
  - 플레이어 행동마다 `take_action`을 호출한다
  - 숫자를 지어내지 않는다
  - tool 결과에 없는 정보를 말하지 않는다
  - 장면이 끝나면 `record_turn_summary`를 호출한다
  - 입력이 `!`로 시작하면 서술하지 말고 `run_command` 결과를 코드 블록으로 그대로 출력한다 (요약·수정 금지)
  - 플레이 시작 시 `!도움말` 안내를 한 줄 보여 준다

**실행**

- pnpm 스크립트로 MCP 서버를 실행한다 (예: `pnpm mcp`)
- README에 Claude 데스크톱(`claude_desktop_config.json`)과 Claude Code(`.mcp.json`) 등록 방법을 쓴다
- MCP 서버 로그는 stderr로만 쓴다. stdout은 MCP 프로토콜 전용이다

### 11.7 정보 명령어 (MUD식)

**구조**

- 접두어: 웹 앱은 `!`, MCP 모드는 `?` (`?상태`, `?인물 강태호`). 두 모드 모두 `!`·`?`(전각 포함)를 다 받고, 안내에는 모드의 접두어를 쓴다
  - 처음엔 `/` 슬래시 커맨드와 충돌하지 않게 `!`로 정했지만, Claude 앱(Claude Code)은 줄 맨 앞의 `!`를 셸 명령 모드로 가로채 터미널에서 실행한다. 그래서 MCP 모드는 `?`로 바꿨다 (`?`만 치면 도움말)
- 파서와 포맷터는 `core`에 둔다 (`packages/core/commands`). 웹 앱 모드에서도 입력창·커맨드 팔레트로 같은 명령어를 쓴다
- MCP에는 `run_command` 하나로 노출한다 (`get_character_sheet` / `get_map` / `get_relations` 같은 개별 tool은 만들지 않는다)
- 명령어 정의는 데이터로: 이름, 별칭(예: 상태/스탯), 인자, 설명, 핸들러. 시나리오별로 추가·이름 변경이 가능하게 한다

**규칙**

- 정보 명령어는 읽기 전용이다. 게임 시간을 소모하지 않고 상태를 바꾸지 않는다 (테스트로 보장)
- 모든 출력은 정보 필터를 거친다
- 출력은 서버가 완성된 텍스트로 만든다 (고정폭 기준 레이아웃)
- 행동(이동, 수색, 전투 등)은 명령어로 만들지 않는다. 자연어 → `take_action`
- 알 수 없는 명령어는 가장 가까운 명령어를 제안하고 `!도움말`을 안내한다

**MVP 명령어**

| 명령어 | 내용 |
|---|---|
| `!상태` | 능력, 스킬, 레벨·경험치, 몸 상태, 소속과 등급, 평판 |
| `!소지품` | 인벤토리, 무게 |
| `!지도` | 현재 위치, 아는 장소와 연결, 이동 시간 |
| `!시간` | 날짜, 시각, 계절, 날씨 |
| `!인물 [이름]` | 아는 인물 목록 / 특정 인물에 대해 아는 것과 관계 |
| `!세력` | 아는 세력 정보와 관계 |
| `!임무` | 현재 임무와 목표 |
| `!배급` | 받은 배급, 무리 자원에 대해 아는 것 |
| `!소문` | 최근 들은 소문 |
| `!일지 [검색어]` | RAG recall (memory, 현재 캐릭터 기준 필터). 검색어가 없으면 최근 일지 N개 |
| `!연대기` | 죽은 캐릭터들의 기록 |
| `!도움말` | 명령어 목록 |

**게이지**

- 채움 `█`(U+2588), 빈칸 `░`(U+2591), 대괄호 없음
- 기본 8칸. 값은 비율로 환산해 반올림한다 (0이 아니면 최소 1칸)
- `core/commands`의 공통 포매터 함수 하나로 처리하고, 칸 수는 인자로 받는다
- 게이지 뒤 두 칸 띄우고 상태 텍스트

## 12. 데이터와 저장

### 12.1 콘텐츠

- 세력, NPC, 장소, 역할, 아이템, 스토리렛은 **YAML 파일로 Git에 관리**. 시나리오 팩마다 `content/scenarios/<id>/` 아래에 둔다 (12.3)
- 서버 시작 시 메모리로 읽는다. 세이브에는 콘텐츠를 복사하지 않고 id로만 참조한다
- **zod 스키마**로 콘텐츠와 런타임 양쪽 검증. 한 파일에 객체 하나 또는 목록을 둘 수 있다
- 검증은 오류를 한 번에 모아 보고하고, 콘텐츠끼리의 참조(역할의 시작 아이템 등)도 검사한다
- 현재 구현된 종류: 아이템, 역할, NPC, 시작 지식, 임무. 나머지는 해당 단계에서 스키마를 추가한다

### 12.2 세이브

- **SQLite** (로컬 파일). 세계 하나 = DB 파일 하나 (`saves/worlds/<worldId>.db`). 두 플레이 모드가 같은 파일을 쓰고, 잠금 파일로 동시 접근만 막는다 (11.5)
- 구조: **세계 세이브 1개 + 캐릭터 런 기록 여러 개**
- **이벤트 로그가 원본**, 상태는 스냅샷. 판정, 굴린 값, 상태 변경을 append-only로 기록
  - 첫 이벤트는 `world_created`(시작 캐릭터 포함). 상태는 이벤트를 차례로 적용한 결과다
  - 이벤트는 상태에 먼저 적용해 보고, 성공한 것만 기록한다
  - 이벤트가 150개 쌓일 때마다와 닫을 때 스냅샷을 남기고, 불러올 때는 마지막 스냅샷 + 이후 이벤트로 복원한다
  - 이벤트를 적용할 때 상태 전체를 복사하지 않고 바뀐 부분만 새로 만든다 (immer, 구조 공유. 12-47). 그래서 상태는 리듀서 밖에서 고치지 않는다 (`TRPG_FREEZE=1`로 테스트하면 고친 곳이 드러난다). 하는 일이 같은 300턴 자동 플레이가 턴당 14.5ms → 6.9ms
  - `events`, `transcript` 테이블은 트리거로 UPDATE·DELETE를 막는다
- 세이브 형식 버전(`SAVE_SCHEMA_VERSION`)이 다르면 열지 않는다. 형식을 바꾸면 버전을 올리고 이전 세이브를 옮기는 방법을 만든다
- "새 게임"은 새 세계를 하나 더 만든다. 이전 세계는 `saves/worlds/`에 그대로 남는다. 형식·시나리오가 맞지 않는 세이브만 `saves/archive/`로 옮긴다
- 필드 추가처럼 호환되는 변경은 기본값을 주고 버전을 올리지 않는다 (예: 5단계의 `time`은 이전 세이브에서 시작 시각으로 본다)
- 아래 타입은 최종 목표 형태다. 현재 구현은 단계별로 필드를 늘려 간다

```ts
type WorldSave = {
  meta: { schemaVersion: number; scenarioId: string; worldId: string; day: number; updatedAt: string };
  time: GameTime;
  factions: Record<string, FactionState>;
  characters: Record<string, CharacterState>;   // 플레이어와 NPC 동일 스키마
  beliefs: Record<string, Belief[]>;            // 캐릭터별
  deeds: Deed[];
  rumors: Rumor[];
  locations: Record<string, LocationState>;
  clocks: Record<string, { filled: number; max: number }>;
  storylets: Record<string, { fired: number; lastFiredAt?: GameTime }>;
  flags: Record<string, boolean | number | string>;
  currentRun: { characterId: string; startedAt: GameTime };
  chronicle: RunRecord[];                       // 죽은 캐릭터들의 기록
  memory: { recentTurns: Turn[]; summaries: Summary[] };
  eventLog: GameEvent[];
};
```

### 12.3 시나리오 팩

게임 시스템(판정, 시간, 정보 필터, 평판, RAG 파이프라인)은 그대로 두고, 세계관을 시나리오 팩으로 갈아 끼울 수 있게 한다 (예: 나중에 중세 판타지).

**core에 하드코딩하지 않는 것 (시나리오 설정)**

- 자원 종류 (`post_apoc`: 식량, 물, 탄약, 의약품, 연료)
- 능력, 스킬(move)과 각 스킬이 쓰는 능력, 범위·상한, 성장 수치
- 상태 트랙 (`post_apoc`: 부상, 감염)
- 소속 등급 사다리
- 화법 규칙, GM 톤 프롬프트, 환경 위협·조우 테이블

**콘텐츠 구조**

```
content/scenarios/post_apoc/
  scenario.yaml
  factions/ npcs/ locations/ roles/ items/ storylets/
  lore/ speech/ prompts/ eval/
```

```yaml
# scenario.yaml (예시)
id: post_apoc
resources: [food, water, ammo, medicine, fuel]
stats: [strength, agility, nerve, senses, persuasion]
moves: [fight, scavenge, sense_danger, stealth, endure, persuade, aid]
condition_tracks: [harm, infection]
rank_ladder: [loner, outsider, grunt, squad_leader, officer]
speech_rules: speech/post_apoc.yaml
gm_tone: prompts/post_apoc_tone.md
```

**구현 규칙**

- 위 항목은 문자열 리터럴 타입이 아니라 시나리오에서 로드한 ID로 다룬다. zod 스키마는 시나리오 설정을 받아 동적으로 검증한다
- 세이브 메타(`WorldSave.meta`)와 RAG 메타데이터에 `scenarioId`를 기록한다
- 과하게 일반화하지 않는다. 지금은 "이름과 목록을 데이터로 뺀다"까지만 한다. 규칙 자체의 플러그인화는 두 번째 장르를 실제로 만들 때 한다

**구현 (`post_apoc`)**

- `scenario.yaml`의 목록은 `{ id, label }` 객체로 쓴다 (화면·프롬프트에 한국어 이름이 필요해서)
- 위 예시에 더해 둔 항목: `move_roles`(낌새 알아차리기·은밀 행동에 쓰는 행동), `harm_track`(판정 피해가 쓰는 트랙, 마지막 단계는 반드시 사망), `promotion`(진급 경로), `threats`(빨리감기 이상 징후 확률·문구)
- 시작 장면은 역할(`roles/*.yaml`의 `opening_scene`)에 둔다. GM 프롬프트 = 공통 규칙(core) + 시나리오 톤(`prompts/`) + 시작 장면
- ID는 예시를 따랐다 (`nerve`, `senses`, `scavenge`, `outsider`). 예시에 없지만 쓰는 곳이 있는 `staff`(지원 인력)와 `leader`(지도부)는 남겼다. `aid`(돕기)와 `infection`(감염)은 규칙을 구현할 때 목록에 넣는다
- 캐릭터의 부상은 `conditions`(트랙별 단계)와 `dead`로 바뀌었다. 세이브 형식 2. 형식이나 시나리오가 다른 세이브는 서버가 `saves/archive/`로 보관하고 새 세계를 연다
- 아직 core에 있는 장르 후보: 가치관 축(규율·의리 등), 행동 태그 13종, 활동 시간표(보초 등). 두 번째 장르를 만들 때 시나리오로 옮길지 정한다

### 12.4 월드와 시나리오 (12-15)

**말 정하기.** 플레이어에게 보이는 말과 코드의 이름이 다르다.

| 플레이어에게 | 코드·폴더 | 예 (`post_apoc`) |
|---|---|---|
| **월드**: 세계관 하나 | 시나리오 팩 (`content/scenarios/<id>/`, `Scenario`, 세이브 meta `scenario_id`) | 무너진 도시, 가람 |
| **시나리오**: 그 월드에서 어떤 사람으로 어디서 시작하는지 | 시작 역할 (`roles/*.yaml`, 상태의 `roleId`) | 청솔형제단의 하급 전투원 |
| 게임(세이브 슬롯) | 세계 (`saves/worlds/<worldId>.db`, `GameWorld`) | 1. 서진 · … |

코드 이름을 플레이어 말로 바꾸는 큰 이름 바꾸기는 하지 않았다 (세이브·환경 변수·폴더가 걸린다). 새 코드와 문서에서는 위 표로 옮겨 읽는다.

**새 게임 흐름** (MCP, core `game/newGame.ts`): 월드 고르기 → (월드 이야기) → 시나리오 고르기 → (지금 상황) → 캐릭터 만들기(4.2의 대화식 생성) → 확인에서 세계를 만든다. 월드·시나리오가 하나뿐이어도 소개하고 고르게 한다. 사망 뒤 새 캐릭터는 같은 월드·시나리오라 바로 캐릭터 만들기부터 (월드 이야기·지금 상황 없이).

- 월드 고르기에 보이는 것: `scenario.yaml`의 `world: { title, tagline, description }`
- 월드 이야기(시나리오를 고르기 전에 GM이 들려준다): `intro` 파일 (`prompts/intro.md`). 그 월드의 어느 시나리오로 시작해도 알 만한 것만
- 시나리오 고르기에 보이는 것과 지금 상황: `roles/*.yaml`의 `scenario: { title, pitch, intro }`
- 단계별 서술 힌트: `creation.narration`

**여러 월드를 받는 구조**

- MCP 서버는 `content/scenarios/` 아래 `scenario.yaml`이 있는 폴더를 모두 월드로 읽는다 (`loadContentPacks`). 폴더 이름 = 팩 id. `SCENARIO=<id>`로 하나만, `CONTENT_DIR`로 다른 폴더 하나만
- `WorldManager`는 팩 여럿을 들고, 세이브를 만들 때 고른 팩 id를 meta에 남기고 열 때 그 팩으로 연다. 목록에는 아는 월드의 세이브만, 줄마다 월드 이름. 설치되지 않은 월드의 세이브는 목록에 없고 지우지도 않는다
- lore 색인은 월드마다 따로 (`.cache/rag/<id>-lore.db`), 처음 그 월드의 세계를 열 때 연다. 임베딩 모델은 함께 쓴다
- tool 입력 스키마(행동·능력 id 등)가 월드마다 다르다. 세계를 열면 MCP tool의 스키마를 그 월드 것으로 바꾸고 `tools/list_changed`를 알린다. 검증은 core가 그 세계의 월드로 한 번 더 한다
- `pnpm content:check`는 모든 월드 팩을 검사하고, 월드·시나리오 소개가 빠졌으면 알려 준다

**새 월드를 더할 때 (체크리스트)**

1. `content/scenarios/<id>/`를 만든다. `post_apoc`을 본뜬다: `scenario.yaml`(id = 폴더 이름, `world` 소개, 능력·스킬·상태 트랙·등급·생성 규칙·트레잇·이름·전쟁 수치), `roles/`(시나리오마다 `scenario` 소개), `factions/ npcs/ locations/ items/ storylets/ extras/ beliefs/ missions/`, `lore/`, `speech/`, `prompts/`(톤·GM 규칙·MCP 규칙·`intro.md`), `eval/`(검색 평가 세트, 선택)
2. `pnpm content:check`로 검증한다
3. 새 세션에서 `/play` → 0번 → 새 월드가 보이는지
4. 장르가 크게 다르면 아직 core에 남은 장르 요소를 먼저 옮긴다 (아래)

### 12.5 직접 쓰는 시나리오 (12-16)

시나리오 고르기에 **직접 쓰기**가 있다 (월드 팩에 `custom_start`가 있을 때). 플레이어가 누구로, 어디서 시작하는지 글로 쓰면 GM이 그 글을 월드의 부품으로 옮기고, 코드가 검증해 역할을 만든다. core `game/customStart.ts`.

- 흐름: 직접 쓰기 → 플레이어의 글 → GM이 옮기기(`create_character(custom_start: {...})`) → 확인(이대로 / 다시 옮기기 / 다시 쓰기) → 지금 상황(GM이 쓴 첫 장면) → 캐릭터 만들기
- GM이 고르는 것 (목록 안에서만, 코드가 검증): 세력(또는 무소속), 계급, 직함(짧은 글), 시작 구역, 소지품 꾸러미, 시작 훈련, 나이, 첫 장면(한두 문장), 지난 삶(몇 문장)
  - 계급: 세력에 속하면 `custom_start.ranks` (post_apoc: 하급 전투원·지원 인력·분대장·간부). **무리마다 한 자리뿐인 지도부는 고를 수 없다.** 참모·중간 리더는 간부·분대장으로. 리더를 원하면 GM이 가장 가까운 계급으로 옮기고 알린다
  - 무소속: `free_rank`(혼자)로, `free_locations`(누구의 땅도 아닌 곳)에서만. 세력이 있으면 그 세력이 차지한 구역에서만
  - 소지품은 월드가 정한 꾸러미 중 하나 (꾸러미 6개). 시작 훈련은 2포인트, 스킬 하나에 +1까지 (하급 전투원과 같은 무게). 나이 16~65
  - 월드 밖의 세력·인물·장소·물건은 만들지 않는다
- 코드가 정하는 엔진 값: 아는 인물(같은 세력 모두, 무소속은 없음), 상관(같은 세력에서 바로 위 계급의 인물. 간부면 지도부, 분대장이면 간부), 임무·배급(같은 세력의 콘텐츠 역할에서), 시작 지식(그 역할과 계급이 같을 때만. 분대원의 지식을 참모에게 주지 않는다), 스토리렛 태그
- 플레이어가 쓴 지난 삶은 **주인공 자신의 기억**(믿음, 대략적)으로만 남는다. 세계의 사실이 되지 않는다 (원칙 4, 5)
- 만든 역할은 세이브에 들어간다 (`world_created.customRole`, 상태의 `customRole`, `roleId: "custom"`, 세이브 형식 8). `GameWorld.content`가 그 역할을 `roles`에 넣어 주므로 역할을 읽는 곳(임무, 상관, 시작 장면, 연대기, 계승)은 그대로 동작한다. 사망 뒤 새 캐릭터도 같은 역할로 이어 간다
- 무소속은 플레이어의 `factionId`가 비어 있다 (엑스트라의 떠돌이와 같다). 배급·임무·세력 소식이 없고, 진급 경로도 없다. 며칠 지내도 멈추지 않는 것을 테스트로 확인했다
- 무소속은 수색(4.7)으로 먹을 것을 구한다. 꾸러미마다 먹을 것이 하나씩 있다
- 자유 시나리오의 임무·배급·태그는 같은 세력에서 계급이 같은 콘텐츠 역할을 먼저 빌린다 (분대장이면 분대장 시나리오)
- 무소속의 이야기 (`storylets/world_loner.yaml`, 태그 `world` + `factions: [none]`): 무리마다 들어갈 길이 하나씩 있다 (청솔 순찰조, 붉은연합 통행세, 하얀매 수색꾼, 나루상단 하루 품, 버들마을 정문의 하룻밤). 하루벌이·거래·다른 떠돌이·모닥불 소문도 있다. 들어가면(`join_faction`) 그 무리의 상관·동료·임무·배급이 생긴다
- 스카우트 (12-21, `storylets/world_scout.yaml`): 공적 9 이상(진급할 만한 사람, 조건 `merit_gte`)이 되면 다른 무리가 손을 내민다. 붉은연합(마경수, 약탈조장), 청솔형제단(최선희, 분대장), 나루상단(탁봉수, 호위대장), 하얀매(서은영의 편지, 진료소), 버들마을(장현우, 경비조장). 받아들이면 배신 행적과 옛 상관의 신뢰 하락 뒤 옮겨 가고, 거절하고 알리면 공적이 쌓인다. 옮긴 무리의 같은 계급 시나리오 이야기가 이어진다
- 무소속의 긴 이야기 (`storylets/world_loner_arcs.yaml`, 12-22): 떠돌이 무리(만남 → 물 → 저녁 → 열병 → 배신 → 갈 곳), 문소라의 의뢰 장부(일감 셋, 붉은연합을 돕는 봉인된 깡통), 시립병원 옥상의 무전수. 이름 없는 떠돌이는 keep/recall로 같은 사람이 이어진다
- 무리 사이 정치 (`storylets/world_politics.yaml`, 12-22): 버들마을 이탈 전의 긴장과 뒤의 장면, 나루상단이 편을 든 뒤의 물값. 기존 이야기의 선택이 b_waver·e_side를 당기고 늦춘다 세력에 속해도 하급 전투원용 임무만 있다 (간부용 임무·스토리렛은 콘텐츠가 필요하다)

### 12.7 수위 (12-57)

성인 주제(성인 사이의 연애, 성적인 농담·괴롭힘·위협)는 세계마다 켜고 끈다. 기본은 끔이다.

- 새 게임에서 시나리오(또는 직접 만들기의 확인) 다음, 캐릭터 만들기 전에 묻는다 (월드 팩에 `content_rating`이 있을 때). 게임 중에는 플레이어가 말하면 GM tool `set_content_options { mature }`로 바꾼다. 상태 `options.mature`, 이벤트 `content_options_set`
- 이야기 태그 `content_rating.tag`(post_apoc: `mature`)가 붙은 이야기는 수위가 켜져 있고 **주인공과 배역이 모두 `adult_age`(18) 이상**일 때만 열린다. 나이를 모르면 성인이 아닌 것으로 본다. 엑스트라 틀이면 틀의 가장 어린 나이로 본다
- GM 상태에 수위와 지킬 선이 들어간다: 꺼져 있으면 그런 것을 장면에 들이지 않는다. 켜져 있어도 미성년자는 어떤 경우에도 대상이 아니고, 잠자리는 암전, 노골적인 묘사는 하지 않고, 성폭력은 시도와 위협까지만(어떤 판정 결과로도 일어나지 않는다, 벗어나거나 대가를 치르는 것으로)
- 폭력과 죽음, 생존의 잔혹함은 수위와 상관없이 다룬다
- **연애** (12-58, `scenario.romance`, `engine/romance.ts`): 수위가 켜져 있고 둘 다 성인일 때만
  - 끌림은 인물 데이터: NPC의 `attracted_to`(끌리는 성별 목록, 빈 목록이면 아무에게도). 없으면 월드의 `orientation` 비율로 인물 id에서 정해진다 (판마다 같다). 주인공의 마음은 플레이어가 정한다
  - 마음: 끌리고 호감이 `interest_affection` 이상. GM에게는 장면의 **눈길**(겉으로 보이는 낌새)로만 보인다 (속마음을 말하지 않는다, 원칙 4)
  - GM tool `romance { target, action }`: flirt 다가가기(`flirt_moves` 판정, 하루에 한 사람 한 번, 끌리지 않으면 호감이 오르지 않는다), confess 고백(받아들일지는 코드: 끌림·호감 `accept.affection`·신뢰 `accept.trust`, 마음을 둔 다른 사람보다 주인공을 더 좋아하는가), break_up 이별. 잠자리는 암전
  - 상태 `romances`(두 사람: lovers/ended, 질투한 상대), 인물 사이 관계에 `lover`(연인)
  - **삼각관계**: ① 연인이 보는 앞에서 다른 사람에게 다가가면 그 자리에서 알아챈다 ② 연인이 둘이면 먼저 연인이 하루마다 `jealousy_chance`로 알아채고(한자리에 있으면 반드시) 마음이 많이 식으면 떠난다 ③ 연인이 있는 사람이 주인공을 받아들이면 그 연인은 버림받고 주인공을 원망한다 ④ 둘이 주인공에게 마음이 있고 한자리에 있으면 서로 앙금이 생긴다
  - 연인이 죽으면 마음 트랙 +`grief_nerves`
  - 이야기 배역 `romance: lover | suitor | jealous | rival_lover`, 조건 `has_lover`. 연애 배역을 쓰는 이야기는 성인 주제 태그가 있어야 한다 (콘텐츠 검증)
  - 세이브 형식 29

### 12.6 직분과 배경 (12-46)

시나리오(정해진 시작 역할)보다 **직접 만들기**가 기본이다. 새 게임에서 "직접 만들기"가 먼저 보이고, 정해진 시나리오는 "추천 시작"으로 남는다. 플레이어는 어느 무리에서(세력), 무슨 일을 하는(직분), 어떤 자리의(계급) 사람인지와 지난 일을 쓴다.

**직분** (`scenario.occupations`): 무리 안에서 맡은 일. 계급과 따로다 (요리사도 하급일 수도, 간부일 수도 있다)
- 직분마다: 고를 수 있는 계급(`ranks`), 무소속 가능(`free`), 직분 훈련(`skills`, 시작 훈련 포인트와 따로 더한다), 직분 도구(`kit`), 일감(`missions`, 무리를 가리지 않는다), 이야기 태그(`occ_<id>`)
- 전투원(`borrows_role`)은 무리의 같은 계급 시나리오의 임무·이야기를 그대로 받는다. 다른 직분은 그 시나리오에서 배급·회의 자리만 빌리고 임무와 시나리오 이야기는 빌리지 않는다 (요리사에게 정찰 임무가 오지 않는다)
- 직분 사다리(`ladder`): 평판(`standing`)이 쌓이면 오른다 (요리사: 숙수 → 부엌 반장 → 주방장). 직분의 일감을 완수하면 +1, 이야기 효과 `standing: ±n`. 캐릭터의 `occupation { id, standing }` (NPC도 같은 스키마, 원칙 6)
- 이야기 조건 `occupations: [id | none]`, `occupation_step_gte`
- `post_apoc`: 전투원, 요리사, 목수, 상인, 종교인, 의무병, 정비공, 수색꾼. 기존 시나리오 중 전투원 다섯과 수습 의무병에 직분을 붙였다
- NPC도 직분이 있다 (12-50, 64명: 전투원 37, 의무병 12, 상인 9, 요리사 3, 정비공 3, 수색꾼 3, 목수·종교인 1). GM의 인물 소개에 보이고, 계승하면 그 직분의 일감·이야기가 이어진다. 배역 `occupations: [id | same]`로 같은 직분의 동료를 부른다

**배경 부품** (`custom_start.history`): 플레이어가 쓴 지난 일 중 **세계의 사실이 되는 것**. GM은 글을 이 목록 안에서만 옮기고 코드가 검증한다. 나머지 지난 삶은 지금처럼 주인공의 기억(믿음)으로만 남는다 (원칙 4, 5)
- `loss { who, by, where }` 잃은 사람들 / `enemy { target, why, knows_you }` 원수 (세력 또는 **기존 인물도 된다**: 그 사람이 정말 그 일을 한 것이 된다) / `kin_alive { template, label, zone }` 살아서 기다리는 가족 / `seeking { template, label }` 찾는 사람 / `debt { faction, size }` 빚 (크기는 월드의 `debt_sizes`) / `deserter { faction }` 도망쳐 나온 무리
- 세계에 남는 것: 플래그(`bg_loss`, `bg_loss_by_<세력>`, `bg_enemy`, `bg_enemy_person`, `bg_hunted`, `bg_kin_alive`, `bg_seeking`, `bg_debt`, `bg_deserter_<세력>`), 주인공의 기억 한 문장씩, 원수·가해자가 인물이면 주인공이 그 이름을 안다(원수가 주인공을 알면 그쪽의 신뢰 -2), 살아 있는 가족은 그 구역에서 기다리는 연고 동행(7.9), 찾는 사람은 코드가 아무 구역에나 둔다(아무도 모른다), 빚. 상태의 `background`, 세이브 형식 22
- 배역 `background: enemy | enemy_member | kin | sought | creditor | deserted` (+ `here`: 지금 이 구역에 있는 사람만, 함께 다니는 사람은 늘 여기): 배경의 사람을 이야기가 부른다. 원수가 인물이면 `enemy_member`는 그 사람의 무리(본인 빼고). `creditor`는 빚진 무리, `deserted`는 도망친 무리의 사람
- 이야기 조건 `at_loss_place`: 잃은 그곳(loss.where)에 있을 때만. 선택지 조건 `cast_empty`(있으면 쓰는 배역이 비었을 때만), `in_faction`(무리 소속일 때만/무소속일 때만). 몸 상태 효과 `body`에 `chance`
- 전투원이 아닌 직분의 상관은 거점에 머무는 윗사람(간부, 간부면 지도부). 처음부터 붙잡힌 사람과 떠도는 사람은 상관이 되지 않는다
- 콘텐츠 (12-46): 직분 이야기 `storylets/occ_<id>.yaml` (요리사 13, 종교인 13, 목수 11, 정비공 10, 상인 12, 수색꾼 10, 의무병 10, 전투원 8)과 일감 `missions/occ_<id>.yaml` (직분마다 2~4). 배경 이야기 `storylets/bg_history.yaml` 18개 (원수 연쇄: 멀리서 → 같은 불 앞 → 둘만 남은 골목, 원수의 가족, 쫓김, 원수 무리의 부상자, 가족이 짐이 되는 날, 찾는 사람: 소문 → 목격자 → 재회, 빚쟁이, 도망자 수배, 기일)
- (12-48) 남은 빈틈 메우기:
  - **마음** (상태 트랙 `nerves`: 멀쩡함 → 흔들림 → 너덜너덜함 → 무너짐, 부상은 주지 않고 판정만 어렵다): 크게 다치면 +1, 곁의 사람(장면·동행)이 죽는 것을 보면 +1. 냉정 1당 15% 버틴다. 굶주리거나 얼지 않고 우리 땅이거나 곁에 사람이 있으면 하루마다 25%(냉정 1당 +10%) 가라앉는다. 이야기 조건 `conditions_at_least { 트랙: 단계 }` (숨은 단계는 보지 않는다), 효과 `body { track: nerves }`
  - **구역 보강** (`zones[].fort` 0~3): 이야기 효과 `fortify: ±n` (우리 땅에서만), 임무 `fortifies: n` (완수하면 그 무리 거점, 일부 완수는 절반). 한 단계마다 지키는 병력 ×1.2. 빼앗기면 사라진다. 우리 땅이면 GM 상태에 보인다. 목수의 담·망루 이야기와 일감에 붙였다
  - **엿듣기** 효과 `overhear { faction: other | enemy | id, source }`: 그 무리가 지금 준비하는 일(세력 클락)이 어디쯤인지 대략의 믿음으로 남긴다. 코드가 진짜 상태에서 고르므로 GM이 지어내지 않는다. 정비공의 무전 이야기에 붙였다
  - 세이브 형식 23
- 자기 무리를 통째로 원수로 둘 수 없고, 지금 무리에서 도망쳐 나왔을 수도 없다. 찾는 사람은 하나
- GM 상태의 "지난 일": 첫 주인공일 때만 (계승한 다음 사람의 과거가 아니다)

**두 번째 월드가 장르가 다를 때 남은 일** (원칙 7: 플러그인화는 두 번째 장르를 실제로 만들 때)

| UI | Vite + React (SPA) |
| MCP | `@modelcontextprotocol/sdk`, stdio transport. 상태 화면은 같은 프로세스의 로컬 HTTP(SSE) |
| DB | SQLite + Drizzle (나중에 Postgres 전환 가능하게 저장소 레이어 분리) |
| 검증 | zod |
| LLM | Claude 앱 세션이 GM (구독 사용량). 프로젝트 코드는 LLM을 부르지 않는다 |
| 임베딩 | bge-m3 로컬 실행 (transformers.js, ONNX q8). `Embedder` 인터페이스로 교체 가능 |
| 벡터 검색 | SQLite + sqlite-vec |
| 키워드 검색 | SQLite FTS5. 벡터 결과와 RRF로 병합 |
| 패키지 | pnpm workspaces 모노레포 |

```
trpg/
├── CLAUDE.md
├── docs/design.md          # 이 문서
├── packages/
│   ├── core/               # 엔진: 판정, 시뮬레이션, 상태, 저장, RAG, 정보 필터, 명령어 (LLM 호출 없음)
│   ├── mcp/                # MCP 서버 어댑터 (core만 사용, stdio) + 상태 화면 서버
│   └── ui/                 # 상태 화면 (캐릭터 시트, status.html)
└── content/
    └── scenarios/
        └── post_apoc/          # 시나리오 팩 (12.3)
            ├── scenario.yaml   # 자원·능력치·행동·상태 트랙·등급 사다리·화법·톤
            ├── factions/  npcs/  locations/  roles/  items/  storylets/
            ├── lore/           # RAG lore 컬렉션 원문 (*.md)
            ├── speech/         # 화법 규칙
            ├── prompts/        # GM 톤 프롬프트
            └── eval/           # RAG 검색 평가 세트
```

- `core`는 UI, 서버, LLM을 모른다. 나중에 Electron이든 호스팅 웹이든 껍데기만 바꿔 끼운다
- 어댑터(`mcp`)에는 게임 로직을 두지 않는다
- `.env`(로컬 설정)는 Git에 올리지 않는다

| 전쟁 | 세력 단위 추상 시뮬레이션 + 개인 단위 체험 |
| 시나리오 | 고정 스토리렛 10개 + 템플릿 15~20개, 세력 클락, 계절 |
| 사망·계승 | 아이언맨, 연대기, 다음 캐릭터 선택 (기존 NPC 포함) |
| 저장 | 세계 세이브, 이벤트 로그 |

| 시나리오 팩 | 장르 요소를 `post_apoc` 시나리오 설정으로 분리 (12.3) |

### 15.2 제외 (2차 이후)

- 세력 자원을 하나하나 옮기는 분배표. 분대 명령·지도부 회의·교역 방침은 12-31·12-33에서 넣었다 (9.11)
- 다른 시작 역할
- 대규모 전투, 외교
- 소문 왜곡, 세력 간 전파, 소문 조작
- 교역망과 복잡한 경제
- 연애
- 두 번째 시나리오 팩, 규칙 자체의 플러그인화

### 15.3 완성 기준

- 하급 전투원으로 시작해 여러 날을 생존하며 임무, 소문, 관계, 전쟁의 영향을 체감할 수 있다
- 사망하면 연대기가 남고, 같은 세계에서 다른 캐릭터로 이어서 플레이할 수 있다
- 중간에 종료해도 이어서 플레이할 수 있다

## 16. 로드맵

**2차**
- 분대장·간부 콘텐츠: 분대 명령, 회의 방침, 교역, 붉은연합 분대는 들어갔다(9.11). 남은 것은 분배표, 다른 무리(버들마을·하얀매·나루상단)의 간부 시나리오
- 시작 역할 선택 (혼자 / 외부 무리 / A~E 일원 / 간부)
- 소문 왜곡, 세력 간 전파, 소문 관리 행동
- 무리 단위 전투, 외교

**3차**
- 연애 요소
  - 성격 태그 궁합으로 관계가 빠르게 오르거나 내려감 (AI는 대화를 태그로 분류, 수치는 코드)
  - 관계 단계: 낯선 사람 → 동료 → 친구 → 호감 → 연인
  - 연애 대상은 이성 간으로 한정 (NPC 데이터의 연애 가능 필드로 설정)
  - 연인이 위험 요소가 되는 전개 (부상, 포로, 명령과의 충돌), 연인으로 계승
- 교역망과 경제
- 두 번째 시나리오 팩 (예: 중세 판타지)과 그에 필요한 규칙 플러그인화
- 배포 형태 결정 (Electron 또는 호스팅 웹)

### 17.3 게임 밖 이야기

- 플레이 중 `(( ))`로 감싼 말은 게임 밖 이야기다. GM은 서술·판정·시간 경과 없이 짧게 답한다 (규칙, 지난 결과의 이유). 정보 필터는 그대로 (캐릭터가 모르는 것은 말하지 않는다)
- 게임 수정(코드·콘텐츠) 요청은 게임 세션에서 하지 않는다. GM은 별도의 Claude Code 세션을 안내한다. 상태를 바로 바꾸는 것은 `~` 치트 (17.2)

### 17.2 치트 (개발 모드)

테스트를 위해 상태를 강제로 바꾸는 명령. 평소 플레이에는 없다

- 켜기: 저장소 `.env`에 `TRPG_DEBUG=1` (git에 올라가지 않는다). 웹 서버와 MCP 서버가 시작할 때 읽는다 (MCP는 Claude 세션을 새로 열면)
- 입력: `~`로 시작 (예: `~kill me`). 웹은 입력창에, Claude 세션은 GM이 `cheat` 도구에 그대로 넘기고 서술하지 않는다. 치트는 플레이어가 친 것만 실행한다 (GM은 스스로 쓰지 않는다, 원칙 2·3의 예외는 개발 모드뿐)
- 명령: kill, harm, set(몸 상태), heal, stat, skill, trait add/remove, xp, give, summon(인물·엑스트라), goto, time(+2d, +5h, 시간대 — 그 사이 세계도 돌아간다), weather, storylet, battle, relation, faction(자원·사기), help
- 기록: 바뀐 것은 모두 보통 이벤트로 남고, `cheat_used`가 세이브에 치트 표시를 남긴다 (슬롯에 "🛠 치트"). 규칙은 core `debug/cheats.ts`
