## 12. 데이터와 저장

### 12.1 콘텐츠

- 세력, NPC, 장소, 역할, 아이템, 스토리렛은 **YAML 파일로 Git에 관리**. 시나리오 팩마다 `content/scenarios/<id>/` 아래에 둔다 (12.3)
- 서버 시작 시 메모리로 읽는다. 세이브에는 콘텐츠를 복사하지 않고 id로만 참조한다
- **zod 스키마**로 콘텐츠와 런타임 양쪽 검증. 한 파일에 객체 하나 또는 목록을 둘 수 있다
- 검증은 오류를 한 번에 모아 보고하고, 콘텐츠끼리의 참조(역할의 시작 아이템 등)도 검사한다
- 현재 구현된 종류: 아이템, 역할, NPC, 시작 지식, 임무. 나머지는 해당 단계에서 스키마를 추가한다

### 12.2 세이브

- **SQLite** (로컬 파일). 세계 하나 = DB 파일 하나 (`saves/worlds/<worldId>.db`). 두 플레이 모드가 같은 파일을 쓰고, 잠금 파일로 동시 접근만 막는다 (11.5)
- 구조: **세계 세이브 1개 + 캐릭터 런 기록 여러 개**
- **이벤트 로그가 원본**, 상태는 스냅샷. 판정, 굴린 값, 상태 변경을 append-only로 기록
  - 첫 이벤트는 `world_created`(시작 캐릭터 포함). 상태는 이벤트를 차례로 적용한 결과다
  - 이벤트는 상태에 먼저 적용해 보고, 성공한 것만 기록한다
  - 이벤트가 150개 쌓일 때마다와 닫을 때 스냅샷을 남기고, 불러올 때는 마지막 스냅샷 + 이후 이벤트로 복원한다. 스냅샷은 마지막 하나만 남긴다 (12-110)
  - 이벤트를 적용할 때 상태 전체를 복사하지 않고 바뀐 부분만 새로 만든다 (immer, 구조 공유. 12-47). 그래서 상태는 리듀서 밖에서 고치지 않는다 (`TRPG_FREEZE=1`로 테스트하면 고친 곳이 드러난다). 하는 일이 같은 300턴 자동 플레이가 턴당 14.5ms → 6.9ms
  - `events`, `transcript` 테이블은 트리거로 UPDATE·DELETE를 막는다
- 세이브 형식 버전(`SAVE_SCHEMA_VERSION`)이 다르면 열지 않는다. 형식을 바꾸면 버전을 올리고 이전 세이브를 옮기는 방법을 만든다
- "새 게임"은 새 세계를 하나 더 만든다. 이전 세계는 `saves/worlds/`에 그대로 남는다. 형식·시나리오가 맞지 않는 세이브만 `saves/archive/`로 옮긴다
- 필드 추가처럼 호환되는 변경은 기본값을 주고 버전을 올리지 않는다 (예: 5단계의 `time`은 이전 세이브에서 시작 시각으로 본다)
- 아래 타입은 최종 목표 형태다. 현재 구현은 단계별로 필드를 늘려 간다

```ts
type WorldSave = {
  meta: { schemaVersion: number; scenarioId: string; worldId: string; day: number; updatedAt: string };
  time: GameTime;
  factions: Record<string, FactionState>;
  characters: Record<string, CharacterState>;   // 플레이어와 NPC 동일 스키마
  beliefs: Record<string, Belief[]>;            // 캐릭터별
  deeds: Deed[];
  rumors: Rumor[];
  locations: Record<string, LocationState>;
  clocks: Record<string, { filled: number; max: number }>;
  storylets: Record<string, { fired: number; lastFiredAt?: GameTime }>;
  flags: Record<string, boolean | number | string>;
  currentRun: { characterId: string; startedAt: GameTime };
  chronicle: RunRecord[];                       // 죽은 캐릭터들의 기록
  memory: { recentTurns: Turn[]; summaries: Summary[] };
  eventLog: GameEvent[];
};
```

### 12.3 시나리오 팩

게임 시스템(판정, 시간, 정보 필터, 평판, RAG 파이프라인)은 그대로 두고, 세계관을 시나리오 팩으로 갈아 끼울 수 있게 한다 (예: 나중에 중세 판타지).

**core에 하드코딩하지 않는 것 (시나리오 설정)**

- 자원 종류 (`post_apoc`: 식량, 물, 탄약, 의약품, 연료)
- 능력, 스킬(move)과 각 스킬이 쓰는 능력, 범위·상한, 성장 수치
- 상태 트랙 (`post_apoc`: 부상, 감염)
- 소속 등급 사다리
- 화법 규칙, GM 톤 프롬프트, 환경 위협·조우 테이블

**콘텐츠 구조**

```
content/scenarios/post_apoc/
  scenario.yaml
  factions/ npcs/ locations/ roles/ items/ storylets/
  lore/ speech/ prompts/ eval/
```

```yaml
# scenario.yaml (예시)
id: post_apoc
resources: [food, water, ammo, medicine, fuel]
stats: [strength, agility, nerve, senses, persuasion]
moves: [fight, scavenge, sense_danger, stealth, endure, persuade, aid]
condition_tracks: [harm, infection]
rank_ladder: [loner, outsider, grunt, squad_leader, officer]
speech_rules: speech/post_apoc.yaml
gm_tone: prompts/post_apoc_tone.md
```

**구현 규칙**

- 위 항목은 문자열 리터럴 타입이 아니라 시나리오에서 로드한 ID로 다룬다. zod 스키마는 시나리오 설정을 받아 동적으로 검증한다
- 세이브 메타(`WorldSave.meta`)와 RAG 메타데이터에 `scenarioId`를 기록한다
- 과하게 일반화하지 않는다. 지금은 "이름과 목록을 데이터로 뺀다"까지만 한다. 규칙 자체의 플러그인화는 두 번째 장르를 실제로 만들 때 한다

**구현 (`post_apoc`)**

- `scenario.yaml`의 목록은 `{ id, label }` 객체로 쓴다 (화면·프롬프트에 한국어 이름이 필요해서)
- 위 예시에 더해 둔 항목: `move_roles`(낌새 알아차리기·은밀 행동에 쓰는 행동), `harm_track`(판정 피해가 쓰는 트랙, 마지막 단계는 반드시 사망), `promotion`(진급 경로), `threats`(빨리감기 이상 징후 확률·문구)
- 시작 장면은 역할(`roles/*.yaml`의 `opening_scene`)에 둔다. GM 프롬프트 = 공통 규칙(core) + 시나리오 톤(`prompts/`) + 시작 장면
- ID는 예시를 따랐다 (`nerve`, `senses`, `scavenge`, `outsider`). 예시에 없지만 쓰는 곳이 있는 `resident`(주민, 원래 지원 인력 `staff`. 12-310에서 id를 바꿨다: 영어 staff가 간부·참모로 읽혀 '높은 사람' 배역에 잘못 쓰였다)와 `leader`(지도부)는 남겼다. `aid`(돕기)와 `infection`(감염)은 규칙을 구현할 때 목록에 넣는다
- 캐릭터의 부상은 `conditions`(트랙별 단계)와 `dead`로 바뀌었다. 세이브 형식 2. 형식이나 시나리오가 다른 세이브는 서버가 `saves/archive/`로 보관하고 새 세계를 연다
- 아직 core에 있는 장르 후보: 가치관 축(규율·의리 등), 행동 태그 13종, 활동 시간표(보초 등). 두 번째 장르를 만들 때 시나리오로 옮길지 정한다

### 12.4 월드와 시나리오 (12-15)

**말 정하기.** 플레이어에게 보이는 말과 코드의 이름이 다르다.

| 플레이어에게 | 코드·폴더 | 예 (`post_apoc`) |
|---|---|---|
| **월드**: 세계관 하나 | 시나리오 팩 (`content/scenarios/<id>/`, `Scenario`, 세이브 meta `scenario_id`) | 무너진 도시 가람 |
| **시나리오**: 그 월드에서 어떤 사람으로 어디서 시작하는지 | 시작 역할 (`roles/*.yaml`, 상태의 `roleId`) | 청솔형제단의 분대원 |
| 게임(세이브 슬롯) | 세계 (`saves/worlds/<worldId>.db`, `GameWorld`) | 1. 서진 · … |

코드 이름을 플레이어 말로 바꾸는 큰 이름 바꾸기는 하지 않았다 (세이브·환경 변수·폴더가 걸린다). 새 코드와 문서에서는 위 표로 옮겨 읽는다.

**새 게임 흐름** (MCP, core `game/newGame.ts`, 12-88): 월드 고르기 → 시나리오 고르기 → 캐릭터 만들기(4.2의 대화식 생성, 처음에 고른 시나리오의 지금 상황) → 수위 → 서술 방식 → 시작. 처음 설정이 복잡할수록 시작의 허들이 높아지므로, 플레이어가 글을 쓰는 단계는 두지 않는다. 월드가 하나뿐이어도 소개하고 고르게 한다. 사망 뒤 새 캐릭터는 같은 월드·시나리오라 바로 캐릭터 만들기부터.

- 월드 고르기에 보이는 것: `scenario.yaml`의 `world: { title, tagline, description }`만. 짧게 쓴다 (플레이어는 세계 배경을 다 읽지 않는다. 세계는 튜토리얼 시나리오로 천천히 익힌다). 죽음과 계승 같은 게임 규칙도 이 화면에 붙이지 않는다. 카드를 누르면 바로 고른다
- 시나리오 고르기: 12.4.1. 카드를 누르면 바로 고른다. 잠긴 시나리오는 자물쇠와 해금 조건만 보인다
- 시나리오의 소개와 지금 상황: `roles/*.yaml`의 `scenario: { title, pitch, intro }`. 무리에서 부르는 계급 이름(`factions.rank_labels`, `rankName`)이 카드에 "누구로" 보인다
- 시나리오는 스킬을 주지 않는다 (`start_skills: {}`). 계급마다 그 자리에 꼭 필요한 솜씨 하나는 계급 기본 훈련으로 받는다 (12-87). 스킬과 능력은 캐릭터 만들기의 첫 단계인 **과거 배경**(`creation.pasts`: 붕괴 전에 하던 일)이 기본값을 주고, 같은 포인트 안에서 고칠 수 있다. `post_apoc`: 소방관·경찰·군인·의사·간호사·도둑·조폭·정비사·건설 노동자·요리사·영업사원·배달원·교사·농부·학생
- 무리·계급·떠돌이 동행·동기와 이야기·소규모 무리를 고르는 단계(12-77, 12-84, 12-86)는 12-88에서 지웠다. 무리에 들어가 역할을 만드는 규칙(`buildCustomRole`, `joinRole`)과 가족 관계 규칙(`custom_start.group`, core `game/startGroup.ts`)은 남아 이야기(`join_faction`)와 튜토리얼의 가족에 쓰인다
- 단계별 서술 힌트: `creation.narration`

**여러 월드를 받는 구조**

- MCP 서버는 `content/scenarios/` 아래 `scenario.yaml`이 있는 폴더를 모두 월드로 읽는다 (`loadContentPacks`). 폴더 이름 = 팩 id. `SCENARIO=<id>`로 하나만, `CONTENT_DIR`로 다른 폴더 하나만
- `WorldManager`는 팩 여럿을 들고, 세이브를 만들 때 고른 팩 id를 meta에 남기고 열 때 그 팩으로 연다. 목록에는 아는 월드의 세이브만, 줄마다 월드 이름. 설치되지 않은 월드의 세이브는 목록에 없고 지우지도 않는다
- lore 색인은 월드마다 따로 (`.cache/rag/<id>-lore.db`), 처음 그 월드의 세계를 열 때 연다. 임베딩 모델은 함께 쓴다
- tool 입력 스키마(행동·능력 id 등)가 월드마다 다르다. 세계를 열면 MCP tool의 스키마를 그 월드 것으로 바꾸고 `tools/list_changed`를 알린다. 검증은 core가 그 세계의 월드로 한 번 더 한다
- `pnpm content:check`는 모든 월드 팩을 검사하고, 월드·시나리오 소개가 빠졌으면 알려 준다

**새 월드를 더할 때 (체크리스트)**

1. `content/scenarios/<id>/`를 만든다. `post_apoc`을 본뜬다: `scenario.yaml`(id = 폴더 이름, `world` 소개, 능력·스킬·상태 트랙·등급·생성 규칙·트레잇·이름·전쟁 수치), `roles/`(시나리오마다 `scenario` 소개), `factions/ npcs/ locations/ items/ storylets/ extras/ beliefs/ missions/`, `lore/`, `speech/`, `prompts/`(톤·GM 규칙·MCP 규칙·`intro.md`), `eval/`(검색 평가 세트, 선택)
2. `pnpm content:check`로 검증한다
3. 새 세션에서 `/play` → 0번 → 새 월드가 보이는지
4. 장르가 크게 다르면 아직 core에 남은 장르 요소를 먼저 옮긴다 (아래)

**`post_apoc`의 시작 시나리오** (12-17): 플레이마다 다른 경험이 되도록 무리마다 하나씩 + 직접 쓰기

### 12.4.1 시나리오 목록과 해금 (12-88)

월드를 고르면 그 월드에 준비된 시나리오 목록이 나온다 (core `game/startChoice.ts`). 시나리오는 역할(`roles/*.yaml`) 중 `scenario.order`가 있는 것이고, 목록 맨 위는 튜토리얼이다. 나머지는 잠겨 있고, 어느 시나리오에서든 그 시나리오에 적힌 해금 조건을 채우면 열린다.

- **해금**: `scenario.unlock: { text, when }`. `text`는 잠긴 카드에 보이는 말, `when`은 코드가 판정하는 조건 목록(하나라도 맞으면 열린다, `scenarioConditionSchema`)
  - `scenario_ended: <역할>` 그 시나리오가 끝났다 (클리어했거나 주인공이 죽었다) / `scenario_cleared: <역할>` 클리어했다
  - `enter: <구역>` 그 구역에 들어갔다 / `fight: <세력>` 그 무리 사람에게 공격 판정을 했거나 그 무리와 전투 장면이 열렸다 / `join: <세력>` 그 무리에 들어갔다 / `promoted: true` 계급이 올랐다
  - 판정: tool 하나가 끝날 때마다 그동안 쌓인 이벤트와 지금 상태로 (core `engine/scenarioProgress.ts`, `GameWorld`가 이벤트를 모은다). 열리면 `unlock_earned { id: <역할> }`, 세이브 폴더의 `unlocks.json`에 월드별로 남아 모든 판에 옮겨진다 (9.12)
  - 알림: tool 결과 뒤에 GM에게 "시나리오 「…」을(를) 플레이할 수 있습니다"를 장면과 섞지 말고 그대로 알리라고 붙이고, 상태 화면 위에 같은 말의 토스트를 띄운다. 토스트는 ×를 눌러야 닫히고(`POST /api/unlock-notice`), 닫지 않은 알림은 `unlock-notices.json`에 남아 다음 세션에도 뜬다. 턴 문(11.6)이 닫혀 있으면 새 알림은 서술이 끝난 뒤 시트와 함께 뜬다
- **클리어 목표**: `scenario.goal: { text, when, ending }`. 조건이 차면 `scenario_cleared`가 남고, GM은 `ending`대로 엔딩을 연출한 뒤 끝낼지(end_session) 계속할지 묻는다. 계속하면 주인공이 죽을 때까지 이어진다. 목표가 없는 시나리오는 죽음이 끝이다. 클리어 조건 `reunite: family`는 찾던 가족 중 누군가가 주인공 앞(같은 장면)에 나타난 것 (같은 구역에 들어가기만 해서는 아니다)
- **두 번째 주인공부터** (`engine/succession.ts`): 시나리오 없이 세계만 이어 간다. 시나리오의 연출 지침·클리어 목표·사연은 첫 주인공의 것이다 (`scenarioRole`이 비고, GM 지침에 "## 시나리오"가 없다). 후보는 둘이다
  - **조우한 사람**: 이전 주인공들이 이름을 알게 된, 살아 있고 플레이할 수 있는 인물 (무리가 달라도 된다, 무리의 우두머리는 뺀다). 그 사람이 있던 곳에서 이어 간다
  - **새 캐릭터** (`new:<세력>:<계급>`): 이전 주인공들이 조우한 무리(이름을 아는 사람의 무리, 속했던 무리)의 수색대원·분대장·간부 (`custom_start.ranks`, 이름은 `rankName`). 캐릭터 만들기부터 (과거 배경부터, 세계 소개 없이)
  - 어느 쪽이든 그 무리·계급의 **자리**(`heirSeat`)를 받는다: 개인 사연이 없는 콘텐츠 역할(목록에서 뺀 간부 역할 등), 없으면 코드가 만든 자리(`joinRole`), 무리가 없으면 떠돌이 자리. 분대원 NPC로 이어 가면 분대장 자리가 따라오지 않는다
  - 열린 다른 시나리오는 새 게임에서만 고른다
- **이어 가기**: `scenario.heirs: false`면 주인공이 죽었을 때 다음 캐릭터 후보가 없고 그 판은 죽음으로 끝난다 (`storyEnded`). GM은 죽음을 이야기의 끝으로 서술하고 묘비명·연대기 뒤 end_session으로 닫으며, 슬롯 목록에는 "사망 (이야기가 끝남)"으로 남는다. 해금은 그대로 일어난다 (튜토리얼에서 죽으면 비극의 고리와 담 밖의 사람이 열린다). 튜토리얼만 false. 아무도 만나지 못한 채 죽어 이어 갈 사람이 없을 때도 그 판은 끝난다
- **지금 플레이하는 시나리오**: 상태의 `scenarioRole`. 무리에 들어 역할(`roleId`)이 바뀌어도 그대로라, 클리어 목표와 시나리오의 연출 지침(`scenario.gm`, GM 지침의 "## 시나리오")이 이어진다. 시나리오의 스토리렛 태그도 무소속으로 시작한 시나리오이거나 아직 그 무리에 있을 때 이어진다. 새 캐릭터가 다른 시나리오로 시작하면 바뀐다
- **미리 정해진 사연**: 역할의 `history`(배경 부품, 12.6)와 `background`(기억)는 세계를 만들 때 세이브의 역사가 된다. `start_bonds { ids, trust, affection, respect, best }`는 그 인물들이 주인공을 보는 관계를 범위 안에서 무작위로 올린다 (가장 친한 친구는 축마다 하나 더). `family { zone, count }`는 코드가 주인공 나이에 맞춰 가족을 만들어 그 구역 무리의 사람으로 둔다 (형제자매·자식과 부모 한 사람은 주인공의 성을 따른다). 주인공은 가족의 이름을 알지만 어디 있는지 모르고, 그 무리 사람들은 가족을 안다. 스토리렛 배역 `background: family`로 부른다
- 목록에 없는 역할(간부 등)은 무리에 들거나 다음 캐릭터로 이어 갈 때 그 자리의 규칙(상관·임무·이야기)으로만 쓴다. 무리에 들 때 빌려 오는 역할은 개인 사연이 없는 것 먼저
- **가람의 시나리오** (`post_apoc`)

### 12.5 직접 쓰는 시나리오 (12-16)

> 12-77에서 새 게임의 보기에서 뺐다. 글로 통째로 쓰는 시작 대신 무리·계급·직분을 고르고(코드가 이 절의 `buildCustomRole`·`checkCustomStart`로 역할을 만든다) 동기와 이야기를 쓴다 (4.2 아래 "무리 → 역할 고르기"). 아래는 역할을 만드는 규칙으로 남는다. `custom_start` 툴 입력·`describeCustomStartOptions`는 지웠다.

시나리오 고르기에 **직접 쓰기**가 있다 (월드 팩에 `custom_start`가 있을 때). 플레이어가 누구로, 어디서 시작하는지 글로 쓰면 GM이 그 글을 월드의 부품으로 옮기고, 코드가 검증해 역할을 만든다. core `game/customStart.ts`.

- 흐름: 직접 쓰기 → 플레이어의 글 → GM이 옮기기(`create_character(custom_start: {...})`) → 확인(이대로 / 다시 옮기기 / 다시 쓰기) → 지금 상황(GM이 쓴 첫 장면) → 캐릭터 만들기
- GM이 고르는 것 (목록 안에서만, 코드가 검증): 세력(또는 무소속), 계급, 직함(짧은 글), 시작 구역, 소지품 꾸러미, 시작 훈련, 나이, 첫 장면(한두 문장), 지난 삶(몇 문장)
  - 계급: 세력에 속하면 `custom_start.ranks` (post_apoc: 분대원·주민·분대장·간부. 고를 수 있는 계급은 직분이 정한다). **무리마다 한 자리뿐인 지도부는 고를 수 없다.** 참모·중간 리더는 간부·분대장으로. 리더를 원하면 GM이 가장 가까운 계급으로 옮기고 알린다
  - 무소속: `free_rank`(혼자)로, `free_locations`(누구의 땅도 아닌 곳)에서만. 세력이 있으면 그 세력이 차지한 구역에서만
  - 소지품은 월드가 정한 꾸러미 중 하나 (꾸러미 6개). 시작 훈련은 2포인트, 스킬 하나에 +1까지 (분대원과 같은 무게). 나이 16~65
  - 월드 밖의 세력·인물·장소·물건은 만들지 않는다
- 코드가 정하는 엔진 값: 아는 인물(같은 세력 모두, 무소속은 없음), 상관(같은 세력에서 바로 위 계급의 인물. 간부면 지도부, 분대장이면 간부), 임무·배급(같은 세력의 콘텐츠 역할에서), 시작 지식(그 역할과 계급이 같을 때만. 분대원의 지식을 참모에게 주지 않는다), 스토리렛 태그
- 플레이어가 쓴 지난 삶은 **주인공 자신의 기억**(믿음, 대략적)으로만 남는다. 세계의 사실이 되지 않는다 (원칙 4, 5)
- 만든 역할은 세이브에 들어간다 (`world_created.customRole`, 상태의 `customRole`, `roleId: "custom"`, 세이브 형식 8). `GameWorld.content`가 그 역할을 `roles`에 넣어 주므로 역할을 읽는 곳(임무, 상관, 시작 장면, 연대기, 계승)은 그대로 동작한다. 사망 뒤 새 캐릭터도 같은 역할로 이어 간다
- 무소속은 플레이어의 `factionId`가 비어 있다 (엑스트라의 떠돌이와 같다). 배급·임무·세력 소식이 없고, 진급 경로도 없다. 며칠 지내도 멈추지 않는 것을 테스트로 확인했다
- 무소속은 수색(4.7)으로 먹을 것을 구한다. 꾸러미마다 먹을 것이 하나씩 있다
- 자유 시나리오의 임무·배급·태그는 같은 세력에서 계급이 같은 콘텐츠 역할을 먼저 빌린다 (분대장이면 분대장 시나리오)
- 무소속의 이야기 (`storylets/world_loner.yaml`, 태그 `world` + `factions: [none]`): 무리마다 들어갈 길이 하나씩 있다 (청솔 순찰조, 붉은연합 통행세, 하얀매 수색꾼, 나루상단 하루 품, 버들마을 정문의 하룻밤). 하루벌이·거래·다른 떠돌이·모닥불 소문도 있다. 들어가면(`join_faction`) 그 무리의 상관·동료·임무·배급이 생긴다
- 스카우트 (12-21, `storylets/world_scout.yaml`): 공적 9 이상(진급할 만한 사람, 조건 `merit_gte`)이 되면 다른 무리가 손을 내민다. 붉은연합(마경수, 약탈조장), 청솔형제단(최선희, 분대장), 나루상단(탁봉수, 호위대장), 하얀매(서은영의 편지, 진료소), 버들마을(장현우, 경비조장). 받아들이면 배신 행적과 옛 상관의 신뢰 하락 뒤 옮겨 가고, 거절하고 알리면 공적이 쌓인다. 옮긴 무리의 같은 계급 시나리오 이야기가 이어진다
- 무소속의 긴 이야기 (`storylets/world_loner_arcs.yaml`, 12-22): 떠돌이 무리(만남 → 물 → 저녁 → 열병 → 배신 → 갈 곳), 문소라의 의뢰 장부(일감 셋, 붉은연합을 돕는 봉인된 깡통), 시립병원 옥상의 무전수. 이름 없는 떠돌이는 keep/recall로 같은 사람이 이어진다
- 무리 사이 정치 (`storylets/world_politics.yaml`, 12-22): 버들마을 이탈 전의 긴장과 뒤의 장면, 나루상단이 편을 든 뒤의 물값. 기존 이야기의 선택이 b_waver·e_side를 당기고 늦춘다 세력에 속해도 분대원용 임무만 있다 (간부용 임무·스토리렛은 콘텐츠가 필요하다)

### 12.7 수위 (12-57)

성인 주제(성인 사이의 잠자리, 성적인 농담·괴롭힘·위협)는 세계마다 켜고 끈다. 기본은 끔이다. 연애는 여기에 들지 않는다 (12-100).

- 새 게임에서 시나리오(또는 직접 만들기의 확인) 다음, 캐릭터 만들기 전에 묻는다 (월드 팩에 `content_rating`이 있을 때). 게임 중에는 상태 화면의 설정 창(12-63)에서, 또는 플레이어가 말하면 GM tool `set_content_options { mature }`로 바꾼다. 상태 `options.mature`, 이벤트 `content_options_set`
- **연애는 성인 콘텐츠가 아니다** (12-100): 끌림·호감·연애·고백·연인·질투·삼각관계는 수위와 상관없이 다룬다 (성인끼리만). 수위가 가리는 것은 성적인 것뿐이다: 잠자리(암전), 성적인 농담·괴롭힘·위협과 그 뒷이야기. 꺼져 있으면 연인 사이도 손잡기·기대기·입맞춤까지
- 이야기 태그 `content_rating.tag`(post_apoc: `mature`)가 붙은 이야기는 수위가 켜져 있고 **주인공과 배역이 모두 `adult_age`(18) 이상**일 때만 열린다. 나이를 모르면 성인이 아닌 것으로 본다. 엑스트라 틀이면 틀의 가장 어린 나이로 본다
- GM 상태에 수위와 지킬 선이 들어간다: 꺼져 있으면 그런 것을 장면에 들이지 않는다. 켜져 있어도 미성년자는 어떤 경우에도 대상이 아니고, 잠자리는 암전, 노골적인 묘사는 하지 않고, 성폭력은 시도와 위협까지만(어떤 판정 결과로도 일어나지 않는다, 벗어나거나 대가를 치르는 것으로)
- 폭력과 죽음, 생존의 잔혹함은 수위와 상관없이 다룬다
  - 인육·사람 매매 (12-337, docs/cannibal-plan.md): 잔혹함 자체는 수위와 상관없이 열고, 해체·도축은 결과로만 그린다. 노골적인 글은 믿음·행적의 mature 칸(렌즈)에만. 주인공도 가담할 수 있다 (행적 잔혹·소문·무리 반응·마음 트랙). 성적 착취에는 주인공이 가담하지 않는다
- **연애** (12-58, `scenario.romance`, `engine/romance.ts`): 둘 다 성인일 때만 (12-100부터 수위와 상관없다. 순수한 연애 이야기 11개는 mature 태그를 뗐고, 잠자리 "같은 담요"와 성적 위협·뒷이야기는 태그가 남는다. 성적 위협 배역 `menace`를 쓰는 이야기만 태그가 꼭 있어야 한다)
  - 끌림은 인물 데이터: NPC의 `attracted_to`(끌리는 성별 목록, 빈 목록이면 아무에게도). 없으면 월드의 `orientation` 비율로 인물 id에서 정해진다 (판마다 같다). 주인공의 마음은 플레이어가 정한다
  - 마음: 끌리고 호감이 `interest_affection` 이상. GM에게는 장면의 **눈길**(겉으로 보이는 낌새)로만 보인다 (속마음을 말하지 않는다, 원칙 4)
  - GM tool `romance { target, action }`: flirt 다가가기(`flirt_moves` 판정, 하루에 한 사람 한 번, 끌리지 않으면 호감이 오르지 않는다), confess 고백(받아들일지는 코드: 끌림·호감 `accept.affection`·신뢰 `accept.trust`, 마음을 둔 다른 사람보다 주인공을 더 좋아하는가), break_up 이별. 잠자리는 암전
  - 상태 `romances`(두 사람: lovers/ended), 인물 사이 관계에 `lover`(연인)
  - **남의 연인**: 연인이 있는 사람은 그 연인보다 주인공을 더 좋아할 때만 고백을 받는다. 받으면 그 연인은 버림받고 주인공을 원망하며, 이야기 "빼앗긴 사람"(배역 `jilted`)으로 찾아온다
  - **뺀 것** (12-185): 연인을 둘 둔 데 따른 질투(보는 앞에서·하루마다 알아채기, 식으면 떠남, 이야기 "누구야"), 주인공에게 마음 있는 사람들끼리의 앙금, 다가가기만 해도 나서던 연적. 연인을 둘 둔 결과는 GM의 연기로 남는다. 예전 세이브의 `romance_jealousy`는 읽기만 한다
  - 연인이 죽으면 마음 트랙 +`grief_nerves`
  - 이야기 배역 `romance: lover | suitor | ex | jilted`(연인, 마음 있는 사람, 헤어진 사람, 연인을 빼앗긴 사람), 조건 `has_lover`. 12-193: 마음 있는 사람은 주인공이 만난 사람만 (처음 보는 사람이 연애 이야기에 나오지 않게), 연애 배역에도 무리 조건 `faction`이 먹는다. 연애 배역을 쓰는 이야기는 성인 주제 태그가 있어야 한다 (콘텐츠 검증)
  - 세이브 형식 29
- **성적 위협** (12-59): 인물 데이터 `menace: harass | coerce | assault` (성적인 농담·괴롭힘 / 몸을 거래 조건으로 / 위협과 시도). 엑스트라 틀은 `menace { kind, chance }`로 만들 때 굴린다. GM이 즉석에서 정하지 않는다
  - 수위가 켜져 있고, 둘 다 성인이고, **그 자가 주인공에게 끌릴 때만** 쓰인다 (성별로 정하지 않는다: 끌림 데이터를 따른다)
  - GM 상태: 그런 자가 장면에 있으면 "[GM 전용, 성인 주제]" 한 줄 (판정과 이야기로만, 위협·시도까지)
  - 이야기 배역 `menace: [종류]`(성인 주제 태그 필수), 효과 `grudge { who, why }`(그 자를 원수로: 배경 enemy가 더해지고 원수 이야기가 열린다)
  - post_apoc: 마경수(거래 조건), 석중기·배철구(괴롭힘), 사동규(거래 조건), 엑스트라 붉은연합 보초(괴롭힘 20%)·약탈조원(시도 15%)·떠돌이 무리 우두머리(거래 조건 20%)
  - 세이브 형식 30
- **이야기** (12-60, `storylets/romance.yaml` 23개, 모두 `[world, mature]`, 갇힌 동안은 `[captivity, mature]`): 연애(물 받는 줄의 눈길, 드럼통 불가, 바깥에서 지켜 준 사람, 같은 담요의 다음 새벽(암전), 다친 연인, 섬으로 보내지는 연인, 연인과 무리 사이), 질투·삼각관계(물통을 두고 맞서는 두 사람, 연인이 보는 앞의 선물, 알아챈 연인의 추궁, 헤어진 사람과 다시, 우물가의 연적), 성적 위협(길 위의 농담, 배급 줄의 괴롭힘 → 불 꺼진 통로, 폐허에서 덮치려 드는 자, 약값으로 몸을 요구하는 자 → 받으러 온 날, 갇힌 밤의 간수, 문을 열 수 있다는 자), 그 뒤(잠 못 드는 밤과 원수 삼기, 털어놓기, 갚기)
  - 위협 이야기마다 ai_direction에 같은 선: 위협과 시도까지만, 어떤 결과에서도 성폭력은 일어나지 않는다, 몸을 묘사하지 않는다, 피해자를 탓하지 않는다. 최악이어도 빠져나온 데서 끊는다 (대가는 wound·마음·빼앗김·끊긴 배급)
  - 연인 관계 3쌍 (모두 성인, 털어놓아야 드러남): 방소라↔고석진, 민서연↔임동욱, 문소라↔모준기
  - 효과 `end_romance { who }`, `npc_heal { who, steps }`. 위협 배역은 이 구역의 이름 없는 인물(엑스트라)도 고른다. 연애 배역도 몸 상태 조건을 본다. 세이브 형식 31

### 12.6 직분과 배경 (12-46)

시나리오(정해진 시작 역할)보다 **직접 만들기**가 기본이다. 새 게임에서 "직접 만들기"가 먼저 보이고, 정해진 시나리오는 "추천 시작"으로 남는다. 플레이어는 어느 무리에서(세력), 무슨 일을 하는(직분), 어떤 자리의(계급) 사람인지와 지난 일을 쓴다.

**직분** (`scenario.occupations`, 12-80): 무리 안에서 맡은 일. 시나리오(역할)와 인물이 정한다. 새 게임에서 따로 고르지 않는다. 떠돌이는 직분이 없다. 떠돌이가 무리에 들면 우두머리가 붕괴 전 직업을 보고 직분을 권한다 (공통 규칙 22, 12-309)
- 직분마다: 훈련(`skills`), 도구(`kit`), 일감(`missions`, 무리를 가리지 않는다), 이야기 태그(`occ_<id>`, 간호사·의사는 의무병 이야기 `occ_medic`를 함께 쓴다)
- 직분 안의 사다리는 없다 (12-83). 계급(분대원·분대장·간부)이 곧 사다리다. 직분의 일감을 완수하면 평판(`standing`) +1, 이야기 효과 `standing: ±n` (숫자로만 쌓인다). 캐릭터의 `occupation { id, standing }` (NPC도 같은 스키마, 원칙 6)
- 이야기 조건 `occupations: [id | none]`, `occupations_not`, `occupation_step_gte` (계급으로 본다: 분대원·주민 0, 분대장 1, 간부 2, 12-82)
- `post_apoc`: 군(수색대원·수비대원·의무병)과 살림(요리사·목수·상인·종교인·정비공·간호사·의사). 군은 나가는 사람(수색대원: 폐허·길·전선·습격·호위, 12-81에 전투원을 합쳤다)과 지키는 사람(수비대원: 담·문·창고)으로만 나눈다. 큰 전쟁이 나면 모두 나간다. 간호사·의사는 붕괴 전에 의술을 배운 사람이라 바깥 싸움에 내보내지 않는다 (하얀매·청솔·섬의 의료진: 의사 셋, 간호사 여섯). 살림을 맡는 사람의 계급은 주민(`staff`)
- NPC도 직분이 있다 (12-50, 64명: 전투원 37, 의무병 12, 상인 9, 요리사 3, 정비공 3, 수색대원 3, 목수·종교인 1). GM의 인물 소개에 보이고, 계승하면 그 직분의 일감·이야기가 이어진다. 배역 `occupations: [id | same]`로 같은 직분의 동료를 부른다

**배경 부품** (`custom_start.history`): 플레이어가 쓴 지난 일 중 **세계의 사실이 되는 것**. GM은 글을 이 목록 안에서만 옮기고 코드가 검증한다. 나머지 지난 삶은 지금처럼 주인공의 기억(믿음)으로만 남는다 (원칙 4, 5)
- `loss { who, by, where }` 잃은 사람들 / `enemy { target, why, knows_you }` 원수 (세력 또는 **기존 인물도 된다**: 그 사람이 정말 그 일을 한 것이 된다) / `kin_alive { template, label, zone }` 살아서 기다리는 가족 / `seeking { template, label }` 찾는 사람 / `debt { faction, size }` 빚 (크기는 월드의 `debt_sizes`) / `deserter { faction }` 도망쳐 나온 무리
- 세계에 남는 것: 플래그(`bg_loss`, `bg_loss_by_<세력>`, `bg_enemy`, `bg_enemy_person`, `bg_hunted`, `bg_kin_alive`, `bg_seeking`, `bg_debt`, `bg_deserter_<세력>`), 주인공의 기억 한 문장씩, 원수·가해자가 인물이면 주인공이 그 이름을 안다(원수가 주인공을 알면 그쪽의 신뢰 -2), 살아 있는 가족은 그 구역에서 기다리는 연고 동행(7.9), 찾는 사람은 코드가 아무 구역에나 둔다(아무도 모른다), 빚. 상태의 `background`, 세이브 형식 22
- 배역 `background: enemy | enemy_member | kin | sought | creditor | deserted` (+ `here`: 지금 이 구역에 있는 사람만, 함께 다니는 사람은 늘 여기): 배경의 사람을 이야기가 부른다. 원수가 인물이면 `enemy_member`는 그 사람의 무리(본인 빼고). `creditor`는 빚진 무리, `deserted`는 도망친 무리의 사람
