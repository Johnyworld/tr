# 배포 방안 (메모, 구현 전)

> 상태: 검토 메모 · 2026-11-13. 당장 할 일은 아니다. 나중에 다른 사람도 MCP 모드로 즐길 수 있게 배포할 때 참고한다.

목표: 다른 사람이 이 저장소를 받지 않고도, Claude 앱(Claude Code·Claude 데스크톱)에서 MCP 모드로 게임을 할 수 있게 한다.

어느 방식이든 **GM(서술)은 사용자 쪽 Claude가 맡는다.** 각자의 Claude 구독으로 돌기 때문에 우리가 Claude API 비용을 내지 않는다. 우리 서버가 Claude API를 불러 GM을 돌리는 웹 앱 모드와는 다르다. claude.ai 로그인을 우리 앱에 연결하지 않는다는 원칙(CLAUDE.md 원칙 10)도 그대로 지킨다.

## 지금 상태

- MCP 서버는 저장소 전체에 기대고 있다.
  - pnpm 워크스페이스, `tsx`로 TypeScript 직접 실행
  - 시나리오 콘텐츠
  - 네이티브 모듈 `better-sqlite3`, `sqlite-vec`
  - bge-m3 임베딩 모델 (약 570MB, 첫 실행 때 내려받는다)
- 그래서 지금은 저장소를 받아 `pnpm install`까지 해야 한다.

## 방안 A: 로컬 설치 (npm 패키지 + Claude Code 플러그인)

사용자 컴퓨터에서 MCP 서버가 돈다. 세이브도 각자 컴퓨터에 남는다.

**할 일**
- MCP 서버와 core를 JS로 번들해 npm 패키지로 낸다. 시나리오 콘텐츠와 빌드된 상태 화면(`status.html`)도 같이 넣는다.
- Claude 설정에는 `npx -y <패키지명>` 한 줄만 넣으면 되게 한다.
- 세이브 위치를 저장소 안이 아니라 사용자 홈 폴더(예: `~/.trpg/saves`)로 바꾼다.
- Claude Code 플러그인으로 MCP 설정, `/play`·`/quit` 스킬, GM 지침을 한 묶음으로 낸다. Claude Code 사용자는 플러그인 설치만으로 `/play`까지 바로 쓴다. Claude 데스크톱은 MCP만 등록하고 `play` 프롬프트로 시작한다.

**걸리는 점**
- 네이티브 모듈은 OS·CPU별 바이너리가 필요하다. 보통은 미리 빌드된 것을 받지만, 환경에 따라 설치가 실패할 수 있다.
- RAG 모델 다운로드(약 570MB). 배포판은 기본으로 끄거나(`RAG=off`), 첫 실행에 받는다고 안내한다.

**장점:** 우리가 운영할 것이 없다 (서버·DB·백업·개인정보 보관 없음).

## 방안 B: 원격 MCP 서버 (우리가 서버를 띄운다)

우리 서버에서 엔진(core), 세이브, bge-m3 임베딩, 시나리오 콘텐츠가 모두 돈다. 사용자는 Claude 앱에 MCP 서버 주소(HTTPS URL)만 추가한다. Claude 앱은 원격 MCP(커스텀 커넥터)를 지원한다.

- 우리 서버는 판정·상태·저장·검색만 한다. GM은 사용자 쪽 Claude다
- 상태 화면도 같은 서버에서 웹 페이지로 제공한다

**장점**
- 설치가 필요 없다. 네이티브 모듈·모델 다운로드 문제가 없다
- 업데이트를 서버에서 한 번만 하면 모두에게 반영된다

**할 일**
1. **전송 방식:** 지금은 stdio(로컬 전용)다. MCP SDK의 Streamable HTTP 전송을 붙인다.
2. **사용자 구분과 인증:** 지금은 1인용이라 세이브가 한 폴더에 있다. 사용자별로 세이브를 나누고 누가 접속했는지 알아야 한다. 원격 MCP는 OAuth 로그인이 표준이라 가장 큰 작업이다.
   - 친구 몇 명과 시험할 때는 인증 없이 사람마다 다른 비밀 URL을 주는 방식으로 시작할 수 있다.
3. **동시 접속:** 지금은 프로세스 하나가 세계 하나를 연다. 여러 사용자의 세션을 동시에 들고 있도록 바꾼다. 세이브 잠금도 파일 잠금에서 사용자·세션 단위로 바꾼다.
4. **저장소 (DB 운영, 아래)**
5. **운영 비용과 보안:** 서버, 임베딩 계산(CPU·메모리), HTTPS, 남용 방지(요청 제한).

### DB 운영

원격으로 가면 세이브를 우리가 보관하므로 DB 운영이 따라온다. 규모에 따라 단계적으로 한다.

**1단계: SQLite 파일 그대로**
- 사용자마다 세이브 파일(`saves/<사용자>/worlds/*.db`)을 서버 디스크에 둔다. 지금 코드를 거의 그대로 쓴다.
- 별도 DB 서버가 없어 운영 부담이 가장 적다. 친구들과 시험하거나 수십 명 규모까지는 충분하다.
- 서버 한 대에 묶인다. 디스크 백업을 직접 챙긴다 (주기적 스냅숏, 또는 Litestream 같은 도구로 S3에 복제).

**2단계: 관리형 Postgres**
- 사용자가 늘거나 서버를 여러 대 띄울 때 옮긴다.
- Neon, Supabase 같은 관리형 서비스를 쓰면 백업과 운영은 서비스가 맡는다.
- DB 접근을 저장소(repository) 레이어로 모아 두었으므로, 옮길 때 고칠 곳이 그쪽에 모여 있다.

**DB 말고 챙길 것**
- **임베딩 색인:** 공용 로어 색인은 하나라 가볍다. 사용자별 기억(memory) 색인은 세이브에서 다시 만들 수 있는 파생 데이터라 날아가도 복구된다.
- **개인정보:** 세이브는 사용자의 플레이 기록이다. 백업, 삭제 요청 처리, 접근 제한을 처음부터 챙긴다.
- **콘텐츠 라이선스:** 시나리오·로어를 같이 배포하므로 공개 범위를 정한다 (방안 A도 같다).

## 정리

| | 방안 A: 로컬 설치 | 방안 B: 원격 서버 |
|---|---|---|
| 사용자 설치 | npm 패키지(+ 플러그인) | URL 추가만 |
| 세이브 위치 | 각자 컴퓨터 | 우리 서버 |
| 우리 운영 | 없음 | 서버, DB, 백업, 인증, 보안 |
| 걸리는 점 | 네이티브 모듈, 모델 다운로드 | OAuth, 동시 접속, 운영 비용 |
| GM 비용 | 각자 Claude 구독 | 각자 Claude 구독 |

- 운영 부담 없이 가려면 방안 A
- 설치를 가장 쉽게 하려면 방안 B. 시작은 SQLite + 비밀 URL로 작게, 사용자가 늘면 OAuth와 Postgres로
