# 플레이 테스트 방법

플레이 테스트는 **하네스 방식**으로 돌린다: 에이전트 하나가 GM 겸 플레이어로 `scripts/playtest/`의 하네스를 몰고, 결과는 파일로 받는다.

## 왜 하네스인가 (PT14에서 정함, 2026-11-22)

| | 하네스 (PT8~13) | GM·플레이어 두 에이전트 (PT14) |
|---|---|---|
| 판당 토큰 | 약 30만 (열 판에 300만 남짓) | 약 1억 2천만 (대부분 캐시 읽기) |
| 도구 호출 | 한 번 실행에 1~4개 묶음, 판당 80~90회 | 하나씩, GM 호출 판당 300회 안팎 |
| 결과 | 파일 (`oN.txt`) | GM 대화에 그대로 쌓임 |

PT14는 열 판이 30분 남짓 만에 5시간 한도와 주간 한도를 다 써서 중간에 멈췄다. 그래서 다음 판부터는 하네스로 한다.

- 판 수는 기본 3~5판. 열 판은 사용자가 정할 때만
- Claude 앱 세션을 판마다 새로 띄우거나(GM 세션 + 플레이어 에이전트) 플레이어 에이전트를 따로 두는 방식은 쓰지 않는다. 정보 누설·플레이 감각을 꼭 봐야 할 때만, 사용자에게 비용(판당 1억 토큰 안팎)을 먼저 말하고 1~2판으로
- 판 하나는 서브에이전트(Agent 도구) 하나가 맡는다. 같은 세션에서 여러 판을 동시에 돌려도 된다
- 판을 맡는 에이전트는 Sonnet으로 돌린다 (`model: "sonnet"`, 프로젝트 설정의 서브에이전트 기본값도 Sonnet). 원문 보고서를 묶고 고칠 것을 거르는 일은 메인 세션(Opus)이 한다

## 하네스

```bash
# 1. 세계 만들기 (해금과 상관없이 시나리오를 바로 고른다. 사용자의 saves/를 건드리지 않게 scratchpad 아래 폴더를 쓴다)
npx tsx scripts/playtest/setup.ts <판 폴더>/saves role_a_grunt '{"past":"soldier","persona":{"temper":2,"talk":-1},"settings":["ideal_obedience","secret_deserter"]}' 7

# 2. 한 번 실행: cN.json의 호출을 차례로 돌리고 결과를 oN.txt로
npx tsx scripts/playtest/play.ts <판 폴더>/saves <세계 id> <판 폴더>/c0.json > <판 폴더>/o0.txt
```

- `cN.json`: `[{"tool":"take_action","args":{...}}, ...]`. 한 번에 1~4개. `start_session`은 하네스가 부른다 (`SHOW_START=1`이면 그 결과도 출력). 세션을 열 때 처리한 일("지난번 뒤에 일어난 일": 쓰러진 동안의 돌봄 등)은 실제 플레이에서 GM이 먼저 받는 글이라 늘 출력한다
- 실행마다 MCP 서버를 새로 띄운다. 상태 화면·RAG는 끄고 치트는 켜 두지만 쓰지 않는다
- 특정 커밋으로 돌리려면 그 커밋을 `git worktree`로 꺼내고 `PLAYTEST_ROOT=<그 폴더>`를 붙인다 (다른 세션의 작업이 섞이지 않게)
- 캐릭터 JSON에 성격·설정·출신을 넣는다 (PT13은 성격을 비워 성격 축을 못 봤다)

### 알려진 한계 (하네스 탓)

- 실행마다 서버가 새로 떠서 캐릭터 만들기 상태가 날아간다. 계승 뒤 새 캐릭터 만들기는 한 실행(cN.json 하나)에 몰아넣는다
- 에이전트가 GM 상태를 다 보므로 정보 누설(원칙 4)은 GM에게 보이는 글만 따질 수 있다. 플레이어 쪽 감각은 볼 수 없다
- 호출을 묶다 보면 이야기를 건너뛰거나 판정을 마치기 전에 보고할 수 있다. 결과를 읽고 다음 묶음을 쓴다

## 에이전트에게 주는 지시 (틀)

```
너는 1인용 AI TRPG(한국어)의 GM이자 플레이어로서, MCP 엔진을 하네스로 몰아 판 하나를 플레이하고 보고서를 쓴다.
- 하네스: docs/playtests/README.md의 "하네스". 판 폴더 <폴더>, 세계 id <id>. 코드·콘텐츠를 고치지 않는다. 커밋하지 않는다
- 처음에 get_gm_guide와 get_scene으로 규칙과 상태를 읽는다. 치트는 쓰지 않는다. 정보 명령어(?상태 등)는 써도 된다
- 목표: 게임 안 N일 또는 하네스 실행 M회. 주인공이 죽으면 계승해서 이어 간다
- 이번에 볼 것: <바뀐 규칙 목록, docs/design.md 12-xxx>
- 보고서: docs/playtests/<날짜>-mcp-<회차>-<판>.md 하나. 1. 요약 번호 목록 2. 기본 정보 3. 날짜별 진행 4. 발견 5. 바뀐 규칙이 어땠는지(의도대로 / 문제 / 못 봄) 6. 좋았던 것
- 발견에는 종류([버그] [균형] [설계] [정보 누설] [이야기 전제] [GM 부담])와 함께 심각도를 붙인다:
  - [막힘] 판이 더 나아갈 길이 없거나 같은 일을 되풀이해야 했다
  - [틀림] 상태·믿음·관계가 실제와 다르게 남았다, 정보 누설
  - [어색함] 그 밖 (문구, 판 하나의 균형 감각, 있으면 좋을 설계)
- [막힘]·[틀림]은 근거(oN.txt 문구)와 고칠 안을 자세히, [어색함]은 4절 끝에 한 줄 목록으로만. 한 번만 나온 것도 빠짐없이 적는다
- docs/playtests/backlog.md에 있는 것이 다시 나오면 "다시 나옴: backlog"를 적는다
```

판이 끝나면 원문 보고서들을 `<날짜>-mcp-<회차>.md` 하나로 묶는다 (여러 판에서 겹친 것을 앞에, 판 하나에서만 나온 것도 빠짐없이). 묶음 보고서 맨 앞에 [막힘]·[틀림] 건수와 두 판 이상에서 겹친 종류 수를 적고 지난 회차와 비교한다. 고칠 것은 backlog.md의 "고치는 기준"으로 거르고 나머지는 backlog.md로 옮긴다.
